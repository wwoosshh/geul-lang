# 연구: 의미를 잃지 않는 GPU 컴파일러

판: 초안 1 (2026-10-08). 결정 기록 D-48. 산출물은 [`research/gpu/`](../research/gpu/README.md).
이 문서는 연구 계획이다 — 판정 기준을 결과보다 먼저 적고, 결과가 나오면 상태 칸만 고친다.

## 1. 왜 다시 여나

D-45 는 **쓸모**(사람들이 쓸 것인가, 확실히 돈이 되는가)를 근거로 개발을 접었다. 이번 연구는 쓸모가 아니라
**언어의 능력**을 묻는 개인 연구다. 그래서 D-45 의 판단과 부딪히지 않는다. 호환 약속(11장)은 그대로다.

## 2. 출발점

- **다른 연구의 발견.** AI 연산 과정에서 의미 손실 — 시작값이 어디로 가야 하는지, 무슨 값인지 — 이 고수준뿐
  아니라 저수준에서도 일어나고, 그 훼손이 부분함수로 존재하며 흔히 아는 AI 버그(한 단어 무한 반복, 관계없는
  외국어 출력, 논점 상실, 출력 실패)로 보인다.
- **공개 사례.** Anthropic 의 [사후 분석](https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues)
  (2025-09): TPU 서버 설정 오류로 영어 답에 태국어·중국어 글자가 섞였고, XLA:TPU **컴파일러**의 잠복 버그가 토큰을
  고르는 근사 top-k 연산을 잘못 컴파일했다 — 고친 방법은 더 높은 정밀도의 정확한 top-k 였다. 저수준 연산과
  컴파일러의 의미 훼손이 "AI 버그"로 보인 사례다.
- **글 자신의 역사.** 1세대를 끝낸 원인 중 둘이 "타입 없는 IR"과 "조용한 실패"였다(01장) — IR 에서 값의 정체가
  사라지자 백엔드가 추측했고, 그것이 결함이 됐다. 컴파일러 안의 의미 손실이다.

## 3. 질문

**말하는 어법의 문법이 GPU 연산에서 값의 자리·정체·흐름이 훼손되는 것을 컴파일 시점에 막을 수 있는가.
그리고 그 의미를 기계어 직전까지 잃지 않고 내려보낼 수 있는가.**

## 4. 두 주장

| 주장 | 내용 | 근거 |
|---|---|---|
| A. 컴파일러여야 한다 | 의미는 라이브러리 아래, 컴파일러 안에서도 손실된다 → 의미를 기계어까지 들고 가며 단계마다 보존을 검사한다 | XLA 사례, 1세대의 타입 없는 IR. 0단계 목록으로 보강 |
| B. 글의 문법이어야 한다 | 조사·축 이름·배분어(마다·별로·씩·끼리)·종류 꼬리표가 의미를 말 속에 접어 넣어, 같은 검사력을 더 적은 표기로, 빠뜨림 없이 얻는다 | 종이 시험(0′), 2단계 비교 실험 |

A 는 라이브러리(jaxtyping·einops)로는 닿지 않는 곳 — 커널 안의 인덱스·정밀도 변환·컴파일러의 최적화 — 까지
의미를 지키는 일이고, B 는 그 의미를 사람이 가볍게, 그러나 빠뜨릴 수 없게 적게 하는 일이다. B 가 약하게 나와도
A 만으로 "의미를 끝까지 지키는 GPU 컴파일러"라는 결과가 남는다.

## 5. 의미의 갈래 (작업 분류)

다른 연구의 분류가 들어오면 그것으로 맞춘다.

| 갈래 | 묻는 것 | 예 |
|---|---|---|
| 자리 | 값이 어디에 있고 어디로 가는가 | 축의 이름·순서, 주소 공간, 인덱스·보폭, 크기의 대응 |
| 정체 | 무슨 값인가 | 정밀도, 저장 형식(양자화·영점), 척도, 종류(로짓·확률·양수) |
| 흐름 | 누가 읽고 누가 쓰는가 | 역할(출처·목적지·누적), 겹침 |
| 의도 | 무엇을 계산하려는가 | 공식, 경계의 방향 |

종이 시험에서 문법이 막은 실수는 앞의 셋, 못 막은 실수는 전부 **의도**였다.

## 6. 가벼움의 원칙

- **접어 넣어서 가볍게** — 조사·명사·배분어가 의미를 함께 싣고 와서, 따로 선언하지 않아도 빠지지 않는다. 목표다.
- **생략해서 가볍게** — 구어체처럼 문맥에 맡기는 것. 컴파일러가 **하나로 복원할 수 있을 때만** 허용하고, 후보가
  둘 이상이면 오류로 묻는다(D-22·D-30 의 원칙). 추론에 맡긴 의미가 틀리게 복원되는 자리가 곧 의미 손실이기 때문이다.

### 뿌리 갈래 — PTX 아래로 (2026-10-08 더함)

PTX 의 마지막 단계(PTX → SASS 기계어)는 NVIDIA 드라이버 안의 비공개 컴파일러가 한다. 그 단계까지 글이 맡으면 "의미를
기계어까지"가 말 그대로 참이 된다. CPU 쪽에서 Windows 가 글의 PE 를 올리듯, GPU 쪽에서는 드라이버가 로더만 맡는다.
SASS 의 인코딩은 공개되지 않았지만, 드라이버가 어떤 PTX 에 대해서든 정답 기계어를 돌려주므로 바이트 대조로 익히고 검증한다.

| 단계 | 내용 | 판정 | 상태 |
|---|---|---|---|
| S0 | 드라이버가 만든 cubin 을 글 호스트가 PTX 없이 실행 | 틀린 값 0 | **끝** |
| S1 | 포장(ELF·메타데이터·노트)을 글이 처음부터 쓴다, SASS 는 드라이버 것 | 실행 + 두 구현 바이트 동일 | **끝**: 글판 = 파이썬판, GPU 에서 틀린 값 0 |
| S2 | 벡터 덧셈에 필요한 명령 여남은 개를 글이 직접 인코딩 | 드라이버 SASS 와 바이트 동일 | **중단** (2026-10-08, 아래) |
| S3 | 글 IR → SASS 백엔드 (작은 부분집합 + 스케줄링 제어 규칙) | 탐침 커널들이 PTX 없이 돈다 | **중단** (2026-10-08, 아래) |

치르는 것: 한 GPU 세대(sm_89, Ada)에 묶이고, 설명서 없이 역공학하며, 틀리면 조용히 틀린다. 그래서 주 갈래(의미 층)와
나란히, 짧은 단계로 실현성을 잰다.

**S1 에서 멈춘다 (2026-10-08).** 이 갈래의 목표("의미를 기계어까지"를 말 그대로 참으로)를 S2·S3 가 이루지 못한다고 판단했다.

- **종속이 줄지 않는다.** S0·S1 이 보였듯 드라이버는 로더로 남고, PTX 를 기계어로 바꾸는 JIT 도 같은 `nvcuda.dll` 안에 있다.
  글이 SASS 를 내도 빠지는 파일이 없다.
- **지킬 기준이 사라진다.** PTX 는 의미가 공개 명세로 정해진 가장 아래 층이다(반올림 방식, 비정규수, 메모리 모델까지).
  SASS 는 명세가 없어서, 그 아래에서 "의미를 지켰다"는 말은 역공학으로 짐작한 의미에 맞췄다는 뜻밖에 안 된다.
- **조용한 오답의 원인을 새로 만든다.** 명령마다 붙는 스케줄링 정보(대기·의존 장벽)를 틀리면 하드웨어가 잡지 않는 경우가
  있다. S1 에서 `KPARAM_INFO` 를 빼자 오류 없이 값이 틀린 것과 같은 종류다 — 이 연구가 막으려는 손실이다.
- **한 세대에 묶인다.** PTX 는 다음 세대 GPU 에서도 돌지만 SASS 인코딩은 세대마다 바뀐다.

대신 **PTX 를 계약 경계로 삼는다** — 그 아래(드라이버)가 의미를 고를 여지를 PTX 에 남기지 않는다. 아래 표.

### PTX 계약 — 드라이버가 고를 여지를 남기지 않는다 (2026-10-08 더함)

의미는 PTX 에 다 적고, 드라이버는 그 명세대로만 옮기게 한다. 글의 의미는 참조 구현이 정한다(03장 머리말: 실행 가능한
형태는 `ref/`) — 짧은실수 연산은 CPU 백엔드가 연산마다 반올림한다(`mulss`·`addss`, 명세 3.3 은 폭만 적고 반올림은 적지 않았다).
판정은 **CPU 의 글과 비트까지 같음**이다. 값이 아니라 비트로 맞추므로 +0 과 -0 도 가른다.

| 항목 | 드라이버의 여지 | 판정 | 상태 |
|---|---|---|---|
| P1 곱과 덧셈의 합침 | 반올림을 적지 않은 `mul`/`add`/`sub` 는 PTX 명세상 FMA 로 합쳐도 된다 | 곱더하기 커널, 1,048,576개 중 CPU 의 글과 비트가 다른 값 0 | **끝**: 아래 |
| P2 근사·비정규수 | `.approx`·`.ftz` 를 쓰면 정확한 반올림·비정규수를 버린다 | 소스가 밝히지 않았으면 PTX 에 `.approx`·`.ftz` 가 없다 | 지금은 지킨다(글ptx.py 가 내지 않고, 나눗셈은 처음부터 `div.rn`). 제곱근·지수 같은 함수가 들어올 때 다시 잰다 |

**P1 결과.** 이 항목은 문제를 먼저 보고 세운 것이다 — 판정 기준이 결과보다 늦다. 처음 판의 `글ptx.py` 는 `mul.f32`·`add.f32`
를 반올림 없이 냈고, 드라이버가 실제로 FMA 로 합쳤다. 1단계 탐침은 벡터 덧셈이라 곱이 없어 드러나지 않았다.

| PTX | CPU 의 글(두 번 반올림)과 비트가 다른 값 | 한 번 반올림(실수로 계산, FMA 꼴)과 다른 값 |
|---|---|---|
| 반올림 없음 (`mul.f32`·`add.f32`, 고치기 전) | 245,734 / 1,048,576 | 0 |
| `.rn` (`mul.rn.f32`·`add.rn.f32`, 지금) | **0** | 245,734 |

합침이 "마지막 자리의 작은 차이"에 그치지 않는다는 것도 쟀다. 같은 값을 두 자리에 넘긴 `x·x − y·y`(제곱차 커널)는 글의
의미로는 모든 칸이 정확히 0 인데, 반올림을 빼면 1,048,576칸 중 1,048,342칸이 0 이 아니었고 그중 524,113칸이 **음수**였다 —
제곱근을 씌우면 NaN 이다. 분산을 `E[x²] − E[x]²` 로 구하는 정규화 같은 자리에서 컴파일러의 재량이 NaN 을 만드는 길이다.
`.rn` 판은 0칸.

글ptx.py 가 부동소수 덧셈·뺄셈·곱셈에 `.rn` 을 적게 고쳤다. 레지스터(16)·스택(48 B)은 그대로다. 합치면 반올림이 한 번
줄어 대개 더 정확해지지만, 소스에 적힌 것과 다른 연산이고 위처럼 식의 성질을 깨기도 한다. 그래서 금지가 아니라 **소스가 밝힐 때만** 합친다 —
예를 들어 종이 시험의 `(A × B)를 공유에 걸쳐 더한 값` 처럼 곱의 합을 말로 적은 줄이기는 FMA 누적을 그 말의 의미로
정할 수 있다. 합침을 고르는 말은 2단계에서 정한다. 행렬곱처럼 곱과 덧셈이 대부분인 커널에서 합침을 막으면 명령 수가
늘어나므로, 성능을 잴 때는 같은 의미의 손 PTX 와 견준다.

## 8. 운영 규칙

- 연구 산출물은 `research/gpu/`, 작업은 가지 `research/gpu` 에서.
- **참조 구현에서 먼저 시험**하고(D-44 선례), 이정표를 닫을 때 자체 컴파일러로 옮겨 고정점과 바이트 대조를 되찾는다.
  PTX 는 텍스트라서 두 구현이 같은 PTX 를 내는지 지금의 덤프 대조처럼 볼 수 있다.
- 호환 약속은 그대로다. GPU 쪽 새 문법은 1.x 코드를 깨지 않는 방식(새 옵션, 새 파일)으로 들어오고, 깨야 하면
  2.0 결정으로 간다.
- CI 에는 GPU 가 없다 — PTX 생성과 대조는 CI 에서, 실행은 이 PC 에서.
- 시간 상자: 0단계 2주, 2단계 6주(초안). 넘기면 그 자리에서 판정한다.
