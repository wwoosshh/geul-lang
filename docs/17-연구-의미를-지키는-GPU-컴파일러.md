# 연구: 의미를 잃지 않는 GPU 컴파일러

판: 초안 2 (2026-10-08 — 초안 1 에 뿌리 갈래의 중단, PTX 계약, 주장 C 를 더함). 결정 기록 D-48. 산출물은 [`research/gpu/`](../research/gpu/README.md).
이 문서는 연구 계획이다 — 판정 기준을 결과보다 먼저 적고, 결과가 나오면 상태 칸만 고친다.

## 1. 왜 다시 여나

D-45 는 **쓸모**(사람들이 쓸 것인가, 확실히 돈이 되는가)를 근거로 개발을 접었다. 이번 연구는 쓸모가 아니라
**언어의 능력**을 묻는 개인 연구다. 그래서 D-45 의 판단과 부딪히지 않는다. 호환 약속(11장)은 그대로다.

## 2. 출발점

- **다른 연구의 발견.** AI 연산 과정에서 의미 손실 — 시작값이 어디로 가야 하는지, 무슨 값인지 — 이 고수준뿐
  아니라 저수준에서도 일어나고, 그 훼손이 부분함수로 존재하며 흔히 아는 AI 버그(한 단어 무한 반복, 관계없는
  외국어 출력, 논점 상실, 출력 실패)로 보인다.
- **공개 사례.** Anthropic 의 [사후 분석](https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues)
  (2025-09): TPU 서버 설정 오류로 영어 답에 태국어·중국어 글자가 섞였고, XLA:TPU **컴파일러**의 잠복 버그가 토큰을
  고르는 근사 top-k 연산을 잘못 컴파일했다 — 고친 방법은 더 높은 정밀도의 정확한 top-k 였다. 저수준 연산과
  컴파일러의 의미 훼손이 "AI 버그"로 보인 사례다.
- **글 자신의 역사.** 1세대를 끝낸 원인 중 둘이 "타입 없는 IR"과 "조용한 실패"였다(01장) — IR 에서 값의 정체가
  사라지자 백엔드가 추측했고, 그것이 결함이 됐다. 컴파일러 안의 의미 손실이다.

## 3. 질문

**말하는 어법의 문법이 GPU 연산에서 값의 자리·정체·흐름이 훼손되는 것을 컴파일 시점에 막을 수 있는가.
그리고 그 의미를 기계어 직전까지 잃지 않고 내려보낼 수 있는가.**

(2026-10-08 더함) 그리고 **그 문법이 빠뜨릴 수 없게 적게 하는 사실로, 의미를 잃지 않으면서 계산을 더 빠르게 할 수
있는가** — 어순 자체가 아니라 문법이 강제하는 사실에서 이득이 나오는지 묻는다(주장 C).

## 4. 세 주장

| 주장 | 내용 | 근거 |
|---|---|---|
| A. 컴파일러여야 한다 | 의미는 라이브러리 아래, 컴파일러 안에서도 손실된다 → 의미를 기계어까지 들고 가며 단계마다 보존을 검사한다 | XLA 사례, 1세대의 타입 없는 IR. 0단계 목록으로 보강 |
| B. 글의 문법이어야 한다 | 조사·축 이름·배분어(마다·별로·씩·끼리)·종류 꼬리표가 의미를 말 속에 접어 넣어, 같은 검사력을 더 적은 표기로, 빠뜨림 없이 얻는다 | 종이 시험(0′), 2단계 비교 실험 |
| C. 문법이 준 사실이 최적화를 허가한다 (2026-10-08 더함) | 문법이 빠뜨릴 수 없게 만든 사실 — 흐르는 중간값(`-서`), 일이 나뉘는 모양(배분어), 역할과 겹침 — 이 검사의 근거이자 안전한 최적화의 근거가 된다. 다른 언어에서 이 사실은 고를 수 있는 주석·플래그이고, 틀리게 적으면 조용한 오답이다 | PTX 계약 P1(합침을 막아야 합쳐 돌려도 값이 같다). §7 의 주장 C 표 |

A 는 라이브러리(jaxtyping·einops)로는 닿지 않는 곳 — 커널 안의 인덱스·정밀도 변환·컴파일러의 최적화 — 까지
의미를 지키는 일이고, B 는 그 의미를 사람이 가볍게, 그러나 빠뜨릴 수 없게 적게 하는 일이다. B 가 약하게 나와도
A 만으로 "의미를 끝까지 지키는 GPU 컴파일러"라는 결과가 남는다.

C 는 그 사실이 검사로 끝나지 않고 속도로도 돌아오는가를 묻는다. 어순(SOV) 자체는 속도를 바꾸지 않는다 — 어느
언어로 쓰든 같은 PTX 를 거쳐 같은 드라이버 컴파일러로 간다. 이득이 난다면 문법이 빠뜨릴 수 없게 만든 사실에서다.
C 가 약하게 나와도 A·B 의 결과는 그대로 남는다.

## 6. 가벼움의 원칙

- **접어 넣어서 가볍게** — 조사·명사·배분어가 의미를 함께 싣고 와서, 따로 선언하지 않아도 빠지지 않는다. 목표다.
- **생략해서 가볍게** — 구어체처럼 문맥에 맡기는 것. 컴파일러가 **하나로 복원할 수 있을 때만** 허용하고, 후보가
  둘 이상이면 오류로 묻는다(D-22·D-30 의 원칙). 추론에 맡긴 의미가 틀리게 복원되는 자리가 곧 의미 손실이기 때문이다.

### 뿌리 갈래 — PTX 아래로 (2026-10-08 더함)

PTX 의 마지막 단계(PTX → SASS 기계어)는 NVIDIA 드라이버 안의 비공개 컴파일러가 한다. 그 단계까지 글이 맡으면 "의미를
기계어까지"가 말 그대로 참이 된다. CPU 쪽에서 Windows 가 글의 PE 를 올리듯, GPU 쪽에서는 드라이버가 로더만 맡는다.
SASS 의 인코딩은 공개되지 않았지만, 드라이버가 어떤 PTX 에 대해서든 정답 기계어를 돌려주므로 바이트 대조로 익히고 검증한다.

| 단계 | 내용 | 판정 | 상태 |
|---|---|---|---|
| S0 | 드라이버가 만든 cubin 을 글 호스트가 PTX 없이 실행 | 틀린 값 0 | **끝** |
| S1 | 포장(ELF·메타데이터·노트)을 글이 처음부터 쓴다, SASS 는 드라이버 것 | 실행 + 두 구현 바이트 동일 | **끝**: 글판 = 파이썬판, GPU 에서 틀린 값 0 |
| S2 | 벡터 덧셈에 필요한 명령 여남은 개를 글이 직접 인코딩 | 드라이버 SASS 와 바이트 동일 | **중단** (2026-10-08, 아래) |
| S3 | 글 IR → SASS 백엔드 (작은 부분집합 + 스케줄링 제어 규칙) | 탐침 커널들이 PTX 없이 돈다 | **중단** (2026-10-08, 아래) |

치르는 것: 한 GPU 세대(sm_89, Ada)에 묶이고, 설명서 없이 역공학하며, 틀리면 조용히 틀린다. 그래서 주 갈래(의미 층)와
나란히, 짧은 단계로 실현성을 잰다.

**S1 에서 멈춘다 (2026-10-08).** 이 갈래의 목표("의미를 기계어까지"를 말 그대로 참으로)를 S2·S3 가 이루지 못한다고 판단했다.

- **종속이 줄지 않는다.** S0·S1 이 보였듯 드라이버는 로더로 남고, PTX 를 기계어로 바꾸는 JIT 도 같은 `nvcuda.dll` 안에 있다.
  글이 SASS 를 내도 빠지는 파일이 없다.
- **지킬 기준이 사라진다.** PTX 는 의미가 공개 명세로 정해진 가장 아래 층이다(반올림 방식, 비정규수, 메모리 모델까지).
  SASS 는 명세가 없어서, 그 아래에서 "의미를 지켰다"는 말은 역공학으로 짐작한 의미에 맞췄다는 뜻밖에 안 된다.
- **조용한 오답의 원인을 새로 만든다.** 명령마다 붙는 스케줄링 정보(대기·의존 장벽)를 틀리면 하드웨어가 잡지 않는 경우가
  있다. S1 에서 `KPARAM_INFO` 를 빼자 오류 없이 값이 틀린 것과 같은 종류다 — 이 연구가 막으려는 손실이다.
- **한 세대에 묶인다.** PTX 는 다음 세대 GPU 에서도 돌지만 SASS 인코딩은 세대마다 바뀐다.

대신 **PTX 를 계약 경계로 삼는다** — 그 아래(드라이버)가 의미를 고를 여지를 PTX 에 남기지 않는다. 아래 표.

### PTX 계약 — 드라이버가 고를 여지를 남기지 않는다 (2026-10-08 더함)

의미는 PTX 에 다 적고, 드라이버는 그 명세대로만 옮기게 한다. 글의 의미는 참조 구현이 정한다(03장 머리말: 실행 가능한
형태는 `ref/`) — 짧은실수 연산은 CPU 백엔드가 연산마다 반올림한다(`mulss`·`addss`, 명세 3.3 은 폭만 적고 반올림은 적지 않았다).
판정은 **CPU 의 글과 비트까지 같음**이다. 값이 아니라 비트로 맞추므로 +0 과 -0 도 가른다.

| 항목 | 드라이버의 여지 | 판정 | 상태 |
|---|---|---|---|
| P1 곱과 덧셈의 합침 | 반올림을 적지 않은 `mul`/`add`/`sub` 는 PTX 명세상 FMA 로 합쳐도 된다 | 곱더하기 커널, 1,048,576개 중 CPU 의 글과 비트가 다른 값 0 | **끝**: 아래 |
| P2 근사·비정규수 | `.approx`·`.ftz` 를 쓰면 정확한 반올림·비정규수를 버린다 | 소스가 밝히지 않았으면 PTX 에 `.approx`·`.ftz` 가 없다 | 지금은 지킨다(글ptx.py 가 내지 않고, 나눗셈은 처음부터 `div.rn`). 제곱근·지수 같은 함수가 들어올 때 다시 잰다 |

**P1 결과.** 이 항목은 문제를 먼저 보고 세운 것이다 — 판정 기준이 결과보다 늦다. 처음 판의 `글ptx.py` 는 `mul.f32`·`add.f32`
를 반올림 없이 냈고, 드라이버가 실제로 FMA 로 합쳤다. 1단계 탐침은 벡터 덧셈이라 곱이 없어 드러나지 않았다.

| PTX | CPU 의 글(두 번 반올림)과 비트가 다른 값 | 한 번 반올림(실수로 계산, FMA 꼴)과 다른 값 |
|---|---|---|
| 반올림 없음 (`mul.f32`·`add.f32`, 고치기 전) | 245,734 / 1,048,576 | 0 |
| `.rn` (`mul.rn.f32`·`add.rn.f32`, 지금) | **0** | 245,734 |

합침이 "마지막 자리의 작은 차이"에 그치지 않는다는 것도 쟀다. 같은 값을 두 자리에 넘긴 `x·x − y·y`(제곱차 커널)는 글의
의미로는 모든 칸이 정확히 0 인데, 반올림을 빼면 1,048,576칸 중 1,048,342칸이 0 이 아니었고 그중 524,113칸이 **음수**였다 —
제곱근을 씌우면 NaN 이다. 분산을 `E[x²] − E[x]²` 로 구하는 정규화 같은 자리에서 컴파일러의 재량이 NaN 을 만드는 길이다.
`.rn` 판은 0칸.

글ptx.py 가 부동소수 덧셈·뺄셈·곱셈에 `.rn` 을 적게 고쳤다. 레지스터(16)·스택(48 B)은 그대로다. 합치면 반올림이 한 번
줄어 대개 더 정확해지지만, 소스에 적힌 것과 다른 연산이고 위처럼 식의 성질을 깨기도 한다. 그래서 금지가 아니라 **소스가 밝힐 때만** 합친다 —
예를 들어 종이 시험의 `(A × B)를 공유에 걸쳐 더한 값` 처럼 곱의 합을 말로 적은 줄이기는 FMA 누적을 그 말의 의미로
정할 수 있다. 합침을 고르는 말은 2단계에서 정한다. 행렬곱처럼 곱과 덧셈이 대부분인 커널에서 합침을 막으면 명령 수가
늘어나므로, 성능을 잴 때는 같은 의미의 손 PTX 와 견준다.

### 주장 C — 문법이 준 사실이 최적화를 허가하는가 (2026-10-08 더함)

판정 기준을 실험보다 먼저 적는다.

- **정확성 쪽이 먼저다**(§7 첫머리). C1 의 정확성 쪽은 2단계의 문법 작업과 함께 한다. 속도 쪽과 C2·C3 은 축·줄이기·주소
  공간이 IR 에 들어온 2단계 뒤에 잰다. 지금 탐침 커널은 스칼라라서 사슬로 쓰든 식으로 쓰든 중간값이 어차피 레지스터 안이다 —
  차이가 날 자리가 아직 없다.
- **속도는 같은 의미의 판끼리만 견준다**(손 PTX 도 `.rn`, 같은 반올림). 전문가가 다듬은 라이브러리(cuBLAS·FlashAttention)를
  이기는 것은 목표가 아니다 — 9장의 "초기의 성능 경쟁"을 하지 않는다는 원칙은 그대로다.
- 실행 시간은 이 PC(RTX 4070 Ti)에서 10회 실행의 중앙값이고, 첫 실행(드라이버 JIT)은 뺀다.

| 항목 | 문법 장치 → 컴파일러가 얻는 사실 | 판정: 정확성 | 판정: 속도 (2단계 뒤) | 상태 |
|---|---|---|---|---|

**C1 의 규칙 (제안 — 구현할 때 명세 항목과 결정 기록으로 올린다).** `1에 2를 더해서 3을 곱하다` 는 (1+2)×3 이다 — 계산
순서가 문장 순서라 우선순위 규칙도 괄호도 필요 없다.

- `-서` 로 이은 절에서 앞 절의 값은 다음 절의 **비어 있는 역할 하나**로 들어간다. 빈 역할이 둘 이상이면 오류다(§6
  "하나로 복원할 수 있을 때만"). 빈 역할이 없으면 지금처럼 별개의 문장이다 — 이미 받는 코드라 1.x 약속상 바꿀 수 없다.
  그때는 앞 절의 값이 조용히 버려지므로, GPU 커널(새 자리)에서 오류로 할지는 2단계에서 정한다.
- `-고` 는 지금처럼 값이 흐르지 않는 차례다. 한국어의 `-고`(나열)와 `-아서/-어서`(앞 동작의 결과를 이어받음: "사과를
  깎아서 먹다")의 차이를 그대로 쓴다.
- 절 하나는 연산 하나이고, 그 타입으로 반올림한다. 그래서 `곱해서 더하다` 는 반올림 두 번이다. 반올림 한 번(FMA)은 한
  동작이므로 따로 한 낱말로 둔다(표준 라이브러리의 `큰수_곱하고더하기` 처럼 두 동작을 한 낱말로 부르는 선례가 있다).
- 가지가 둘인 식((a+b)×(c+d))은 사슬 하나로 쓸 수 없다. 가지는 관형절로 쓴다: `a에 b를 더해서 c에 d를 더한 값을
  곱하다`. 종이 시험 v0 가 이미 `~에 걸쳐 더한 값`·`~로 푼 값` 꼴을 쓴다. 줄기는 `-서`, 가지는 `-한 값` 이면 우선순위
  없이 식의 나무를 다 쓴다.
- 산술 동사(`더하다`·`빼다`·`곱하다`·`나누다`)가 역할을 가진 함수로 있어야 한다 — `[a에 b를 더하기]`,
  `[a에서 b를 빼기]`, `[a에 b를 곱하기]`, `[a를 b로 나누기]`. 지금 표준에는 없다.
- 지금의 컴파일러(2026-10-08 확인, `더하기`·`곱하기` 를 위 꼴로 직접 정의한 시험 프로그램): `1에 2를 더해서 3을 곱하다.` 는
  활용형 `더해서` 를 못 읽고("동사 '더해다'에 해당하는 함수가 없습니다", 07장 2.5), `1에 2를 더하서 3을 곱하다.` 는
  "'곱하기' 호출에 'a'(에) 인자가 없습니다" 오류다.
  둘 다 지금 오류라 뜻을 주는 것은 받아들이는 변화다(1.x 약속 안). 같은 계산은 지금 괄호로만 쓸 수 있다:
  `((1에 2를 더하다)에 3을 곱하다)` → 9. 활용은 `하다 → 해서` 같은 규칙 활용부터 받고, 불규칙(`나눠서`·`도와서`)은
  규칙표로 받으며, 후보가 둘이면 오류다(D-22).
- **꼴은 새것이 아니다.** 일본어 なでしこ 공식판은 `2に3を足して4を掛けて表示。` 를 20 으로 계산한다
  ([처리계 비교 표](https://github.com/soramikan/lnako/issues/105)). C1 이 주장하는 것은 꼴이 아니라 컴파일러에 대한
  약속이다 — 순서·반올림의 고정, 합쳐 돌려도 값이 같은 융합, 조사로 정하는 자리. 지금의 융합 컴파일러는 합치면서 곱과
  덧셈을 FMA 로 묶거나 중간값을 더 높은 정밀도로 들고 있어, 합친 판과 나눈 판의 값이 달라지기도 한다. 그중 FMA 쪽은 P1 이
  이미 막았다 — 합쳐 돌려도 값이 같으려면 먼저 있어야 하는 조건이다.

### 3단계 시작 — GPT-2 small 을 글 커널로 (2026-10-08 더함)

사용자 판단: 실제 AI 모델을 글 컴파일러로 돌려, 이전(PyTorch)과 무엇이 다르고 얼마나 좋은지를 보이는 것이 더 중요하다. 다른 컴파일러보다
빠르면 좋다. 대상은 GPT-2 small(openai-community/gpt2, 124M, fp32). 판정을 실험보다 먼저 적는다.

- **범위** — 모든 GPU 계산은 글로 쓴 커널(글ptx.py → PTX → 드라이버)이 한다. 호스트(가중치 읽기, 커널을 부르는 순서, 토크나이저)는
  파이썬 ctypes 이고 PyTorch 를 쓰지 않는다. 비교 대상은 같은 PC 의 PyTorch eager fp32 로 쓴 같은 GPT-2.
- **밝힌 근사** — 지수 함수는 근사 명령(`ex2.approx`)을 쓰는 내장 `근사지수` 로, 소스가 밝혀서 쓴다(PTX 계약 P2). 제곱근·나눗셈은 정확한 반올림.
- **설계의 의미** — 한 토큰(행)의 계산은 함께 계산하는 행의 수와 상관없게 한다(`행마다`): 행렬곱은 행마다 같은 순서로 더하고, 어텐션은
  질의마다 같은 계산을 한다. 그래서 프롬프트를 한 번에 처리하든(prefill) 하나씩 처리하든(decode) 같은 위치의 결과가 같아야 한다.

### 3단계 성능 — 바닥까지 (2026-10-08 더함)

사용자 결정: 바닥 수치까지 최적화하고 긴 프롬프트도 개선한다. 글 컴파일러가 PyTorch 보다 일반적인 성능 우위를 갖는 것을 목표로 둔다.
§9 의 "초기의 성능 경쟁"을 이 단계에서 푼다. 정확성이 먼저라는 원칙은 그대로다 — 모든 최적화는 3b 의 행 불변과 PTX 계약(밝힌
근사만)을 지키고, 판정은 실험보다 먼저 적는다.

**바닥 (재서 정함 — 결과가 아니라 이 기계의 성질).** RTX 4070 Ti 에서 큰 배열 읽기 470 GB/s(글 커널) · 475 GB/s(PyTorch `sum`) →

약속을 지킨다). 커널을 합쳐 토큰당 실행 수를 줄인다(KV 저장을 c_attn 의 끝손질로, 층정규화를 생성 쪽 선형의 머리로). 어텐션은 질의

### 3단계 성능 2 — 길이를 가리지 않고 (2026-10-09 더함)

사용자 질문: 512토큰만 이기면 되는가 — 실사용의 문맥은 수천~수만 토큰까지 늘어난다. 맞다. 문맥이 길어지면 병목이 바뀐다:
프롬프트 처리에서는 어텐션(길이의 제곱)이 행렬곱을 넘어서고, 생성에서는 걸음마다 읽는 KV 캐시가 가중치보다 커진다. 그래서 "일반적인
우위"는 길이 전체에서 판정한다. GPT-2 small 은 문맥 1024 까지라, 실제 모델로는 1024 까지 재고, 그 위는 **같은 모양의 합성 모델**(위치표만
16384 줄, 값은 무작위 — 연산·크기·순서는 GPT-2 그대로)로 속도와 비트만 본다. 정확도는 실제 모델에서만 판정한다. 긴 문맥을 실제로 쓰는
모델(내려받기 필요)은 나중 일로 둔다. 3f 의 상태(기준 미달)는 그대로 두고, 아래는 따로 판정한다.

**비교 대상 (재서 정함 — 결과가 아니라 비교 대상의 성질).** PyTorch 2.14.1 fp32, eager / CUDA 그래프, 7번 중앙값(생성은 32걸음).

점수 표를 두지 않으며(지금 판은 길이의 제곱만큼 점수를 둔다), 생성은 조각을 여러 블록이 나눠 맡는다. 약속이 바뀌면 3b·3g 의 비트와
정확도를 새 약속으로 다시 잰다. (2) 프롬프트 처리의 행렬곱에서 파도의 꼬리와 가닥 합치기의 값을 줄인다. (3) 호스트가 긴 문맥을 받게 한다.

## 8. 운영 규칙

- 연구 산출물은 `research/gpu/`, 작업은 가지 `research/gpu` 에서.
- **참조 구현에서 먼저 시험**하고(D-44 선례), 이정표를 닫을 때 자체 컴파일러로 옮겨 고정점과 바이트 대조를 되찾는다.
  PTX 는 텍스트라서 두 구현이 같은 PTX 를 내는지 지금의 덤프 대조처럼 볼 수 있다.
- 호환 약속은 그대로다. GPU 쪽 새 문법은 1.x 코드를 깨지 않는 방식(새 옵션, 새 파일)으로 들어오고, 깨야 하면
  2.0 결정으로 간다.
- CI 에는 GPU 가 없다 — PTX 생성과 대조는 CI 에서, 실행은 이 PC 에서.
- 시간 상자: 0단계 2주, 2단계 6주(초안). 넘기면 그 자리에서 판정한다.

## 9. 하지 않는 것

범용 GPU 언어, 초기의 성능 경쟁, NVIDIA 밖의 장치(나중에 SPIR-V), 자동 미분과 학습.

## 10. 위험

- 가상 문법 v0 의 모호성 — `별로` 와 `마다` 의 경계, 줄이기 동사 목록. 특히 종류 추론(양수 / 축 합 → 확률)은 주장이 크다.
- 1인과 AI 의 규모, 그리고 두 구현을 함께 키우는 비용.
- 종이 시험의 편향 — 0단계가 그것을 이긴다.
- 주장 C 는 성능 주장이라 비교가 기울기 쉽다 — 같은 의미의 판끼리만 견주고, 기준(시간·배수)은 실험 전에 적은 §7 의 표를 따른다.
- `-서` 사슬이 길면 오히려 읽기 어렵고, 이름 없는 중간값은 들여다볼 수 없다(디버깅). 활용(특히 불규칙)을 받는 비용이 든다.
