# 연구: 의미를 잃지 않는 GPU 컴파일러

판: 초안 2 (2026-10-08 — 초안 1 에 뿌리 갈래의 중단, PTX 계약, 주장 C 를 더함). 결정 기록 D-48. 산출물은 [`research/gpu/`](../research/gpu/README.md).
이 문서는 연구 계획이다 — 판정 기준을 결과보다 먼저 적고, 결과가 나오면 상태 칸만 고친다.

## 1. 왜 다시 여나

D-45 는 **쓸모**(사람들이 쓸 것인가, 확실히 돈이 되는가)를 근거로 개발을 접었다. 이번 연구는 쓸모가 아니라
**언어의 능력**을 묻는 개인 연구다. 그래서 D-45 의 판단과 부딪히지 않는다. 호환 약속(11장)은 그대로다.

## 2. 출발점

- **다른 연구의 발견.** AI 연산 과정에서 의미 손실 — 시작값이 어디로 가야 하는지, 무슨 값인지 — 이 고수준뿐
  아니라 저수준에서도 일어나고, 그 훼손이 부분함수로 존재하며 흔히 아는 AI 버그(한 단어 무한 반복, 관계없는
  외국어 출력, 논점 상실, 출력 실패)로 보인다.
- **공개 사례.** Anthropic 의 [사후 분석](https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues)
  (2025-09): TPU 서버 설정 오류로 영어 답에 태국어·중국어 글자가 섞였고, XLA:TPU **컴파일러**의 잠복 버그가 토큰을
  고르는 근사 top-k 연산을 잘못 컴파일했다 — 고친 방법은 더 높은 정밀도의 정확한 top-k 였다. 저수준 연산과
  컴파일러의 의미 훼손이 "AI 버그"로 보인 사례다.
- **글 자신의 역사.** 1세대를 끝낸 원인 중 둘이 "타입 없는 IR"과 "조용한 실패"였다(01장) — IR 에서 값의 정체가
  사라지자 백엔드가 추측했고, 그것이 결함이 됐다. 컴파일러 안의 의미 손실이다.

## 3. 질문

**말하는 어법의 문법이 GPU 연산에서 값의 자리·정체·흐름이 훼손되는 것을 컴파일 시점에 막을 수 있는가.
그리고 그 의미를 기계어 직전까지 잃지 않고 내려보낼 수 있는가.**

(2026-10-08 더함) 그리고 **그 문법이 빠뜨릴 수 없게 적게 하는 사실로, 의미를 잃지 않으면서 계산을 더 빠르게 할 수
있는가** — 어순 자체가 아니라 문법이 강제하는 사실에서 이득이 나오는지 묻는다(주장 C).

## 4. 세 주장

| 주장 | 내용 | 근거 |
|---|---|---|
| A. 컴파일러여야 한다 | 의미는 라이브러리 아래, 컴파일러 안에서도 손실된다 → 의미를 기계어까지 들고 가며 단계마다 보존을 검사한다 | XLA 사례, 1세대의 타입 없는 IR. 0단계 목록으로 보강 |
| B. 글의 문법이어야 한다 | 조사·축 이름·배분어(마다·별로·씩·끼리)·종류 꼬리표가 의미를 말 속에 접어 넣어, 같은 검사력을 더 적은 표기로, 빠뜨림 없이 얻는다 | 종이 시험(0′), 2단계 비교 실험 |
| C. 문법이 준 사실이 최적화를 허가한다 (2026-10-08 더함) | 문법이 빠뜨릴 수 없게 만든 사실 — 흐르는 중간값(`-서`), 일이 나뉘는 모양(배분어), 역할과 겹침 — 이 검사의 근거이자 안전한 최적화의 근거가 된다. 다른 언어에서 이 사실은 고를 수 있는 주석·플래그이고, 틀리게 적으면 조용한 오답이다 | PTX 계약 P1(합침을 막아야 합쳐 돌려도 값이 같다). §7 의 주장 C 표 |

A 는 라이브러리(jaxtyping·einops)로는 닿지 않는 곳 — 커널 안의 인덱스·정밀도 변환·컴파일러의 최적화 — 까지
의미를 지키는 일이고, B 는 그 의미를 사람이 가볍게, 그러나 빠뜨릴 수 없게 적게 하는 일이다. B 가 약하게 나와도
A 만으로 "의미를 끝까지 지키는 GPU 컴파일러"라는 결과가 남는다.

C 는 그 사실이 검사로 끝나지 않고 속도로도 돌아오는가를 묻는다. 어순(SOV) 자체는 속도를 바꾸지 않는다 — 어느
언어로 쓰든 같은 PTX 를 거쳐 같은 드라이버 컴파일러로 간다. 이득이 난다면 문법이 빠뜨릴 수 없게 만든 사실에서다.
C 가 약하게 나와도 A·B 의 결과는 그대로 남는다.

- **접어 넣어서 가볍게** — 조사·명사·배분어가 의미를 함께 싣고 와서, 따로 선언하지 않아도 빠지지 않는다. 목표다.

### 뿌리 갈래 — PTX 아래로 (2026-10-08 더함)

PTX 의 마지막 단계(PTX → SASS 기계어)는 NVIDIA 드라이버 안의 비공개 컴파일러가 한다. 그 단계까지 글이 맡으면 "의미를
기계어까지"가 말 그대로 참이 된다. CPU 쪽에서 Windows 가 글의 PE 를 올리듯, GPU 쪽에서는 드라이버가 로더만 맡는다.
SASS 의 인코딩은 공개되지 않았지만, 드라이버가 어떤 PTX 에 대해서든 정답 기계어를 돌려주므로 바이트 대조로 익히고 검증한다.

| 단계 | 내용 | 판정 | 상태 |
|---|---|---|---|
| S0 | 드라이버가 만든 cubin 을 글 호스트가 PTX 없이 실행 | 틀린 값 0 | **끝** |
| S1 | 포장(ELF·메타데이터·노트)을 글이 처음부터 쓴다, SASS 는 드라이버 것 | 실행 + 두 구현 바이트 동일 | **끝**: 글판 = 파이썬판, GPU 에서 틀린 값 0 |
| S2 | 벡터 덧셈에 필요한 명령 여남은 개를 글이 직접 인코딩 | 드라이버 SASS 와 바이트 동일 | **중단** (2026-10-08, 아래) |
| S3 | 글 IR → SASS 백엔드 (작은 부분집합 + 스케줄링 제어 규칙) | 탐침 커널들이 PTX 없이 돈다 | **중단** (2026-10-08, 아래) |

치르는 것: 한 GPU 세대(sm_89, Ada)에 묶이고, 설명서 없이 역공학하며, 틀리면 조용히 틀린다. 그래서 주 갈래(의미 층)와
나란히, 짧은 단계로 실현성을 잰다.

**S1 에서 멈춘다 (2026-10-08).** 이 갈래의 목표("의미를 기계어까지"를 말 그대로 참으로)를 S2·S3 가 이루지 못한다고 판단했다.

- **종속이 줄지 않는다.** S0·S1 이 보였듯 드라이버는 로더로 남고, PTX 를 기계어로 바꾸는 JIT 도 같은 `nvcuda.dll` 안에 있다.
  글이 SASS 를 내도 빠지는 파일이 없다.
- **지킬 기준이 사라진다.** PTX 는 의미가 공개 명세로 정해진 가장 아래 층이다(반올림 방식, 비정규수, 메모리 모델까지).
  SASS 는 명세가 없어서, 그 아래에서 "의미를 지켰다"는 말은 역공학으로 짐작한 의미에 맞췄다는 뜻밖에 안 된다.
- **조용한 오답의 원인을 새로 만든다.** 명령마다 붙는 스케줄링 정보(대기·의존 장벽)를 틀리면 하드웨어가 잡지 않는 경우가
  있다. S1 에서 `KPARAM_INFO` 를 빼자 오류 없이 값이 틀린 것과 같은 종류다 — 이 연구가 막으려는 손실이다.
- **한 세대에 묶인다.** PTX 는 다음 세대 GPU 에서도 돌지만 SASS 인코딩은 세대마다 바뀐다.

대신 **PTX 를 계약 경계로 삼는다** — 그 아래(드라이버)가 의미를 고를 여지를 PTX 에 남기지 않는다. 아래 표.

### PTX 계약 — 드라이버가 고를 여지를 남기지 않는다 (2026-10-08 더함)

의미는 PTX 에 다 적고, 드라이버는 그 명세대로만 옮기게 한다. 글의 의미는 참조 구현이 정한다(03장 머리말: 실행 가능한
형태는 `ref/`) — 짧은실수 연산은 CPU 백엔드가 연산마다 반올림한다(`mulss`·`addss`, 명세 3.3 은 폭만 적고 반올림은 적지 않았다).
판정은 **CPU 의 글과 비트까지 같음**이다. 값이 아니라 비트로 맞추므로 +0 과 -0 도 가른다.

| 항목 | 드라이버의 여지 | 판정 | 상태 |
|---|---|---|---|
| P1 곱과 덧셈의 합침 | 반올림을 적지 않은 `mul`/`add`/`sub` 는 PTX 명세상 FMA 로 합쳐도 된다 | 곱더하기 커널, 1,048,576개 중 CPU 의 글과 비트가 다른 값 0 | **끝**: 아래 |
| P2 근사·비정규수 | `.approx`·`.ftz` 를 쓰면 정확한 반올림·비정규수를 버린다 | 소스가 밝히지 않았으면 PTX 에 `.approx`·`.ftz` 가 없다 | 지금은 지킨다(글ptx.py 가 내지 않고, 나눗셈은 처음부터 `div.rn`). 제곱근·지수 같은 함수가 들어올 때 다시 잰다 |

**P1 결과.** 이 항목은 문제를 먼저 보고 세운 것이다 — 판정 기준이 결과보다 늦다. 처음 판의 `글ptx.py` 는 `mul.f32`·`add.f32`
를 반올림 없이 냈고, 드라이버가 실제로 FMA 로 합쳤다. 1단계 탐침은 벡터 덧셈이라 곱이 없어 드러나지 않았다.

| PTX | CPU 의 글(두 번 반올림)과 비트가 다른 값 | 한 번 반올림(실수로 계산, FMA 꼴)과 다른 값 |
|---|---|---|
| 반올림 없음 (`mul.f32`·`add.f32`, 고치기 전) | 245,734 / 1,048,576 | 0 |
| `.rn` (`mul.rn.f32`·`add.rn.f32`, 지금) | **0** | 245,734 |

합침이 "마지막 자리의 작은 차이"에 그치지 않는다는 것도 쟀다. 같은 값을 두 자리에 넘긴 `x·x − y·y`(제곱차 커널)는 글의
의미로는 모든 칸이 정확히 0 인데, 반올림을 빼면 1,048,576칸 중 1,048,342칸이 0 이 아니었고 그중 524,113칸이 **음수**였다 —
제곱근을 씌우면 NaN 이다. 분산을 `E[x²] − E[x]²` 로 구하는 정규화 같은 자리에서 컴파일러의 재량이 NaN 을 만드는 길이다.
`.rn` 판은 0칸.

글ptx.py 가 부동소수 덧셈·뺄셈·곱셈에 `.rn` 을 적게 고쳤다. 레지스터(16)·스택(48 B)은 그대로다. 합치면 반올림이 한 번
줄어 대개 더 정확해지지만, 소스에 적힌 것과 다른 연산이고 위처럼 식의 성질을 깨기도 한다. 그래서 금지가 아니라 **소스가 밝힐 때만** 합친다 —
예를 들어 종이 시험의 `(A × B)를 공유에 걸쳐 더한 값` 처럼 곱의 합을 말로 적은 줄이기는 FMA 누적을 그 말의 의미로
정할 수 있다. 합침을 고르는 말은 2단계에서 정한다. 행렬곱처럼 곱과 덧셈이 대부분인 커널에서 합침을 막으면 명령 수가
늘어나므로, 성능을 잴 때는 같은 의미의 손 PTX 와 견준다.

### 주장 C — 문법이 준 사실이 최적화를 허가하는가 (2026-10-08 더함)

판정 기준을 실험보다 먼저 적는다.

- **정확성 쪽이 먼저다**(§7 첫머리). C1 의 정확성 쪽은 2단계의 문법 작업과 함께 한다. 속도 쪽과 C2·C3 은 축·줄이기·주소
  공간이 IR 에 들어온 2단계 뒤에 잰다. 지금 탐침 커널은 스칼라라서 사슬로 쓰든 식으로 쓰든 중간값이 어차피 레지스터 안이다 —
  차이가 날 자리가 아직 없다.
- **속도는 같은 의미의 판끼리만 견준다**(손 PTX 도 `.rn`, 같은 반올림). 전문가가 다듬은 라이브러리(cuBLAS·FlashAttention)를
  이기는 것은 목표가 아니다 — 9장의 "초기의 성능 경쟁"을 하지 않는다는 원칙은 그대로다.
- 실행 시간은 이 PC(RTX 4070 Ti)에서 10회 실행의 중앙값이고, 첫 실행(드라이버 JIT)은 뺀다.

| 항목 | 문법 장치 → 컴파일러가 얻는 사실 | 판정: 정확성 | 판정: 속도 (2단계 뒤) | 상태 |
|---|---|---|---|---|

**C1 의 규칙 (제안 — 구현할 때 명세 항목과 결정 기록으로 올린다).** `1에 2를 더해서 3을 곱하다` 는 (1+2)×3 이다 — 계산
순서가 문장 순서라 우선순위 규칙도 괄호도 필요 없다.

- `-서` 로 이은 절에서 앞 절의 값은 다음 절의 **비어 있는 역할 하나**로 들어간다. 빈 역할이 둘 이상이면 오류다(§6
  "하나로 복원할 수 있을 때만"). 빈 역할이 없으면 지금처럼 별개의 문장이다 — 이미 받는 코드라 1.x 약속상 바꿀 수 없다.
  그때는 앞 절의 값이 조용히 버려지므로, GPU 커널(새 자리)에서 오류로 할지는 2단계에서 정한다.
- `-고` 는 지금처럼 값이 흐르지 않는 차례다. 한국어의 `-고`(나열)와 `-아서/-어서`(앞 동작의 결과를 이어받음: "사과를
  깎아서 먹다")의 차이를 그대로 쓴다.
- 절 하나는 연산 하나이고, 그 타입으로 반올림한다. 그래서 `곱해서 더하다` 는 반올림 두 번이다. 반올림 한 번(FMA)은 한
  동작이므로 따로 한 낱말로 둔다(표준 라이브러리의 `큰수_곱하고더하기` 처럼 두 동작을 한 낱말로 부르는 선례가 있다).
- 가지가 둘인 식((a+b)×(c+d))은 사슬 하나로 쓸 수 없다. 가지는 관형절로 쓴다: `a에 b를 더해서 c에 d를 더한 값을
  곱하다`. 종이 시험 v0 가 이미 `~에 걸쳐 더한 값`·`~로 푼 값` 꼴을 쓴다. 줄기는 `-서`, 가지는 `-한 값` 이면 우선순위
  없이 식의 나무를 다 쓴다.
- 산술 동사(`더하다`·`빼다`·`곱하다`·`나누다`)가 역할을 가진 함수로 있어야 한다 — `[a에 b를 더하기]`,
  `[a에서 b를 빼기]`, `[a에 b를 곱하기]`, `[a를 b로 나누기]`. 지금 표준에는 없다.
- 지금의 컴파일러(2026-10-08 확인, `더하기`·`곱하기` 를 위 꼴로 직접 정의한 시험 프로그램): `1에 2를 더해서 3을 곱하다.` 는
  활용형 `더해서` 를 못 읽고("동사 '더해다'에 해당하는 함수가 없습니다", 07장 2.5), `1에 2를 더하서 3을 곱하다.` 는
  "'곱하기' 호출에 'a'(에) 인자가 없습니다" 오류다.
  둘 다 지금 오류라 뜻을 주는 것은 받아들이는 변화다(1.x 약속 안). 같은 계산은 지금 괄호로만 쓸 수 있다:
  `((1에 2를 더하다)에 3을 곱하다)` → 9. 활용은 `하다 → 해서` 같은 규칙 활용부터 받고, 불규칙(`나눠서`·`도와서`)은
  규칙표로 받으며, 후보가 둘이면 오류다(D-22).
- **꼴은 새것이 아니다.** 일본어 なでしこ 공식판은 `2に3を足して4を掛けて表示。` 를 20 으로 계산한다
  ([처리계 비교 표](https://github.com/soramikan/lnako/issues/105)). C1 이 주장하는 것은 꼴이 아니라 컴파일러에 대한
  약속이다 — 순서·반올림의 고정, 합쳐 돌려도 값이 같은 융합, 조사로 정하는 자리. 지금의 융합 컴파일러는 합치면서 곱과
  덧셈을 FMA 로 묶거나 중간값을 더 높은 정밀도로 들고 있어, 합친 판과 나눈 판의 값이 달라지기도 한다. 그중 FMA 쪽은 P1 이
  이미 막았다 — 합쳐 돌려도 값이 같으려면 먼저 있어야 하는 조건이다.

### 3단계 시작 — GPT-2 small 을 글 커널로 (2026-10-08 더함)

사용자 판단: 실제 AI 모델을 글 컴파일러로 돌려, 이전(PyTorch)과 무엇이 다르고 얼마나 좋은지를 보이는 것이 더 중요하다. 다른 컴파일러보다
빠르면 좋다. 대상은 GPT-2 small(openai-community/gpt2, 124M, fp32). 판정을 실험보다 먼저 적는다.

- **범위** — 모든 GPU 계산은 글로 쓴 커널(글ptx.py → PTX → 드라이버)이 한다. 호스트(가중치 읽기, 커널을 부르는 순서, 토크나이저)는
  파이썬 ctypes 이고 PyTorch 를 쓰지 않는다. 비교 대상은 같은 PC 의 PyTorch eager fp32 로 쓴 같은 GPT-2.
- **밝힌 근사** — 지수 함수는 근사 명령(`ex2.approx`)을 쓰는 내장 `근사지수` 로, 소스가 밝혀서 쓴다(PTX 계약 P2). 제곱근·나눗셈은 정확한 반올림.
- **설계의 의미** — 한 토큰(행)의 계산은 함께 계산하는 행의 수와 상관없게 한다(`행마다`): 행렬곱은 행마다 같은 순서로 더하고, 어텐션은
  질의마다 같은 계산을 한다. 그래서 프롬프트를 한 번에 처리하든(prefill) 하나씩 처리하든(decode) 같은 위치의 결과가 같아야 한다.

### 3단계 성능 — 바닥까지 (2026-10-08 더함)

사용자 결정: 바닥 수치까지 최적화하고 긴 프롬프트도 개선한다. 글 컴파일러가 PyTorch 보다 일반적인 성능 우위를 갖는 것을 목표로 둔다.
§9 의 "초기의 성능 경쟁"을 이 단계에서 푼다. 정확성이 먼저라는 원칙은 그대로다 — 모든 최적화는 3b 의 행 불변과 PTX 계약(밝힌
근사만)을 지키고, 판정은 실험보다 먼저 적는다.

**바닥 (재서 정함 — 결과가 아니라 이 기계의 성질).** RTX 4070 Ti 에서 큰 배열 읽기 470 GB/s(글 커널) · 475 GB/s(PyTorch `sum`) →

### 3단계 성능 2 — 길이를 가리지 않고 (2026-10-09 더함)

사용자 질문: 512토큰만 이기면 되는가 — 실사용의 문맥은 수천~수만 토큰까지 늘어난다. 맞다. 문맥이 길어지면 병목이 바뀐다:
프롬프트 처리에서는 어텐션(길이의 제곱)이 행렬곱을 넘어서고, 생성에서는 걸음마다 읽는 KV 캐시가 가중치보다 커진다. 그래서 "일반적인
우위"는 길이 전체에서 판정한다. GPT-2 small 은 문맥 1024 까지라, 실제 모델로는 1024 까지 재고, 그 위는 **같은 모양의 합성 모델**(위치표만
16384 줄, 값은 무작위 — 연산·크기·순서는 GPT-2 그대로)로 속도와 비트만 본다. 정확도는 실제 모델에서만 판정한다. 긴 문맥을 실제로 쓰는
모델(내려받기 필요)은 나중 일로 둔다. 3f 의 상태(기준 미달)는 그대로 두고, 아래는 따로 판정한다.

**비교 대상 (재서 정함 — 결과가 아니라 비교 대상의 성질).** PyTorch 2.14.1 fp32, eager / CUDA 그래프, 7번 중앙값(생성은 32걸음).

정확도를 새 약속으로 다시 잰다. (2) 프롬프트 처리의 행렬곱에서 파도의 꼬리와 가닥 합치기의 값을 줄인다. (3) 호스트가 긴 문맥을 받게 한다.

### 3단계 성능 3 — 프롬프트 처리도 메가커널로 (2026-10-09 더함)

그대로라 따로 도는 커널들과 비트까지 같아야 한다.

| 판정 | 기준 (미리 정함) | 상태 |
|---|---|---|
| 3l 프롬프트 메가커널 | 실제 GPT-2 128·256·512·1024토큰 프롬프트 처리 + 첫 토큰 시간이 지금의 따로 도는 커널들(3h 의 판)보다 짧고, 128·256·512 에서 PyTorch CUDA 그래프 판보다도 짧다. 로짓은 따로 도는 커널들과 비트까지 같다(3k 의 길들에 메가커널 프롬프트를 더해) | **기준 미달 (속도)**: 비트는 지켰다 — 네 길이 모두 마지막 행 로짓 다른 칸 0, 메가 프롬프트 + 생성 메가커널의 64토큰과 걸음마다 로짓도 하나씩 계산한 것과 같다(세 프롬프트). 속도는 따로 도는 커널보다 느리다: 128 / 256 / 512 / 1024토큰 3.11 / 4.96 / 7.17 / 14.23 ms (따로 2.73 / 3.96 / 6.15 / 11.67, CUDA 그래프 2.56 / 3.69 / 6.03 / 12.64). 일마다 GPU 시각을 남겨 보니 단계를 겹쳐도 하는 일의 총량은 같고(512 에서 블록이 일한 몫 79% — 따로 도는 커널과 비슷), 짧은 프롬프트에서는 mlp c_proj 타일(64 × 64, 깊이 3072 — 155 µs)과 64 행씩의 층정규화가 의존 사슬의 긴 막대였다. 32 × 32 타일과 8 행씩의 층정규화를 넣자 커널이 PTX 명령 약 5만 개로 커지면서 모든 일이 약 두 배로 느려졌다(지역 메모리로 밀린 레지스터 168 → 272 바이트). 메가커널은 따로 둔 모듈(커널프롬.gl, `글GPT2(프롬메가=True)`)로 남기고 기본은 따로 도는 커널이다 |

### 4단계 2 — 밝힌 정밀도: 반실수 KV 캐시 (2026-10-09 더함)

사용자 결정: 4단계에서 llama.cpp 가 앞선 칸은 소스가 밝히지 않은 정밀도 재량(TF32 행렬곱, F16 어텐션, F16 KV 캐시)에서 왔다.
같은 이득을 **소스가 밝힌 정밀도**로 얻는다 — KV 캐시를 반실수로 둔다. `반실수` 의 형식도 정했다: 종이시험의 가상 문법 v0 규칙 2 는
반실수를 bf16 으로 적었지만(명세가 아니다), KV 캐시에서 bf16 은 오차가 f16 의 약 10배로 llama.cpp 기본보다도 부정확하다(아래 흉내) —
**사용자 결정: `반실수` = IEEE 754 binary16 (f16)**. v0 규칙 2 를 고친다(bf16 은 필요할 때 다른 이름으로).

**언어 (연구 옵션 — 1.x 의 렉서 · 파서 · 타입 표에는 없다, 글ptx.py 가 켤 때만).** `반실수` 는 저장 형식이다.
- 좁히기(짧은실수 · 실수 → 반실수)는 `으로 반실수` 로만 한다 — 암시 좁히기는 컴파일 오류(v0 규칙 9). 반올림은 IEEE 754 의 가까운 쪽
  (같으면 짝수), 비정규수를 버리지 않는다(PTX 계약 P2). 유한한 값이 넘쳐 무한이 되면 오류 칸에 4 (2c 를 넓힘).
- 넓히기(반실수 → 짧은실수 · 실수)는 암시이고 정확하다.
- 반실수가 든 산술 · 비교는 짧은실수로 올려 계산한다(반실수 산술은 아직 없다 — 들어올 때 밝히는 방법과 함께 정한다).

GPT-2 에서는 c_attn 의 끝손질이 키 · 값을 `으로 반실수` 로 캐시에 쓰고, 어텐션은 읽어서 넓혀 계산한다. 순서 약속은 그대로다 — 반올림은
쓸 때 한 번이고 모든 길이 같은 칸을 읽으므로 비트가 같아야 한다. 짧은실수 KV 판은 그대로 남는다(`글GPT2(KV형식=...)`).

**판정 전에 잰 것.** KV 를 반올림하는 비용을 fp64 로 흉내 냈다(세 문장, fp64 의 탐욕 64토큰, 반올림 없는 fp64 대비 상대차 중앙값):
f16 2.4~6.8 × 10⁻⁵, bf16 2.9~6.7 × 10⁻⁴ — 고른 토큰은 둘 다 바뀌지 않았다. GPT-2 의 K · V 최댓값은 22.8 · 13.5(f16 의 범위 65504 안).
같은 반올림을 넣은 fp64 를 참값으로 삼으면 fp32 계산도 1.9~4.4 × 10⁻⁵ 어긋난다 — fp32 와 fp64 의 값이 반올림 경계를 사이에 두면
반실수 한 칸(2⁻¹¹)만큼 갈리기 때문이라 그 참값은 날카롭지 않다. 그래서 모형의 정확도는 반올림 없는 fp64 와 견주어 치른 값을 재고
llama.cpp(4c)와 견주며, 반올림 자체의 정확성은 시험 커널로 비트까지 본다. 생성의 바닥(반실수 KV): (가중치 494 MB + KV 36 KB × c) /

### 5단계 — 양자화: 밝힌 손실만 (2026-10-09 더함)

사용자 질문 · 결정: 실사용에서는 32비트보다 16비트를, 로컬에서는 8비트 · 4비트 양자화를 많이 쓴다. 4비트 양자화는 구조적으로 의미

판정의 측정 전에 했다(기준은 그대로). (3) 3단계의 작은타일선형이 끝손질에서 공유판24 밖 64 칸까지 쓰고 있던 것을 찾아 고쳤다 — 값은 그대로
(판끼리 직접 대조 다른 칸 0). `공유판N()` 은 크기를 타입에 싣지 않는 날 참조라 컴파일러가 못 잡았다(가상 문법 v0 규칙 1 이 막을 자리 — 사례로
기록). (4) 같은 설정의 생성 시간이 한 실행에서 모델을 여럿 만든 뒤 10% 넘게 흔들린 적이 있다(메모리 자리로 보인다) — 판정 수치는 재기6.py

### 6단계 — 정수 텐서 코어: 프롬프트 처리를 밝힌 정밀도로 (2026-10-09 더함)

사용자 결정: "전반적으로 우월하다"고 말하려면 남은 둘 — 프롬프트 처리를 정밀도를 밝힌 채 빠르게(6단계), 더 큰 모델에서 다시 견주기
(7단계, 모델 내려받기 허락) — 를 함께 한다.

**왜 정수인가.** llama.cpp 가 프롬프트에서 빠른 까닭은 텐서 코어다. 그런데 실수 텐서 코어(f16 · bf16 · tf32 의 mma)는 곱의 합을 어떤
순서 · 정밀도로 반올림하는지 PTX 명세가 정하지 않는다 — 드라이버와 하드웨어가 고른다. PTX 계약(§7 "PTX 계약" — 의미는 PTX 에 다 적고
드라이버가 고를 여지를 남기지 않는다) 밖이다. **정수 텐서 코어(int8 mma)는 곱과 합이 정수로 정확하다** — 반올림이 없으니 명세가 결과를
다 정한다. Q8_0 · Q4_0 의 가중치는 원래 정수 × 척도라 정수 그대로 들어간다. 남는 것은 활성값(짧은실수)을 정수로 바꾸는 일 — 이것을
밝힌다. llama.cpp 도 같은 정수 텐서 코어를 쓰지만 활성값을 32 개씩 **8 비트**로 바꾼다(5단계의 숨은 손실). 글은 30 비트로 바꾸고,
그 정밀도를 계약에 적는다.

**정수 블록 계약 (Q8_0 · Q4_0 가중치의 선형 층 — 새 순서 약속).** 출력 (행 r, 열 n), 블록 b = k 32 줄:
1. 블록의 지수 E = ⌊log₂ max_k |x_k|⌋ (최댓값이 0 이면 −100, [−100, 100] 밖이면 잘라 오류 칸에 표시).
2. n_k = x_k · 2^(29 − E) 를 가까운 정수로(같으면 짝수) — |n| ≤ 2³⁰. 균형 256진 네 자리 D₀ · D₁ · D₂ ∈ [−128, 127], D₃ ∈ [−64, 64].
3. 블록 합 S_j = Σ_k D_j,k · q_k,n — **정수로 정확** (정수 텐서 코어로 구하든 dp4a 로 구하든 같다 — 그래서 프롬프트와 생성이 다른
   명령을 써도 비트가 같다).
4. v_j = S_j · 2^(8j + E − 29) (정확), u = ((v₃ + v₂) + v₁) + v₀ (짧은실수 덧셈 셋), y ← 곱해더하기(u, d_b,n, y) 를 b 오름차순으로
   (y 는 +0 에서), 출력 = y + 치우침 → 끝손질(그대로 · 잔차 · GELU · KV).
반올림은 블록 32 칸마다 넷(덧셈 셋 + 곱해더하기 하나)과 활성값의 고정소수점 — 지금의 4가닥 약속(칸마다 하나)보다 적다. F16 · 짧은실수
가중치는 정수가 아니라 지금의 약속 그대로다.

**판정 전에 잰 것 — 계약의 정확도 흉내**(numpy, GPT-2 의 Q4_0 c_fc 층 하나, fp64 대비 행 노름 상대차 중앙값): 지금의 약속 2.4 × 10⁻⁷,
새 계약 세 자리(22 비트) 2.7 × 10⁻⁷ · 이상치(1% 를 30배)가 있으면 5.3 × 10⁻⁷, **네 자리(30 비트) 9.8 × 10⁻⁸ · 이상치가 있어도
9.5 × 10⁻⁸** — 그래서 네 자리. 비교 대상(5단계, 같은 실행에서 다시 잼): 프롬프트 처리 + 첫 토큰 llama.cpp Q8_0 2.10 / 4.30 / 7.94 ms,
Q4_0 2.02 / 4.15 / 7.80 ms (128 / 512 / 1024), 5단계의 글 2.81 / 6.22 / 11.77 · 2.82 / 6.28 / 11.84 ms. 텐서 일의 양은 llama.cpp(한 자리)의
네 배다 — 의미를 잃지 않는 값.

**진행 기록 (판정 뒤에 밝혀 둔다).** (1) 적은 계약과 구현의 차이: E 는 [−98, 100] 으로 자르고 0 블록은 −98 이다(적은 글은
−100) — s = 2^(29 − E) 가 짧은실수로 유한하려면 E ≥ −98 이어야 해서다(2¹²⁷ 이 가장 큰 2 의 거듭제곱). 자르기 자체는 오류 칸에 적지
않는다: 위로 넘쳐 n 이 2³¹ 을 넘으면 `가까운정수` 의 범위 검사가 오류 칸에 1 을 켜고, 2⁻⁹⁸ 보다 작은 블록은 그대로 덜 정밀하게 간다(CPU
참조도 같다). 정보는 블록마다 M_0 = ((121 + E) << 23) + 2²² 하나([블록][행수를 64 로 올림])이고 M_j = M_0 + 8j·2²³ 은 커널이 구한다.
Q4_0 의 니블은 부호 있는 바이트(q = 니블 − 8)로 곱한다. (2) 값과 상관없이 고른 것: 정수로가 블록의 낱말을 [0 4 1 5 2 6 3 7] 차례로
두어 A 조각의 두 낱말을 8 바이트 하나로 읽는다; 타일 판 여섯(64 × 128 · 64 × 64 · 32 × 64 · 32 × 32 · 64 × 256 · 32 × 256 — 판 수 2 · 3)을 모양마다
재서 고른다(끝손질까지 같은 판을 시험칸에 써서, 클럭이 오르도록 20 ms 넘게 데운 뒤); u 는 계약의 ((v₃ + v₂) + v₁) + v₀ 와 비트까지 같은
정수 길로 구한다 — Q4_0 은 T = (256·S₃ + S₂)·256 + S₁ 이 정수로 정확하고 256·S₃ + S₂ 가 2²⁴ 안이라 (v₃ + v₂) + v₁ = RN(T)·2^(E−21),
u = 곱해더하기(RN(T), 2^(E−21), v₀); Q8_0 은 T = 256·S₃ + S₂ 로 같은 길(커널생성.py 의 증명) — 그래서 블록마다 명령이 12 개에서 7 · 9 개로;
네 자리 바꾸기를 앞 커널에 묶었다(층정규화 1 · 2 → 층정규화정수, 어텐션 → 흐름어텐션정수, c_fc 의 GELU 끝손질 → _겔루정수 — 워프마다
공유 메모리에 모아 16 바이트씩 쓴다); 어텐션의 차례 합을 가중합의 t 반복 안으로(가린 키의 지수는 +0 이라 값이 같다); KV 끝손질의
자리를 행 부분 · 열 부분으로 나눠 미리 구한다; 행이 다섯 이상인 계산은 CUDA 그래프 하나로 띄운다. 모두 값이 그대로임을 대조로 봤다
(묶은 길 · 묶지 않은 길 · 하나씩 길의 로짓이 469 토큰까지 다른 칸 0, 새 어텐션과 옛 어텐션 다른 칸 0). 백엔드는 정수 텐서 코어를 쓰는
함수에서만 4 바이트 둘을 8 바이트 하나로 읽고, 매개변수를 다른 타입으로 본 변수도 판으로 본다 — 이전 모듈 일곱의 PTX 는 바이트까지 같다.
(3) 경과(개발용 재기, Q4_0 128 / 512 / 960): 첫 정수 판 2.38 / 4.69 / 7.57 ms → 블록 끝 명령 줄이기 · 판 넷 2.04 / 4.62 / 7.41 →
KV 끝손질 · 판 고르기 2.02 / 4.42 / 7.26 → 층정규화 · GELU 묶기 1.81 / 4.09 / 6.78 → 어텐션 묶기 1.80 / 4.08 / 6.62 → GELU 자리를
모아 쓰기 1.75 / 3.91 / 6.34 → CUDA 그래프 1.58 / 3.83 / 6.30. 시간 나누기로 본 병목은 블록 끝의 계산이 아니라 활성값 자리(칸마다
4 바이트)를 L2 에서 열 타일마다 다시 읽는 몫과 끝손질의 흩어진 쓰기였다. (4) 찾은 것 — 의미를 지키는 장치가 잡았다: (가) _겔루정수 의
첫 판이 행수 밖의 행(정보가 쓰이지 않은 칸 — 쓰레기 값)까지 네 자리로 바꾸다가 `가까운정수` 의 범위 검사가 오류 칸에 1 을 켰다 —
쓰지도 않을 행의 조용한 쓰레기 계산이 드러났다(그 행을 0 으로 고쳤다). (나) 어텐션을 고치며 안쪽 선언 `짧은실수 M2` 가 바깥의 M2(질의 2
의 누적 최댓값)를 가려 네 행 중 하나가 틀렸다 — 하나씩 길과의 비트 대조가 잡았다. 언어가 가림을 조용히 받는다 — 가상 문법 v0 의
규칙으로 막을 자리(사례로 기록). (5) GPU 는 쉬면 210 MHz(P8)로 내려가 짧은 재기를 흔든다 — 개발용 재기는 30 ms 데운 뒤에 쟀다. 판정
수치는 재기7.py 한 실행(엔진을 번갈아 7번, 중앙값)의 값이다 — 이 실행의 llama.cpp 프롬프트 512 는 4.32 · 4.60 ms 로 판정 전 잰 값(4.15 ·
4.30)보다 느렸다.

**진행 기록 (판정 뒤에 밝혀 둔다).** (1) 재는 법의 차이: 짧은실수 판 · PyTorch eager · HF 는 GPU 메모리(12 GB)에 둘이 함께

줄 판 · 메가커널은 깊이 6400 의 x 와 네 자리를 판에 따로 둘 수 없어 레지스터로 읽어 제자리에 바꾼다(정수판바꾸기제자리 — 같은

일이 네 배라 1.65배 느리다. small 에서는 행렬이 작아 커널 사이의 빈틈 · 바꾸기 · 어텐션 몫이 커서 묶기로 이겼고, XL 에서는 그 몫이

### 8단계 — 자리 둘 계약: 밝힌 정밀도로 프롬프트를 더 빠르게 (2026-10-09 더함)

사용자 결정: 슬로건은 "적힌 대로만 잃고, 느려지지 않는다" 여야 한다 — 의미를 지키되 속도를 버리지 않는다. 그리고 속도에 천장을 두지
않는다: 비교 대상을 이겼다고 멈추지 않고, 안정성을 포기하지 않는 빠른 길이 있으면 반드시 해 본다. 7단계에서 큰 모델의 프롬프트가
llama.cpp 의 1.65배 느린 까닭은 자리 넷(활성값 30 비트)의 텐서 일이 네 배이기 때문이었다.

**계약.** 6단계의 정수 블록 계약에서 자리 수만 둘이다 — 활성값을 자리 넷 · 둘 중 소스가 고른다(둘 다 밝힌 정밀도, 둘 다 남는다):
1. E = ⌊log₂ max_k |x_k|⌋, [−98, 100] 으로(자리 넷과 같다). 2. n_k = 가까운정수(x_k · 2^(13 − E)), |n| ≤ 2¹⁴. 균형 256진 두 자리
D₀ ∈ [−128, 127], D₁ ∈ [−64, 64]. 3. S_j = Σ_k D_j,k · q_k,n — 정수로 정확. 4. v_j = S_j · 2^(8j + E − 13) (정확), u = v₁ + v₀,
y ← 곱해더하기(u, d_b,n, y), 출력 = y + 치우침 → 끝손질. 활성값의 눈금은 블록 최댓값의 2⁻¹⁴ — llama.cpp 의 8 비트(2⁻⁷)보다 128배
촘촘하다. 자리 넷은 그대로 두고(정밀도가 필요한 자리), 호스트가 `자리수=2` 로 고른다.

**왜 둘인가 — 하드웨어 산수.** 정수 텐서 코어는 f16 텐서 코어(fp32 누적)의 두 배 속도다(이 GPU 에서 int8 320 TOPS). 자리 둘이면
텐서 일이 llama.cpp(한 자리)의 두 배 — 그래서 f16 텐서 코어 엔진과 같은 시간이 산수로 성립한다. 자리 넷은 네 배라 큰 모델에서 졌다.

**판정 전에 잰 것.** (가) 계약의 정확도 흉내(numpy, Q4_0 의 실제 층, fp64 대비 행 노름 상대차 중앙값): small c_fc — 가닥 약속
2.4 × 10⁻⁷, 자리 둘 6.4 × 10⁻⁵(이상치 1% × 30 이면 1.3 × 10⁻⁴), 자리 셋 2.7 × 10⁻⁷, 자리 넷 9.8 × 10⁻⁸; XL c_fc(깊이 1600) 자리 둘
6.6 × 10⁻⁵ / 1.3 × 10⁻⁴, XL mlp c_proj(깊이 6400) 6.4 × 10⁻⁵ / 1.4 × 10⁻⁴. llama.cpp 가 활성값을 8 비트로 다시 양자화하며 행렬곱
하나에서 잃는 것은 5.4 × 10⁻³ (5단계 라마양자화정밀도) — 자리 둘의 1/40~1/80. 밝힌 반실수 KV 의 손실(3 × 10⁻⁵)과 같은 자릿수다.
(나) 물리적 바닥 — 프롬프트 1024 의 선형 층 연산을 int8 최고치(3.2 × 10¹⁴ /s)로 나눈 시간: XL 자리 둘 18.9 ms(자리 넷 37.8), small
자리 둘 1.1 ms. 비교 대상(7단계 · 6단계): llama.cpp Q4_0 XL 10.8 / 28.1 / 55.4 ms, small 2.18 / 4.32 / 7.77 ms(128 / 512 / 1024);
지금의 자리 넷 판 XL 14.3 / 46.2 / 92.0, small 1.71 / 4.01 / 7.08. small 은 행렬곱이 바닥의 1 ms 인데 7 ms 가 든다 — 남는 몫은
어텐션 · 정규화 · 바꾸기 · 커널 사이의 빈틈이고, 그것도 천장이 아니다.

두고 모양마다 재서 고른다; 척도를 열마다 한 번 짧은실수로 넓혀 판에 둔다(자리 둘 타일만). (4) 8c(XL) · 8e 가 미달인 까닭과 해 본 것:
타일 하나(XL c_fc)는 자리 넷 494 µs(52%) → 자리 둘 282 µs(47%) — 일이 반으로 줄었는데 효율은 떨어졌다. 끝 계산 세 길(정수 → 실수
변환 · 마법수 덧셈 둘 · 마법수를 mma 누적 입력으로), 척도 f32, 워프를 더 띄우는 타일, 행 조각 넷 타일, 판 넷, 실행한도 둘 — 번갈아 재서
모두 같거나 느렸다(변환 길이 가장 빠름). 시간 나누기(전부 295 / 복사 없음 243 / 동기화 없음 285 / 곱만 220 / 끝만 255 / 읽기만 163 µs):
복사 18% · 동기화 3% 이고, 둘을 다 빼도 계산 핵심(판 읽기 + mma + 끝 계산)이 54% 에서 멈춘다 — mma 만은 60%. 출력 칸마다 블록마다의
끝 계산은 계약의 몫(블록 32 칸마다 곱해더하기 하나)이라 자리 수와 상관없이 같고, 자리 둘에서는 mma 와 같은 무게다. 어텐션(XL 1024,
층당 240 µs)은 FMA 두 단계가 148 µs(최고치의 57%)이고 나머지 94 µs(39%)가 셔플 → 지수 → 저장 → 동기화의 직렬 사슬 — 판 48 KB 라
SM 에 블록 둘뿐이라 겹칠 워프가 없다; 프롬프트 1024 에서 어텐션은 XL 20%, small 30%. (5) 다음 후보(판정은 미리 적는다): 어텐션의
구조(V 를 반실수로 판에, K 를 한 조각 앞서, 판을 줄여 블록 셋 이상), 타일의 끝 계산을 다른 워프에 맡기기(워프 분업) 또는 블록 둘을
한 바퀴에, 정수 KV 캐시 계약(어텐션도 정수 텐서 코어로), 손실 없는 가중치 압축(지수 엔트로피 부호화 — 생성이 대역에 묶여 있어
손실 0 으로 20~30%). (6) 변형 커널을 만드는 스크립트가 `exec` 한 함수의 전역 사본에 자리수를 늦게 넣어 자리 넷 커널을 자리 둘이라
믿고 잰 적이 있다(494 µs 가 그 증거) — 변형의 레지스터 · 넘침 · mma 수를 함께 찍어 잡았다. 같은 커널을 따로 재면 ±5% 흔들려 변형
사이의 차이를 못 가린다 — 변형들은 한 프로세스에서 번갈아 7번(중앙값) 쟀다.

### 9단계 — 정수 KV 계약: 어텐션도 정수 텐서 코어로, 긴 문맥까지 (2026-10-09 더함)

사용자의 물음: 실사용은 모델이 더 크고 대화가 쌓여 로컬에서도 문맥이 10만까지 가는데, 프롬프트 누적에서 계속 뒤지면 실사용에서
성능이 떨어지는 것 아닌가. 맞다 — 그리고 문맥이 길수록 더 뒤진다. 지금의 어텐션은 짧은실수 CUDA 코어(f32 FMA 최고치 4 × 10¹³ /s)로
돌고, 그 일은 문맥의 제곱으로 는다: 합성 긴 모델(small 모양)에서 지금의 자리 둘 · 반실수 KV 판은 프롬프트 4096 에서 어텐션이 62%
(llama.cpp 의 0.64배 — 이긴다), 16384 에서 84% (1.50배 — 진다). llama.cpp 는 어텐션을 f16 텐서 코어(flash attention)로 돌린다 —
f16 누적의 반올림이 정해져 있지 않아 계약 밖의 길이다. 남은 길은 하나다: KV 캐시를 정수 블록 계약으로 두고 Q·Kᵀ 와 P·V 를 정수
텐서 코어의 정확한 합으로 — 활성값(8단계)과 같은 문장으로. 동시에 어텐션의 지수를 하드웨어 근사(ex2.approx) 대신 적힌 다항식으로
바꿔, 어텐션 전체가 CPU 에서 비트까지 재현되게 한다.

**계약 — 정수 KV (자리 둘).** c_attn 의 출력 q · k · v 를 8단계의 활성값과 같은 문장으로 바꾼다(d 32 칸 블록마다 E = ⌊log₂ max|x|⌋
[−98, 100], n = 가까운정수(x · 2^(13 − E)), |n| ≤ 2¹⁴, 균형 256진 두 자리). 키 · 값은 그 자리와 지수(E, 바이트 하나)로 캐시에 남는다
— 칸마다 2 바이트, 블록마다 1 바이트(반실수 KV 의 1.03배). 질의 하나(위치 p, 머리 h)의 어텐션 — 키 조각 σ(64 개씩)와 접기는 4단계의
순서 약속 그대로이고, 조각 안이 바뀐다:
1. 점수 s_t = 0.125 × Σ_b (u_b,t × 2^(E_q,b − 13)) × 2^(E_k,t,b − 13). 블록 b(d 32 칸)마다 u_b,t = 짧은실수(Σ_{d∈b} n_q,d · n_k,t,d) —
   자리 짝 넷의 정수 곱의 합 2¹⁶S₁₁ + 2⁸(S₁₀ + S₀₁) + S₀₀ 을 정확히(35 비트) 구해 짧은실수로 반올림 하나. 거듭제곱 곱은 정확하고
   블록 둘의 합은 곱해더하기 하나(반올림 하나). 가린 키(t > p)는 −3 × 10³⁸ (지금과 같다).
2. m_σ = max_{t∈σ} s_t (순서 무관), e_t = 적힌지수(s_t − m_σ). 적힌지수(x) 는 다항식이다: n = 가까운정수(x · log₂e), r = x − n·C₁ − n·C₂
   (곱해더하기 둘, C₁ = 0.693359375, C₂ = −2.12194440 × 10⁻⁴), p = 1 + r + r²·(c₀ + r·(c₁ + … + r·c₅)) (Cephes expf 의 계수, 곱해더하기
   사슬), 결과 = p · 2ⁿ (지수 비트에 n 을 더한다 — 정확), x < −87.3 이면 0. 근사지수(MUFU)와 달리 모든 연산이 IEEE 짧은실수라 CPU 가
   비트까지 같은 값을 낸다. 접기의 비율(가 · 나)도 적힌지수로.
3. l_σ = 짧은실수(Σ_{t∈σ} 가까운정수(e_t · 2²³)) × 2⁻²³ — 정수로 정확히 더한 뒤 반올림 하나(순서 무관; 지금은 t 오름차순 짧은실수 합).
4. o_σ,d: 값의 블록 b(d 의 32 칸 블록)마다 e′_t = e_t × 2^(E_v,t,b − 13) (정확), 키 32 개 블록 j 마다 e′ 를 자리 둘로(지수 E_e,j,b,
   n_e ∈ [0, 2¹⁴]), u_j,d = 짧은실수(Σ_{t∈j} n_e,t · n_v,t,d) (정확한 합, 반올림 하나), o_σ,d = u_0,d × 2^(E_e,0,b − 13) + u_1,d ×
   2^(E_e,1,b − 13) (반올림 하나).
5. 접기 (M, L, O) 와 출력 O / L 은 지금 그대로(곱해더하기) — 출력은 c_proj 의 자리 둘로 바로.
정수 합은 순서와 상관없으니 프롬프트(텐서 코어 mma)와 생성(dp4a)이 같은 비트를 내는 것이 계약에서 바로 나온다. 지수가 다르니
반실수 KV 판과 로짓이 비트까지 같을 수는 없다 — 9b 로 잰다.

**값에 관한 설계 결정(미리 적는다).** (1) 블록은 32 — 활성값과 같은 문장(64 도 흉내 정확도가 같았지만 문장을 하나로). (2) 자리 짝은
넷(정확한 곱) — 아래 자리끼리의 곱을 뺀 짝 셋은 손실이 2.3배(반실수 KV 보다 커서 기본이 못 된다). (3) KV 자리 하나는 이 문장에서
7 비트(±64)라 llama.cpp 의 Q8_0 KV 보다 나쁘다 — 하지 않는다. (4) 생성은 c_attn 의 출력을 짧은실수로 두고 어텐션 블록이 제 머리의
q · k · v 를 바꾼다(마지막 조각을 맡은 블록이 캐시에 쓴다) — 장벽을 더하지 않는다; 값은 프롬프트의 끝손질이 쓴 것과 같다(선형 계약이
비트까지 같으므로). 캐시 배치: 키 [머리][자리][위치][64 바이트](활성값 배치 그대로 — 낱말 차례 0 4 1 5 2 6 3 7), 값 [머리][키 블록
32][자리][d][낱말 8](낱말 (c, h) 는 키 16h + 2c, +1, +8, +9 — mma 의 B 조각이 바로 읽는 차례), 지수 바이트 [머리][위치][블록 2].

**판정 전에 잰 것.** (가) llama.cpp 자신의 Q8_0 KV 캐시(같은 GGUF, flash 자동): 이 GPU 에서 F16 KV 보다 느리다 — 프롬프트 1024
small Q8_0 7.90 → 9.38 ms, Q4_0 8.04 → 9.05, XL Q8_0 56.5 → 66.1, Q4_0 53.2 → 63.1 (1.13~1.19배); 생성 짧은 문맥 small 0.768 → 0.844 ·
0.688 → 0.761, XL 5.17 → 5.47 · 3.59 → 3.90 ms. 정확도도 같거나 나쁘다 — 64걸음 상대차 중앙값 small Q8_0 5.2 / 3.9 / 6.0 × 10⁻³ →
6.8 / 3.7 / 9.8, Q4_0 2.5 / 0.73 / 2.1 × 10⁻² → 2.2 / 0.86 / 4.0; XL Q8_0 3.3 / 3.3 / 4.0 × 10⁻³ → 3.5 / 3.4 / 4.3, Q4_0 7.4 / 6.9 / 8.8
× 10⁻³ → 7.6 / 7.0 / 10.3; KL small 3.92 → 3.92 × 10⁻² (Q8_0) · 4.06 → 4.12 (Q4_0), XL 1.20 → 1.39 × 10⁻⁴ · 1.27 → 1.40. 그래서 비교
대상은 llama.cpp 의 F16 KV(기본값이자 가장 빠르다)이고 Q8_0 KV 는 기록한다. (나) 계약의 정확도 흉내(numpy, 실제 층의 fp64 q · k · v

1.0 × 10⁻² / 5.6 × 10⁻³ (반실수의 40배 · 26배 — q · e′ 자리 둘을 더해도 같다); **정수 KV 자리 둘(블록 32) 2.3 × 10⁻⁴ / 1.3 × 10⁻⁴**
(반실수 KV 의 0.85 · 0.63배 — 밝힌 정밀도가 오히려 촘촘하다), 블록 64 면 2.5 / 1.4 × 10⁻⁴; 짝 셋 5.2 / 3.8 × 10⁻⁴; KV 자리 하나(7 비트)
3.5 / 1.8 × 10⁻²; 모두 자리 하나 4.9 / 3.3 × 10⁻². (다) 긴 문맥(합성 small 모양 · 위치 102400 · Q8_0 가중치, 같은 모델 — llama.cpp 는
F16 KV · n_batch 2048): llama.cpp 프롬프트 4096 49.1 / 16384 246 / 32768 861 / 102400 7197 ms, 생성 문맥 32768 3.39 · 102336 9.10
ms/토큰; 지금의 글(자리 둘 · 반실수 KV — 최대길이 16384 까지) 프롬프트 4096 31.3 (0.64배) / 16384 369 (1.50배), 어텐션 한 층 1.61 /
25.8 ms. llama.cpp 의 어텐션 효율을 (프롬프트 시간 − 선형 몫)으로 어림하면 f16 최고치의 20~25% (16384 에서 2 × 10¹³ MAC/s). (라)
물리적 바닥 — 짝 넷의 정수 곱(int8 1.6 × 10¹⁴ MAC/s): 어텐션 한 층 XL 1024 42 µs(지금 240), small 1024 20 µs, 합성 small 4096 0.33 ms

### 10단계 — 바탕부터: XL 프롬프트를 바닥 쪽으로 (2026-10-10 더함)

사용자 결정: 범위(Llama 계열 · 다른 GPU)를 넓히기 전에 **바탕이 되는 길(타일 · 어텐션 · 사이의 커널)을 먼저 바닥 가까이 맞춘다** — 범위를
먼저 넓히면 모든 범위에서 속도를 다시 맞춰야 한다. 그리고 llama.cpp 는 이 조건의 사실상 기준이지 최고 속도가 아니다 — CUDA C++ · vLLM ·
TensorRT-LLM 같은 더 빠른 길이 있으니 속도는 아직 뒤쳐져 있다고 본다. 9단계로 긴 문맥은 닫혔고, 남은 것은 XL 프롬프트(llama.cpp 의
1.05~1.23배)와 커널 효율(타일 47%, 어텐션 바닥의 2.3~3.3배)이다.

**속도의 가능성 — 둘로 나눠 본다.** (1) 같은 계약 안에서 남은 몫: XL 1024 의 59.4 ms 는 선형 타일 45.9(84%) + 어텐션 6.8(12%) + 층정규화
1.8 + 로짓 · 임베딩 0.4 이다(아래 "판정 전에 잰 것"). 타일이 int8 최고치의 40~45%, 어텐션이 바닥의 3.3배이니 타일 60~65% · 어텐션 2배면
XL 1024 는 38~42 ms — 공학으로 닫을 수 있는 약 1.5배. CUDA C++ 로 같은 의미의 커널을 손으로 써도 더 빠를 이유는 없다(PTX 계약은 명령을
바꾸지 않고, 같은 드라이버가 같은 기계어를 만든다). (2) 계약이 치르는 값: 활성값 자리 둘은 8 비트 엔진의 두 배 정수 일, 어텐션의 자리 짝
넷은 f16 플래시 어텐션의 두 배 일 — 같은 효율이면 8 비트 · FP8 엔진보다 두 배 느린 것이 "적힌 대로만 잃는다"의 값이다. 넘는 길은 자리
하나 계약(8 비트 — 손실은 여전히 적힌 대로)을 소스가 고르게 두는 것뿐이고, 그것은 이 단계의 일이 아니다.

### 12단계 — 겹치기 · 어텐션 · 지속 사용 (2026-10-10 더함)

사용자 결정: 겹치기 구조 변경을 진행하고 어텐션도 개선한다 — "특히 실사용에서는 지속적인 사용이 필수적인데 아무리 처음이 빠르더라도
사용할때 성능이 줄거나 더 느려지면 속도쪽에서 내세울 입지가 없어". 그래서 이 단계는 처음 한 번의 속도가 아니라 **쓰는 동안의 속도**
(대화가 길어지며 문맥이 자랄 때, 길이가 제각각인 차례가 이어질 때, 오래 돌릴 때)를 판정에 넣는다.

**판정 전에 잰 것.** (가) 겹침 시험 커널(블록 128 스레드 × SM 마다 셋, 반복마다 mma 32): mma 만 337 TOPS(최고치 수준 — 클럭이 기준보다
높다), 끝 계산을 흉내 낸 명령 256 개를 섞으면 mma 만의 1.09배(따로면 1.40배), 끝 계산이 mma 결과를 읽어도 1.10, 반복마다 장벽 1.10,
공유 메모리에서 A 를 다시 읽으면 1.33배 — 이 GPU 는 mma 와 실수 명령을 겹칠 수 있다. (나) 11단계 타일의 시간 나누기(c_fc Q8_0, 245 µs ·
53.5%, 값이 틀리는 변형은 재는 데만): 비동기 복사를 빼면 216(−12%), 블록마다의 장벽을 빼면 237(−3%), 복사 · 기다림 · 장벽을 다 빼면 209
(62.8%) — 복사 길이 17%, 계산만의 몸이 63% 다. 명령은 워프마다 32 블록에 485 개(끝 계산 266 · mma 32 · 읽기 35 · 복사와 주소 약 130).
(다) 지속 사용 — 합성 긴 모델(small 모양, 위치 102400)로 차례마다 덩이 1024 토큰을 앞 캐시에 이어 넣고 64 토큰 생성, 두 엔진을 차례마다
번갈아 문맥 10만 1천까지: 넣기는 첫 차례 말고 모두 글이 짧지만 우위가 좁아진다(llama.cpp 대비 0.78 → 0.90배), **생성은 문맥 5만 8천부터
llama.cpp 보다 느리다**(10만 1천에서 9.38 대 9.01 ms/토큰 — 1.04배; 처음은 0.60배). 첫 차례는 207 ms(llama.cpp 43) — 처음 보는 길이마다
판을 재서 고르고 계획을 만든다. **덩이 · 생성 길이가 무작위(16~1024 · 16~128)면 거의 모든 차례가 120~220 ms**(llama.cpp 3~18) — 새 길이마다
같은 일을 다시 한다. (라) 프롬프트 길의 CUDA 그래프는 위치마다 다시 만들어졌다(대화에서 차례마다 0.4~0.5 ms) — 판정을 적기 전에 고쳤다:
그래프의 열쇠에서 위치를 빼고 위치를 받는 마디(임베딩 · 어텐션 · KV 끝손질)의 매개변수만 고친다(값은 그대로 — 12a 가 확인한다).

**할 것(값은 모두 비트까지 같아야 한다).** 실사용: 판 고르기를 행 수의 묶음(2 의 거듭제곱)마다 한 번 — 모델을 올릴 때 미리, 처음 쓰는 계획은
그래프 없이. 타일: 비동기 복사의 주소를 32 비트로, 블록마다의 장벽 대신 비동기 장벽(mbarrier — 글ptx.py 에 장벽만들기 · 장벽도착 ·

### 13단계 — 두 층 접기: 긴 문맥의 짧은 덩이까지 (2026-10-10 더함)

사용자 결정: "어텐션을 고쳐봐" — 12단계 뒤의 추천(어텐션의 접는 순서를 두 층으로 바꾸는 계약 변경)을 따른다.

**왜.** 정수 KV 계약(9단계)의 접기는 키 조각(위치 64)을 처음부터 끝까지 한 줄로 차례대로 접는다. 앞 조각을 접어야 다음을 접으니 한
(행, 머리)의 일을 블록들에 나눌 수 없고, 덩이가 짧으면 블록이 머리 수뿐이다. 12단계의 갈래 판이 블록 안에서 조각 여덟을 함께 계산해
3.3~3.7배 줄였지만 블록 수는 그대로라, 긴 문맥의 짧은 덩이는 아직 llama.cpp 보다 느리다(아래).

**새 계약 — 값이 바뀌는 곳은 위치 1024 넘어서뿐.** 조각을 묶음(조각 16 개 = 위치 1024; 묶음 g 는 위치 [1024g, 1024g + 1024))으로 나눠
(1) 묶음 안에서 조각을 지금과 같은 식 · 같은 차례로 접어 묶음의 (M_g, L_g, O_g) 를 만들고(묶음의 첫 조각이 처음 값), (2) 묶음들을
g = 0, 1, … 차례로 같은 식으로 접는다(첫 묶음이 처음 값): M′ = max(M, M_g), 가 = 적힌지수(M − M′), 나 = 적힌지수(M_g − M′),
L ← 곱해더하기(L_g, 나, L·가), O ← 곱해더하기(O_g, 나, O·가). 행의 조각은 제 위치까지라 마지막 묶음은 짧을 수 있다. 묶음의 경계는 위치만으로
정해지므로 어느 길(프롬프트 · 나눈 덩이 · 대화 · 하나씩 · 메가커널)로 계산해도 같은 비트라는 9단계의 성질은 그대로다. **위치 1024 까지는
묶음이 하나라 9~12단계의 계약과 비트까지 같다** — GPT-2 small · XL(위치 1024)의 모든 결과는 그대로이고, 바뀌는 것은 합성 긴 모델(위치
102400)의 1024 넘는 문맥뿐이다. 묶음 상태끼리 다시 접는 일은 조각마다가 아니라 묶음마다라, 묶음들을 블록들에 나눠 계산하고 묶음 상태
(행마다 낱말 66)만 전역에 두면 된다 — 키 · 값 1024 개(256 KB)마다 행마다 264 바이트.

**판정 전에 잰 것.** (가) CPU 참조(정수계약.어텐션)를 두 층으로 고쳐(묶음 = None 이면 한 층) 옛 구현과 견줬다: 한 층은 위치 300 · 1024 ·
2500 에서 옛 구현과 다른 칸 0, 두 층은 300 · 1024 에서 0(묶음 하나), 2500 에서 61181 칸이 다르다(설계대로 1024 뒤의 행만). 첫행 인자(뒤의

## 8. 운영 규칙

- 연구 산출물은 `research/gpu/`, 작업은 가지 `research/gpu` 에서.
- **참조 구현에서 먼저 시험**하고(D-44 선례), 이정표를 닫을 때 자체 컴파일러로 옮겨 고정점과 바이트 대조를 되찾는다.
  PTX 는 텍스트라서 두 구현이 같은 PTX 를 내는지 지금의 덤프 대조처럼 볼 수 있다.
- 호환 약속은 그대로다. GPU 쪽 새 문법은 1.x 코드를 깨지 않는 방식(새 옵션, 새 파일)으로 들어오고, 깨야 하면
  2.0 결정으로 간다.
- CI 에는 GPU 가 없다 — PTX 생성과 대조는 CI 에서, 실행은 이 PC 에서.
- 시간 상자: 0단계 2주, 2단계 6주(초안). 넘기면 그 자리에서 판정한다.

## 9. 하지 않는 것

범용 GPU 언어, 초기의 성능 경쟁, NVIDIA 밖의 장치(나중에 SPIR-V), 자동 미분과 학습.

## 10. 위험

- 가상 문법 v0 의 모호성 — `별로` 와 `마다` 의 경계, 줄이기 동사 목록. 특히 종류 추론(양수 / 축 합 → 확률)은 주장이 크다.
- 1인과 AI 의 규모, 그리고 두 구현을 함께 키우는 비용.
- 종이 시험의 편향 — 0단계가 그것을 이긴다.
- 주장 C 는 성능 주장이라 비교가 기울기 쉽다 — 같은 의미의 판끼리만 견주고, 기준(시간·배수)은 실험 전에 적은 §7 의 표를 따른다.
- `-서` 사슬이 길면 오히려 읽기 어렵고, 이름 없는 중간값은 들여다볼 수 없다(디버깅). 활용(특히 불규칙)을 받는 비용이 든다.
