# 검토 언어 G0: 최초 실행·변환 계약

2026-09-08. 사용자가 확정한 새 방향의 첫 구현이다. G0는 실험 계층이며 기존 1.x `.gl` 문법과 실행 파일 호환성을 바꾸지 않는다. 현재는 단일 정수 입력의 결정 규칙과 여러 C 파일에 흩어진 상수 함수 호출을 다룬다. 이후 첫 적용 대상은 [TypeScript·React 웹 프론트엔드](13-웹-검토언어-방향.md)로 정했다. 아래 내용은 현재 구현된 C G0의 계약이다.

## 의미

프로필은 `geul-g0/int32-decisions/v1`이다. 입력과 출력은 부호 있는 32비트 정수이며 정의역은 -2147483648부터 2147483647까지다. 효과가 없고 반드시 종료한다. 규칙은 서로 겹치지 않는 오름차순 반열린 구간 `[하한, 상한)`이며 모든 입력을 정확히 한 번 덮는다. 각 구간에서는 정수 상수 하나를 반환한다. 끝 경계 2147483648은 구간 표현에만 쓸 수 있고 입력·출력 값은 아니다.

관찰할 동작은 반환값이다. 이 범위를 벗어난 상태·호출·산술·예외를 숨겨서 ‘동등’이라고 하지 않는다. 입력 구간을 줄이는 암묵적인 전제도 없다.

## 문법

UTF-8, NFC 텍스트를 사용한다. 빈 줄은 허용한다. 각 문장은 한 줄이다. 이름은 NFC인 유니코드 글자·숫자·밑줄로 이루어지고 글자 또는 밑줄로 시작한다. 이름은 업무 의미를 증명하지 않는다.

```text
「배송비」는 부호 있는 32비트 정수 「주문금액」으로 결정한다.
「주문금액」이 0 미만이면 -1을 돌려준다.
「주문금액」이 0 이상 50000 미만이면 3000을 돌려준다.
「주문금액」이 50000 이상이면 0을 돌려준다.
```

헤더는 위 형식 하나다. 조건은 `N 미만`, `N 이상 M 미만`, `N 이상`, `모든 범위` 중 구간 위치에 맞는 형식이다. `모든 범위`는 규칙이 하나일 때만 사용한다. 정수는 ASCII 십진 표기이며 0 이외의 앞자리 0, + 부호, -0은 허용하지 않는다. 같은 결과의 인접 구간은 의미 비교·출력 시 합칠 수 있다. 반환값은 int32 범위 안이어야 한다.

## C 경계

단일 파일 명령 `lift-c`·`verify-c`는 C11 소스의 함수 정의 하나를 받는다. 반환 타입은 `int`, 매개변수는 `int` 하나이며 정적/가변/포인터/한정 타입은 받지 않는다. 선언·링크 환경을 추측하지 않는다. C의 `int`가 정확히 32비트인 환경이 전제다. 생성 파일과 검사 결과에도 전제를 명시한다.

C 이름은 ASCII 글자로 시작하고 이후 글자·숫자·밑줄을 허용한다. 예약 식별자·전처리 매크로가 이름을 바꾸는 경우를 받지 않는다. 빌드 옵션으로 소스 의미를 바꾸지 않는 C11 환경이 전제다. 물리적 CRLF/CR 개행은 C 주석 해석 전에 LF로 정규화하되 원본 해시는 정규화 전 텍스트를 사용한다.

본문에서는 블록, `if/else`, 정수 상수 반환만 허용한다. 조건은 입력과 int32 상수의 `<`, `<=`, `>`, `>=`, `==`, `!=` 비교이며 피연산자의 순서는 바뀔 수 있다. 음수와 `(-2147483647 - 1)`의 INT_MIN 표기는 지원한다. 그 밖의 산술식, 상수 변환, 외부 함수 호출, 반복문, 지역 변수, 전역 변수, 전처리 지시문, 문자열·문자 리터럴은 거부한다. C 주석은 허용한다.

모든 입력에서 반환해야 한다. 조건 분기의 낙하와 뒤따르는 문장도 의미에 포함된다. 같은 매개변수를 다른 이름으로 바꾸는 것은 결과에 영향이 없다. 도달 불가능한 곳에도 미지원 구문이 있으면 거부한다. 비표준 소스의 의미를 추측하지 않는다.

## 여러 C 파일의 상수 함수 연결

`lift-project`·`verify-project`는 명시적으로 나열한 C 파일을 각각의 번역 단위로 유지한다. 파일 내용을 이어 붙여 다른 파일의 선언이 보이는 것으로 처리하지 않는다. 프로젝트 형식은 다음과 같다.

```json
{
  "format": "geul-g0-c-project/v1",
  "entry": "shipping",
  "sources": ["policy.c", "limits.c", "fees.c"]
}
```

`entry`는 int 입력 하나를 받는 선택한 함수다. `sources`는 프로젝트 JSON이 있는 디렉터리 아래의 상대 `.c` 경로이며 `/`로 구분한다. 중복 키·파일·하드 링크, 상위 디렉터리 이동, 절대 경로, 프로젝트 밖으로 향하는 심볼릭 링크를 거부한다. 입력 JSON과 모든 C 파일은 출력 덮어쓰기 방지 대상이다.

각 파일에는 함수 원형과 함수 정의만 둘 수 있다. 함수 원형에는 `extern`을 허용하지만 정의의 `static`·`extern`·`inline`은 지원하지 않는다. 선언과 정의의 반환 타입·인자 수가 일치해야 하며 호출 위치보다 앞서 같은 파일에서 선언을 볼 수 있어야 한다. 인자가 없는 함수는 `함수(void)`로 선언한다. 인자 정보를 주지 않는 `함수()` 선언은 거부한다. 입력 이름이 함수 이름을 가리는 호출도 거부한다.

상수 보조 함수의 본문은 `return 상수;` 또는 `return 다른상수함수();` 하나다. 해당 호출은 인자가 없고 재귀가 없어야 한다. 선택한 int 입력 함수는 비교 경계 또는 반환값 자리에 이 상수 호출을 사용할 수 있다. 호출 체인을 확인해 실제 상수를 대입한 뒤 기존 구간 검사기로 전체 입력을 비교한다. 지역·전역 상태, 산술식, 조건을 가진 보조 함수, 인자가 있는 호출과 함수 포인터는 아직 지원하지 않는다.

모든 제공된 선언에는 제공된 정의가 있어야 한다. 선택한 함수에서 사용하지 않는 정의도 지원 범위와 반환 경로를 검사한다. 그러나 결과가 주장하는 동등성의 대상은 선택한 진입점이다. 기록의 `checked_functions`와 `reachable_functions`를 구분한다. 외부 연결 과정에서 제공한 함수 정의가 다른 구현으로 교체되지 않는다는 전제도 명시한다.

검사 기록에는 모든 C 파일·프로젝트 JSON의 해시, 선택한 진입점, 실제로 참조한 함수의 파일·줄, 상수 값, 호출 위치가 포함된다. 보조 파일 하나가 바뀌어도 기존 기록은 재검사해야 한다. 한 파일의 코드에 대한 실행 증거를 전체 프로젝트로 확대하지 않는다.

최대 C 파일 32개, 파일별 1MiB, 소스 합계 4MiB, 함수 128개, 상수 호출 깊이 32를 허용한다. 이미 계산한 상수를 재사용하더라도 실제 호출 체인의 깊이 제한은 적용한다. 기존 AST·경로 분석 한계도 그대로 적용한다.

변환 후 `emit-c`가 만드는 것은 선택한 행동을 구현하는 독립 C 함수다. 기존 파일 배치와 함수별 구현에 수정을 되돌려 쓰는 편집 동기화 기능은 아직 없다. `#include`·매크로·조건부 컴파일과 빌드 데이터베이스 수집도 아직 지원하지 않는다.

## 검사 수준

C 문법 트리를 제한된 조건·반환 모델로 검증하고, 입력 구간을 조건에 따라 정확히 분할하며 실행한다. 출력된 모든 경로 구간은 겹침·누락 없이 int32 전체를 덮어야 한다. 그 구간과 글의 구간을 합친 분할에서 결과를 비교한다. 다르면 첫 반례 입력과 두 반환값을 제공한다. 지원된 모델에서는 임의 입력 표본만 뽑는 검사가 아니다.

각 비교 조건의 참/거짓은 해당 경계로 나눈 구간 안에서 일정하고, 문장은 조건 분기와 상수 반환뿐이다. 그러므로 각 구간에서 경로와 반환값이 일정하다. 모든 구간을 비교하는 것으로 이 제한된 모델의 전체 입력 결과를 결정할 수 있다.

결과 이름은 `equivalent_in_g0_model`, `different`, `unsupported`다. `equivalent_in_g0_model`은 **Python 검사기·pycparser·소스 해석·C ABI 전제 아래 모델의 전범위 비교가 통과했다는 뜻**이다. 검사기 자체의 정형증명, GCC/Clang 및 생성 기계어의 정확성, 일반 C의 의미 보존, 기획 의도는 증명하지 않았다. 실행 결과는 별도의 차등 실행 테스트로 확인한다.

검사 기록에는 원본 글과 C 소스의 SHA-256, 의미 프로필, 검사기 소스의 SHA-256, pycparser 버전, 전제, 분할 개수, 반례를 담는다. 기록을 다시 확인할 때는 현재 파일로 검사를 다시 실행하고 기록 전체를 비교한다. JSON에 성공 문자열이 있는 것만 믿지 않는다. 미지원 또는 다른 결과는 CLI에서 0이 아닌 종료코드를 반환한다.

파일/규칙/깊이/검사 비용 한계를 넘으면 오류다. 성공한 부분만 조용히 반환하지 않는다. 출력 경로가 입력 경로와 같으면 거부하고, 파일 쓰기는 임시 파일 교체로 완료한다. C 생성은 생성한 C를 다시 분석·비교한 뒤 출력한다.

## 실행

```powershell
python -m pip install -r requirements-review.txt
python build.py review check examples/review/배송비.glr
python build.py review run examples/review/배송비.glr 55000
python build.py review emit-c examples/review/배송비.glr -o build/review/배송비.c
python build.py review verify-c examples/review/배송비.glr build/review/배송비.c -o build/review/검사.json
python build.py review verify-c examples/review/배송비.glr build/review/배송비.c --record build/review/검사.json
python build.py review lift-c examples/review/배송비.c --name 배송비 --input-name 주문금액
python build.py review lift-project examples/review/shipping-project/project.json --name 배송비 --input-name 주문금액 -o build/review/프로젝트.glr
python build.py review verify-project build/review/프로젝트.glr examples/review/shipping-project/project.json -o build/review/프로젝트-검사.json
python build.py review verify-project build/review/프로젝트.glr examples/review/shipping-project/project.json --record build/review/프로젝트-검사.json
python build.py review compare examples/review/배송비.glr examples/review/배송비-수정.glr
python build.py review-test
```

`compare`는 전체 정의역에서 결과가 달라지는 구간을 JSON으로 출력한다. 차이가 있다는 사실은 명령 오류가 아니므로 0으로 종료한다. `verify-c`의 의미 불일치는 종료 코드 1이다. 입력·미지원 오류는 1, 명령 사용 오류는 2다. 출력은 UTF-8이다.

`review-test`는 GCC가 PATH에 있어야 한다. 환경변수 `CC`에는 실행 파일 경로만 지정할 수 있다. 누락 시 테스트는 실패하고 건너뛰지 않는다. 기존 `.gl` 테스트는 기존 `python build.py test`로 실행한다.

## 고정 평가집과 다음 단계

`review-tests/positive.json`의 수작업 C 사례 20개와 기대 구간을 첫 개발 평가집으로 고정한다. 개발 결과를 보고 실패 사례를 제거하지 않는다. 이는 공개 개발 사례이며 독립 보류 평가집이 아니다. `negative.json`의 부정 사례와 의미를 변경한 C, 오래되거나 변조된 검사 기록을 검사한다. 원본 C·글의 독립 실행·재생성 C를 GCC로 차등 실행한다. 경계, INT_MIN/MAX, 고정 시드 입력을 포함한다.

`projects.json`에 각각 3~4개 번역 단위를 가진 수작업 프로젝트 5개를 추가했다. 원본 파일은 실제로 따로 컴파일한 뒤 연결해 재생성 함수와 비교한다. `project-negative.json`의 20개 사례는 미해결 정의, 잘못된 선언 범위, 타입 불일치, 입력에 가려진 함수, 재귀와 숨은 상태 등을 고정한다. 이는 자체 작성한 개발용 사례이며 실제 외부 프로젝트에서의 성공률이나 가독성 평가가 아니다.

최초 사람 평가 질문은 다음과 같다. 아직 사용자 실험을 수행하지 않았다.

1. 주문금액이 음수일 때 반환값은 무엇인가? 그 숫자의 업무 의미까지 알 수 있는가?
2. 49999, 50000, 59999, 60000에서 수정 전후 반환값은 무엇인가?
3. 이 규칙에 외부 호출이나 상태 변경이 있는가? 이를 뒷받침하는 범위는 무엇인가?
4. 조건이 `>=`에서 `>`로 바뀌면 영향을 받는 입력은 무엇인가?
5. 미지원 호출이 있는 원본에 대해 도구가 동등성을 주장하는가?

후속 개발은 [웹 연구 계획](13-웹-검토언어-방향.md)에 따른다. 기존 C 검사는 회귀 실험으로 유지한다. G0 자체의 검사기 정확성을 기계적으로 증명한 것은 아니므로 이 구현만으로 로드맵의 정형검증 단계를 완료했다고 보지 않는다.
