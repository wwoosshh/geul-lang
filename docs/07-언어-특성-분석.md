# 글 언어 특성 분석 — 한국어 문법이 만드는 이점과 함정

작성 2026-09-04. 이 문서는 의견이 아니라 실험 기록이다. 각 항목은 실제로 컴파일하고 실행해 확인했다.

글은 한국어의 어순(SOV)과 조사(역할 표지)를 문법으로 삼는다. 그래서 영어·명령어 기반 언어와
성질이 다르고, 다른 언어에서 당연하게 여기던 문제가 저절로 사라지기도 하고, 다른 언어에는
없던 문제가 새로 생기기도 한다. 이 문서는 그 둘을 구분해 적는다.

방법: 가설마다 최소 프로그램을 만들어 참조 구현으로 컴파일·실행하고 결과를 기록했다. 세 라운드,
서른 개 남짓한 프로그램을 썼다. 실패한 것도 그대로 적었다.

---

## 1. 확인된 이점

### 1.1 조사가 인자 순서를 없앤다

역할 조사가 붙은 인자는 순서와 무관하게 같은 매개변수에 간다. 세 가지 순서로 쓴 같은 호출이
같은 결과를 냈다.

```
[문자열 원본에서 문자열 대상으로 정수 개수를 옮기기]는 -> 정수 { … }

3을 "왼쪽"에서 "오른쪽"으로 옮기다.
"오른쪽"으로 3을 "왼쪽"에서 옮기다.
"왼쪽"에서 3을 "오른쪽"으로 옮기다.
```

세 줄 모두 `왼쪽에서 오른쪽로 3개`를 출력했다.

**이 이점이 실제로 얼마나 큰가.** 처음에는 C 의 `memcpy`/`bcopy` 인자 순서 혼동을 예로 들었는데,
그것은 임베디드나 저수준 C 에 치우친 오래된 예다. `bcopy` 는 이미 폐기된 함수이고 대부분의 개발자는
평생 만질 일이 없다. 예를 바꾸는 것이 정직하다.

같은 성질의 문제로 보통의 개발자가 실제로 겪는 것은 이런 것들이다.

- `substring(시작, 끝)` 과 `substr(시작, 길이)` — 모양이 같고 뜻이 다르다.
- 자바스크립트 `splice(시작, 지울개수, ...)` — 둘째 인자를 끝 위치로 착각한다.
- JUnit 의 `assertEquals(기댓값, 실젯값)` — 뒤집어 쓰면 실패 메시지의 기대와 실제가 반대로 나온다.
- 자바 `System.arraycopy(원본, 원본위치, 대상, 대상위치, 길이)` — 위치 인자 다섯 개.
- 호출부의 참·거짓 리터럴 — `창_설정(참, 거짓)` 은 읽어서 뜻을 알 수 없다.
- `atan2(y, x)` — 이름 순서와 인자 순서가 반대다.

더 나은 근거는 일화가 아니라 업계가 여기에 쏟은 투자다. 편집기의 인라인 매개변수 힌트
(인텔리제이·VS Code 가 호출부에 매개변수 이름을 겹쳐 보여 주는 기능)는 정확히 이 문제 때문에
생겼다. 스위프트는 인자 레이블을 기본값으로 강제했고, 파이썬·코틀린·C# 은 이름 붙인 인자를 넣었으며,
린터는 호출부의 불리언 리터럴을 경고한다. 언어와 도구가 모두 같은 곳을 덧대고 있다는 것은 문제가
실재한다는 뜻이다. 글은 그 자리를 문법으로 이미 덮고 있다.

**한계도 분명하다. 보호는 역할이 서로 다를 때만 성립한다.** 실측했다.

| 함수 | 호출 두 가지 | 결과 |
|---|---|---|
| `[정수 기댓값과 정수 실젯값을 같은가]` | `1을 2와` / `2와 1을` | 둘 다 기대 2, 실제 1 — 순서 무관 |
| `[정수 a를 정수 b를 정수 c를 셋]` | `1을 2를 3을` / `3을 2를 1을` | `1 2 3` / `3 2 1` — 순서가 결정한다 |

매개변수에 쓸 수 있는 역할은 대상(을·를), 목적지(에), 출처(에서), 수단(로·으로), 동반(와·과)
다섯 가지다. 같은 역할이 여럿이면 표면 순서로 대응하므로(명세 3.5) 보호가 사라진다. 정수 셋을 받는
함수처럼 성질이 같은 인자가 여럿인 경우가 바로 그렇다. 즉 글의 보호는 **역할이 자연스럽게 갈리는
호출에서만** 작동하고, 그런 호출이 실무에서 흔하기는 하지만 전부는 아니다.

비슷한 장치가 다른 언어에도 있다. 스몰토크·오브젝티브C 의 키워드 메시지, 스위프트의 인자 레이블,
파이썬·코틀린의 이름 붙인 인자다. 차이는 두 가지다. 그것들은 언어에 덧붙인 장치인데 글은 문법에
내재해 있고, 그것들은 이름을 하나하나 붙이는 반면 글은 다섯 개짜리 역할 어휘를 쓴다. 후자는 표기가
짧아지는 대신 표현력이 좁다. **덧붙인 이름표보다 강하지 않다. 대신 공짜다.**

### 1.2 동사형 호출은 식으로도 쓸 수 있다

괄호로 감싸면 값이 필요한 자리에 그대로 들어간다. 중첩도 된다.

```
정수 r = (3을 세다).
"%lld\n"을 (3을 세다)를 쓰다.
반환 (값을 세다) + 10.
(3을 큰가하다)이면 { … }
"%lld\n"을 ((3을 세다)를 세다)를 쓰다.
```

다섯 가지 모두 통과했다. 괄호를 빼면 전부 오류다. 즉 동사형은 문장 전용이 아니라 "식 자리에서는
괄호가 필요한 형식"이다. 이 규칙은 명세 3.5 에 있다.

### 1.3 연결 어미로 문장을 잇는다

```
1을 찍고 2를 찍다.
```

`고` 와 `서` 로 절을 이으면 차례로 실행된다.

### 1.4 조사 분리의 영향 범위가 좁다

조사를 떼는 처리는 **매개변수 이름에만** 적용된다. 확인한 결과 지역 변수, 전역 변수, 묶음 필드,
함수 이름은 조사 음절로 끝나도 온전하다.

| 자리 | `길이` / `경로` 같은 이름 | 결과 |
|---|---|---|
| 지역 변수 | `정수 길이 = 5.` | 정상 |
| 전역 변수 | `정수 경로 = 4.` | 정상 |
| 묶음 필드 | `묶음 상자는 정수 길이, 정수 경로.` | 정상 |
| 함수 이름 | `[정수 값을 추가]는` | 정상 |
| **매개변수** | `[문자열 경로 열기]는` | **훼손 (2.1)** |

### 1.5 식 자리에서는 조용히 쪼개지 않는다

`길` 만 선언한 상태에서 `길이를 쓰다` 라고 쓰면, `길`+주어조사로 읽지 않고
"선언되지 않은 이름입니다: '길이'" 오류를 낸다. 낱말 전체를 먼저 찾는다.

### 1.6 오류 위치가 문자 기준으로 정확하다

한글이 앞에 있는 줄에서도 열 번호가 맞다. 아래에서 `없는이름` 은 23번째 문자이고 컴파일러도 23을
보고했다. 바이트 기준이었다면 45쯤을 가리켰을 것이다.

```
    정수 나쁨 = 아주아주긴이름 + 없는이름.
```

## 2. 확인된 약점

### 2.1 매개변수 이름이 조용히 훼손된다 (심각)

가장 큰 문제다. 조사 없는 매개변수의 이름이 조사 음절로 끝나면, 그 음절이 역할 조사로 떨어져
나가고 **이름이 짧아진다. 경고는 없다.**

```
[문자열 경로 열기]는 { … }
```

여기서 매개변수의 실제 이름은 `경` 이고 역할은 수단(`로`)이다. 확인한 세 가지 증상:

- 본문에서 `경로`를 쓰면 "선언되지 않은 이름입니다: '경로'" — 선언한 줄이 아니라 사용한 줄에서 난다.
- 본문에서 `경`을 쓰면 **정상 컴파일된다**. 아무 경고도 없다.
- 호출부는 `"가.txt"를 열다` 가 아니라 `"가.txt"로 열다` 여야 한다. 틀리면
  "'열기' 호출에 '경'(로) 인자가 없습니다" 라고 나오는데, 사용자는 `경` 이라는 이름을 쓴 적이 없다.

이름이 한 글자짜리가 아닌 경우에는 아예 거부되기도 한다. `[정수 길이 재기]는` 은
"매개변수에 쓸 수 없는 조사 '이'" 오류다. `길이` 는 어느 언어에서나 가장 흔한 매개변수 이름인데
거부되고, 메시지는 원인을 설명하지 않는다.

영향을 받는 낱말은 드물지 않다. 조사 음절(이·가·과·로·은·는·을·를·에·와)로 끝나는 일상어 중
프로그램에 나올 법한 것만 꼽아도 이만큼이다.

> 길이, 높이, 넓이, 사이, 나이, 종이, 놀이, 경로, 통로, 진로, 회로, 도로,
> 추가, 증가, 평가, 참가, 결과, 효과, 성과, 경과

기존 코드베이스를 감사했다. 표준 라이브러리·컴파일러·테스트를 합쳐 매개변수 자리에서 조사가
떨어지는 낱말이 1417개 있고, 그중 한글 두 음절이 한 음절로 줄어든 것이 102개다. 하지만 그것들은
`값을`(51회), `키를`, `글을`, `틀을`, `수를`, `폭을` 처럼 **원래 한 음절인 이름에 조사를 붙인
것**이라 올바른 처리다. 본문이 낱말 전체를 이름처럼 쓰는 사례, 즉 실제로 훼손된 사례는 **0건**이다.

위험을 피한 것이 아니라 드러나지 않은 것이다. 표준 라이브러리와 컴파일러가 거의 모든 매개변수에
역할 조사를 붙이는 습관을 지켰기 때문이다. 조사를 붙이면 `경로를` → (`경로`, `를`) 로 올바르게
갈라진다. 습관에 기대고 있을 뿐 규칙이 막아 주지는 않는다.

### 2.2 이름이 `의`로 끝나면 선언할 수 없다

`정의`, `회의`, `주의`, `강의`, `편의` 는 이름이 될 수 없다. `정의` 는 프로그래밍에서 매우 흔한
낱말이다. 멤버 접근의 `의` 와 구별할 수 없기 때문인데, 사용자에게는 임의의 금지로 보인다.

### 2.3 변환 조사와 역할 조사가 충돌한다

`로`·`으로`는 형 변환 표지이면서 동시에 수단 역할의 조사다. 그래서 변환 결과를 바로 인자로 줄 수 없다.

```
"%f\n"을 i로 실수를 쓰다.      (* 오류: 선언되지 않은 이름입니다: '실수' *)
"%f\n"을 (i로 실수)를 쓰다.    (* 정상 *)
```

괄호로 풀리지만, 규칙을 모르면 오류 메시지가 원인을 짚어 주지 않는다.

### 2.4 동사 대응이 조용히 하나를 고른다

`계산` 과 `계산하기` 가 둘 다 있으면 `계산하다` 는 `계산하기` 를 부른다. 명세의 우선순위대로지만
경고가 없다. 어근이 겹치는 두 함수가 우연히 생기면 호출부가 조용히 다른 함수로 간다.

### 2.5 자연어처럼 보이지만 활용은 지원하지 않는다

연결 어미 `서` 는 어간을 바꾸지 않은 `찍서` 만 받는다. 한국어로 자연스러운 `찍어서` 는
"동사 '찍어다'에 해당하는 함수가 없습니다" 오류다. 자연어를 표방하는 표면이 실제로는 기계적
규칙이어서, 자연스럽게 쓰면 오히려 틀린다. 이 틈은 문법이 자연어에 가까울수록 커진다.

### 2.6 한 함수가 호출부에서 여러 모습으로 나타난다

`세기` 로 정의한 함수는 호출부에서 `세기(4)`, `1을 세다`, `2를 세고` 로 나타난다. 네 가지 표면형이
모두 같은 함수를 부른다. 정의 이름으로 텍스트 검색을 하면 동사형 호출부를 찾지 못한다. 이것은
다른 언어에 없는 도구 문제다. 편집기 지원이나 참조 찾기를 만들 때 반드시 다뤄야 한다.

## 3. 다른 언어와의 대조

| 문제 | C·자바 등에서 | 글에서 |
|---|---|---|
| 인자 순서 혼동 (substring/substr, assertEquals) | 흔한 버그. 편집기 힌트로 완화 | 역할이 다르면 불가능, 같으면 그대로 (1.1) |
| 인자 레이블 | 언어에 덧붙인 장치, 이름을 하나씩 붙인다 | 문법에 내재, 역할 어휘 다섯 개 |
| 수신자와 인자의 비대칭 (`x.f(y)` 대 `f(x,y)`) | 확장 메서드·UFCS 로 우회 | 개념 자체가 없다 |
| 값을 만드는 호출의 표기 | 하나 | 괄호형과 동사형 두 가지 (1.2) |
| 식별자와 문법 표지의 경계 | 공백·기호로 명확 | 붙여 쓰는 조사와 겹친다 (2.1) |
| 예약어와 일상어의 충돌 | 드물다 | 잦다 (`결과`→`결괏값` 개명 사례) |
| 정의 이름으로 호출부 찾기 | 텍스트 검색으로 충분 | 활용형 때문에 부족 (2.6) |

요약하면 **호출 지점의 안전성은 조건부로 낫고, 이름과 문법 표지의 경계는 무조건 나쁘다.**
전자는 한국어가 격을 표지로 드러내기 때문이고, 후자는 그 표지가 낱말에 붙어 쓰이기 때문이다.
같은 성질의 앞뒷면이다.

## 4. 개발 제안

우선순위 순이다.

1. **매개변수 이름 훼손을 드러낸다.** 조사 없는 매개변수의 이름이 조사 음절로 끝나면 오류로 잡고,
   "이름의 일부입니까, 역할 조사입니까"를 묻는 메시지를 낸다. 지금은 조용히 훼손되거나 엉뚱한 줄에서
   오류가 난다. 더 강한 안은 **모든 매개변수에 역할 조사를 필수로 하는 것**이다. 표준 라이브러리와
   컴파일러가 이미 그렇게 쓰고 있으므로 실제 비용은 작다. 설계 결정으로 올릴 값어치가 있다.
2. **동사 후보가 둘 이상이면 오류로 잡는다.** 조용한 우선순위를 없앤다.
3. **`의`로 끝나는 이름 금지를 다시 본다.** 멤버 접근의 `의` 를 앞말과 띄어 쓰게 하거나, 선언된
   이름을 먼저 찾는 방식으로 풀 수 있는지 검토한다.
4. **활용형을 넓히거나 명확히 막는다.** `찍어서` 를 받아들이든지, 받아들이지 못한다는 것을 오류
   메시지에서 분명히 말한다. 지금 메시지는 존재하지 않는 함수를 찾았다고만 한다.
5. **동사 활용형을 아는 검색 도구.** 정의 이름으로 모든 호출부를 찾는 기능. 컴파일러가 이미 대응
   규칙을 알고 있으므로 덤프 형태로 내보내면 편집기가 쓸 수 있다.
6. **변환식과 조사의 충돌을 명세와 오류 메시지에 명시한다.** 괄호로 푼다는 것을 안내한다.

이 목록은 최적화보다 앞선다. 최적화는 이미 있는 프로그램을 빠르게 하지만, 위 항목들은 사람이 글로
프로그램을 쓸 때 겪는 첫 좌절을 없앤다. 그리고 여기서 나온 결론은 글이라는 언어의 정체성에 직접
닿아 있다. 조사를 역할 표지로 쓴다는 선택이 최대의 강점과 최대의 약점을 동시에 만들었다는 것이다.
