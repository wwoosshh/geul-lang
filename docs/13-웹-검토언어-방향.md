# 웹 프론트엔드 검토를 위한 글의 연구 방향

2026-09-08에 정한 방향, 2026-09-09 구현 상태 갱신. 사용자가 웹 개발 언어를 첫 대상으로 정하자는 방향을 제시했고, 이를 TypeScript·React부터 시작하는 개발 범위로 구체화한다. 이 문서는 연구 우선순위다. **TypeScript 식·JSX 속성 추출, 제한된 여러 모듈 순수 함수 해석의 첫 구현이 추가됐다. 실제 React 앱 전체의 동작 재구성은 아직 미구현이다.** 구체적인 계약과 재현 명령은 [웹 구현 명세](../web-review/README.md), C 실험 계약은 [G0 명세](12-검토언어-G0.md)에 남는다.

> 방향 검토 후 실행 우선순위: 새 조각 모드 확장은 동결한다. 돌아가기 버튼과 모바일 필터를 조건·변경 영향·예외·원본 근거 단위로 제시하고, 표현 예행 이후 행동 연결의 공백을 채운다. 현재 실행 계약은 [web-review/CONTRACTS.md](../web-review/CONTRACTS.md), 근거는 [증거 색인](../web-review/EVIDENCE.md), 예행 계획은 [행동 표현 예행](../web-review/evaluation/behavior-rehearsal.md)에 분리했다. 아래 누적 구현 이력은 과거 체크포인트이며 현재 작업 순서를 대신하지 않는다.

## 목적과 대상

**글은 TypeScript·React 웹 프론트엔드의 여러 파일에 흩어진 동작 조건을 실행 가능한 표현으로 재구성하고, 사람이 코드 변경의 영향과 예외를 검토하도록 돕는 언어를 목표로 한다.**

첫 사용자는 AI와 함께 TypeScript·React 서비스를 개발하고 변경을 검토하는 개발자다. 한국어를 첫 표시 언어로 삼되, 한국어라는 사실만으로 이해도가 개선된다고 가정하지 않는다. 사람이 판단할 단위는 함수 하나나 파일 하나가 아니라 ‘언제 버튼을 사용할 수 있는가’, ‘언제 오류가 나타나는가’ 같은 화면의 행동이다.

| 구분 | 결정 |
|---|---|
| 첫 입력 언어 | TypeScript `.ts`, React가 사용하는 `.tsx` |
| 첫 프레임워크 문맥 | React 함수 컴포넌트와 해당 동작이 의존하는 지역 모듈 |
| 먼저 해석할 것 | 입력 검증 조건, 조건부 JSX 생성, 기본 HTML 요소에 전달되는 `disabled` 등의 동작 속성 |
| 다음에 해석할 것 | 이벤트 처리, 상태 전이, 요청의 성공·실패와 취소·응답 순서 |
| JavaScript | 같은 실행 의미를 갖는 지원 부분부터 추후 확장. 타입이 없거나 동적인 코드를 자동 지원한다고 하지 않는다 |
| Next.js 등 | 해당 프로젝트의 클라이언트 코드도 사례 후보다. 서버 컴포넌트·서버 액션·라우팅·SSR·hydration은 별도 의미 경계로 식별한다 |
| 기존 C 경로 | 재현 가능한 G0 실험과 회귀 검사를 유지한다. C 범위 확장·Java 프런트엔드는 현재 우선순위에서 제외한다 |
| 장기 왕복 | 지원된 글을 수정하고 TypeScript로 생성해 수정된 의미와 비교한다. 원본 구조를 보존하는 편집 동기화는 이후 단계다 |

선정 근거로 GitHub Octoverse 2025는 2025년 8월 기여자 수 기준 TypeScript가 1위가 됐다고 보고한다. 이는 GitHub 활동의 지표이며, AI 개발 전체가 프론트엔드 중심이라는 증명이나 글에 대한 수요 증거는 아니다. React는 이번 연구의 첫 통합 대상으로 선택한 것이며 모든 프레임워크를 동시에 지원하지 않는다. ## 첫 결과물: 화면 동작의 조건과 변경 영향

아래는 개발 목표를 설명하기 위한 예시이며 확정 문법이나 현재 출력이 아니다.

```text
문서 삭제 버튼의 disabled 속성은 다음 조건을 모두 만족할 때 거짓이다.
  사용자가 로그인했다.
  사용자 계정이 정지되지 않았다.
  사용자가 관리자이거나 문서 소유자다.
  문서가 잠겨 있지 않다.

변경 후 관리자 예외가 제거됐다.
로그인했고 정지되지 않은 관리자 중 문서 소유자가 아닌 사용자는,
잠기지 않은 문서에서 이전과 달리 버튼의 disabled 속성이 참이 된다.
```

기본 HTML 버튼의 속성을 확인한 것과 서버의 삭제 허가를 확인한 것은 구별한다. 사용자 정의 Button 컴포넌트가 속성을 다른 뜻으로 사용하거나 덮어쓰면 구현을 따라가거나 미지원으로 남긴다. CSS, 상위 요소, 이벤트 처리기까지 분석하지 않았다면 실제 클릭 가능성 전체를 보장하지 않는다. 단순한 ‘화면에 표시한다’는 설명도 먼저 조건부 JSX 생성 사실과 구분한다.

각 문장에는 원본 위치와 계산에 필요한 의존성을 연결한다. 용어 변경은 원본 이름과 사용자 제공 대응을 기록한다. 미지원 의존성은 원본 위치와 함께 표시하며, 누락한 조건을 감춘 채 완전한 행동을 설명했다고 하지 않는다.

첫 시연은 실제 컴포넌트와 다른 파일의 조건 함수가 연결된 변경으로 한다. 변환을 쉽게 하려고 기존 소스를 G0용 상수 함수로 고쳐 놓는 것은 실제 사례 성공으로 계산하지 않는다.

## 의미 보존의 경계

TypeScript 분석에는 TypeScript 컴파일러의 구문·심볼·모듈 정보를 사용하는 경로를 우선 검토한다. 정규식으로 프로젝트를 읽거나 타입 이름만으로 실행 결과를 추측하지 않는다. `tsconfig`, 모듈 해석, 관련 의존성 버전과 원본 버전을 검사 대상에 결합한다.

TypeScript의 타입 표기는 실행 시 제거된다. 따라서 타입 검사 통과가 입력의 런타임 유효성을 보증하지 않는다. JavaScript의 `number`, `null`·`undefined`, truthiness, 단락 평가와 평가 순서를 보존해야 한다. C의 int32 구간 모델을 그대로 적용하지 않는다. [TypeScript 타입 제거 설명](https://www.typescriptlang.org/docs/handbook/2/basic-types.html#erased-types)

초기 표현력은 불리언·리터럴 문자열의 유한 집합·단순 레코드와 순수 조건식에서 시작한다. 숫자가 필요한 경우 연산·입력 범위를 별도 명세로 정하고 검사한다. 정수만 허용하는 계약을 쓰면 `NaN`·무한대·소수 등 제외한 입력을 명시하고 실제 경계의 검사 근거를 공개한다. 타입 단언만으로 그 전제를 충족했다고 하지 않는다.

객체 읽기의 getter·Proxy, 변경 가능한 공유 상태, 모듈 초기화 효과, 동적 호출 등은 별도 모델 없이 순수한 값 읽기로 바꿀 수 없다. 여러 파일의 선언을 찾는 것과 실행 의미를 확인하는 것은 다른 단계다. 첫 분석 경로는 대상 프로젝트 코드를 가져와 실행하는 방식으로 의존성을 해결하지 않는다.

| 단계 | 비교하는 관찰 | 보장하지 않는 것 |
|---|---|---|
| 첫 단계 | 주어진 props·상태 값에서의 조건 결과, 생성할 JSX 분기와 명시한 기본 요소 속성 | 그 상태의 도달 가능성, 실제 배치·가림·색상·접근성 전체, 서버 권한 |
| 상태 단계 | 명시한 이벤트 모델에서의 상태 전이와 그에 따른 표시 변화 | 모델 밖의 이벤트·렌더링 스케줄 |
| 효과 단계 | 명시한 환경에서의 요청 대상·인자·순서와 성공·실패 이후 전이 | 외부 서비스 내부의 정확성과 임의의 네트워크 상황 |

React 상태는 렌더 시점의 스냅샷이라는 실행 문맥을 갖고, 네트워크 응답 순서가 요청 순서와 다를 수 있다. 비동기 처리와 Effect를 하나의 순차 함수로 평탄화해 보장하지 않는다. [React 상태 스냅샷](https://react.dev/learn/state-as-a-snapshot), [Effect와 응답 순서](https://react.dev/reference/react/useEffect)

결과는 모델 전체 입력 비교, 제한된 실행 비교, 미확인, 미지원으로 구분한다. 모든 관련 의존성을 처리하지 못한 행동을 전체 동등성 성공으로 세지 않는다. 변경 설명의 ‘나머지는 동일’은 정의한 관찰 범위의 나머지를 확인했을 때만 사용한다. 기획 의도나 좋은 UX라는 판단은 사람이 한다.

## 개발 순서와 평가

1. **실제 사례와 의미 계약.** 서로 다른 공개 TypeScript·React 프로젝트 최소 3개에서 동작 변경 10~20개를 먼저 선정한다. 최소 5개는 여러 파일 의존성을 포함하도록 한다. 원본 커밋·사용 조건·기대 영향·미지원 요소를 기록한다. 수작업 변경은 실제 PR과 구분한다. 참가자 모집과 검토 업무 인터뷰를 시작한다.
2. **TypeScript 의미 핵심.** 복수 입력 조건과 순수 함수 호출을 표현할 별도 IR·독립 실행기·비교 경로를 만든다. G0의 실패 처리·버전 결합 원칙은 재사용하되 JavaScript 의미의 정확성은 새로 확인한다.
3. **React 동작 연결.** 원본 프로젝트 문맥에서 TSX의 조건과 의존 함수를 연결한다. 글과 원본 위치를 함께 제시하고 변경 전후에 영향을 받는 조건을 비교한다. 파싱 성공과 동작 해석 성공을 따로 센다.
4. **사람 평가.** 파일럿 6~8명을 목표로 원본+AI, 글+원본 연결, 결정표, 단순 한국어화 조건을 비교한다. 정보 접근과 AI 지원을 맞추고, 변경 탐지 정확도·시간·탐색 횟수·잘못된 확신을 측정한다. 모집 전까지 평가가 완료됐다고 하지 않는다.
5. **확장 판단.** 실제 사례에서 검토 개선이 보이면 이벤트·상태·비동기 경계로 확장한다. 글→TypeScript 생성과 원본 편집 동기화는 각각 따로 평가한다.

최초 사례 수집·계약 결정에 약 2주를 배정하는 계획이다. 이후 일정과 성공률 분모는 사례를 분석한 뒤, 평가 결과를 보기 전에 고정한다. 이전 C·Java 연구안의 30~46주·8~12개월 일정을 웹 분석기의 일정으로 승계하지 않는다. 지원 범위를 사후에 줄여 기존 성공률 목표를 달성했다고 하지 않는다.

후보 행동 중 지원 범위에 들어오는 비율, 지원 대상 중 변환 성공률, 사람 검토 개선을 각각 보고한다. 미지원 사례를 제외한 작은 분모만으로 실용성을 주장하지 않는다. 2026-09-09 현재 실제 프로젝트 3개의 변경 12개와 원본·기대 영향 가설을 고정했고, 5개 사례의 여러 파일 연결을 수동 확인한 뒤 원본 설정으로도 재확인했다. 네 식·속성 지점의 유한 비교와 Actual의 원본 함수 본문 하나에 대한 362개 입력 대조를 수행했으며 **전체 행동 검증은 0/12, 사용자 실험은 미실시**다. 함수 본문 실험은 주변 모듈 초기화와 실제 호출 연결을 보증하지 않는다. 이 부분 검사를 최종 검토 과제 평가집의 완성으로 취급하지 않는다.

검토 정확성과 의미 보존은 핵심 조건이다. 기존의 원본 대비 검토 시간 50%, 원본+AI 대비 25% 감소 수치는 장기 목표로 남으며 달성한 성능이 아니다. 파일럿의 진행 기준·오탐과 실패 처리·표본 계획은 실험 전에 별도로 고정한다. 실행 코드의 성능 목표는 생성 경로 평가 시 재산정하며 첫 리프팅 단계의 완료 조건으로 사용하지 않는다.

추가 구현으로 Excalidraw의 조건부 JSX 경로 네 개와 선행 const를 포함한 구간 하나를 검사했다. 총 260개 입력에서 수작업 기대 관찰과 일치하며, 그중 68개는 원본 const 구간을 JSX·번역 함수 대역과 실행해 대조했다. 지역 변수 선언·참조와 부모 LayerUI → 자식 MobileMenu의 속성 연결도 원본 설정에 결합했다. 이는 화면에 표시되는 전체 경로나 실제 React 실행의 동등성을 입증한 수치가 아니다. 다음 연결 단계에서는 구간 사이에 생략된 평가와 시점 차이를 모델 없이 동일시하지 않는 것이 조건이다.

실제 사례가 대부분 미지원이거나, 글을 읽어도 같은 원본 탐색이 필요하거나, 원본+AI·결정표보다 검토가 개선되지 않으면 기능 확대를 멈추고 표현과 분석 단위를 재설계한다. 작은 파일럿에서 차이가 불명확한 경우 효과가 없다는 확정과 구분한다.

이어 같은 모바일 사례에서 변경 전 인라인 JSX와 변경 후 const 저장·두 자식 참조를 같은 객체 전달 관찰로 비교했다. 불리언 대조군과 메뉴·사이드바의 문자열/객체/null 형태를 반영한 부분 스냅샷 각 64개에서 두 변경 조합을 규칙 하나로 묶었다. 원본 구간·중간 객체 변경·nullish 입력을 포함한 400회 실행 대조가 일치했다. 저장값의 내부를 모르는 객체로 투영하며 정상 JSX 생성과 생략한 평가의 정상 완료를 가정한다. 전체 AppState의 유효성·상태 도달과 사람의 이해도는 별도다. 전체 행동 완료는 계속 0/12다.

실제 런타임 대조의 첫 단계로 원본 잠금 파일의 React 19.0.0과 원본 Island·FixedSideContainer를 연결했다. 선택한 MobileMenu 구간의 HTML 버튼 수가 두 입력 도메인에서 384회 대조와 일치했다. 나머지 helper 대역과 생략한 CSS를 명시하며, 부모가 자식을 버리는 경우와 선행 helper가 예외를 내는 경우의 반례도 함께 기록했다. 이것은 조건부 서버 렌더링 실험이며 브라우저·이벤트·전체 앱 의미의 완료가 아니다.

이 발견에 따라 기존 선택과 별도로 원본 12개 커밋의 변경 파일 전체를 고정했다. 사례별 합계 55개 변경 파일 중 기존 선택에 포함된 변경 파일은 26개이고 선택 밖은 29개였다. CSS·다른 UI·서버 코드도 선택 밖에 있으므로 파일 수를 해석 성공률로 쓰지 않는다. 부분 비교에는 해당 분석에서 다루지 않은 변경 파일을 자동 표시한다.

의미 핵심에는 객체 매개변수와 지역 const의 고정 속성 구조 분해를 추가했다. 호출 인수의 선행 평가, 속성 읽기 순서, 별칭, null 오류를 보존하고 기본값·중첩·나머지 속성은 거부한다. 원본 Jitsi 함수 두 개의 532개 입력 대조와 6개 미지원 입력, CLI 재실행을 확인했다. 두 함수 선언은 해당 원본 커밋에서 바뀌지 않았으므로 지원 범위 실험으로만 센다. 웹 단위·CLI 검사 80개와 변경 목록 파서 검사 2개가 통과했고, 전체 행동·사람 검토 성과의 미확인 상태는 유지한다.

Actual에서는 선택한 함수 호출의 반환값을 받는 const·객체 분해 바인딩과 외부 호출 인자의 사용 위치를 심볼로 연결했다. `resolveStartingSettings`의 날짜·잔액 두 값이 다섯 호출의 인자 속성 10곳에 적힌 사실을 확인했다. 함수 본문 실행 결과와 호출 지점의 실제 실행은 별개로 유지하고, 이 색인은 `run`으로 실행하지 못하게 했다. 관련 경계와 CLI 재검사를 포함한 웹 테스트는 85개가 통과했다.

이어 같은 결과 연결에 서비스별 분기 경로 다섯 개와 앞선 계정 미발견 return 구문을 붙였다. `explain --inputs` 결합 보기는 명시한 함수 매개변수로 반환·즉시 바인딩을 계산하고 그 값의 원본 사용 위치를 함께 표시한다. 원래 호출 인수 식의 평가와 요청 실행은 모델에 포함하지 않는다. Actual 원본 함수·결과 선언의 입력 예시 8개를 네이티브 실행과 대조했으며, 객체가 나중에 바뀌는 반례·null 분해·미확인 prototype·콜백 경계·출력 크기 제한을 검사했다. 웹 테스트 96개와 전체 로컬 검증 18개 단계가 통과했다. 새 결합 보기는 기존 사람 평가 자료의 조건을 바꾸지 않으며 전체 행동 0/12, 참가자 0명 상태를 유지한다.

그다음 단계에서는 계산한 문자열 속성 키를 지원하고, `--caller-inputs`로 호출 지점 스냅샷의 원래 인수 식과 함수 본문·결과 바인딩을 하나의 부분 실행으로 연결했다. Actual의 함수 추출 전후를 같은 관찰 변수로 비교하는 경로도 추가했다. 원래 const 세 선언과 원래 함수 호출을 수정 없이 추출하고 122개 입력에서 날짜·잔액 값과 TypeError 여부를 비교했으며, 원본 실행 244회와 일치했다. 이 계산은 구조 변경으로 구별할 수 있지만 기본 설정과 다른 UI 변경의 의미까지 같다고 하지 않는다. 해당 시점의 전체 검증 19개 단계와 핵심 검사 112개가 통과했다.

이후 객체 spread와 단축 속성·덮어쓰기 순서를 지원해, 입력값 0과 amount 속성 생략을 구별하는 실험을 추가했다. 원본 객체 식 8곳과 JSX 속성 4곳의 독립적인 계산을 496회 대조하고, 미지원 입력 24회와 CLI 재실행을 확인했다. 날짜 수정 객체는 없는 amount를 채우지 않고 잔액 수정 객체는 해당 속성을 지정한다. 같은 스냅샷에서 AmountInput.value가 0이라는 사실을 저장된 잔액 0으로 해석하면 안 된다는 차이를 표시한다. 핵심 검사 121개가 통과했다. 실제 이벤트·상태·요청의 연결 실행은 아직 확인하지 않았고, 이 구현은 5단계 확장 완료나 사람 검토 개선의 근거로 세지 않는다.

Actual의 `onRename`은 키 처리 본문의 직접 호출 1곳과 `InputCell.inputProps` 안 객체 속성 참조 1곳에 연결되며, 둘러싼 구문 조건과 앞선 `preventDefault`·`stopPropagation` 문장을 원본 탐색 정보로 보존한다. `renameTag`의 구조 분해 선언과 `useRenameTagMutation()`도 초기화 실행 없이 연결한다. alias·다른 파일·객체 덮어쓰기·React 전달·실제 이벤트는 미확인이다. 117개 원본 callback 입력 대조 결과는 유지됐고 CLI 재검사 8개, 핵심 검사 230개·전체 검증 33개 단계가 엔진 `48dd7a66b83998c2611388d16aa6c82ee80a614aef63d187cc4ad32876b1de70`로 `build/web-review/verification/run-7t1PNd`에서 통과했다. 새 소스 연결을 원본 실행 횟수나 전체 행동 완료에 합치지 않는다.

읽기 보기의 첫 값 성질 기반 규칙은 정상 완료 시 문자열인 식에 한정한다. 문자열 리터럴·표준 trim·typeof·저장된 같은 값·모든 결과 갈래가 문자열인 식의 근거를 기록하고, 이때만 불리언 반전 조건을 ‘빈 문자열인지’로 표현한다. TypeScript 타입 선언·알 수 없는 입력·같은 이름의 다른 저장값으로 근거가 번지지 않는 것을 검사했다. Actual의 `!trimmed`에는 한 규칙이 적용되며 IR 실행 의미는 바꾸지 않았다. 핵심 검사 233개·전체 검증 33개 단계가 엔진 `d4f16ae92132fc4946d27f5febfe9024d3f1f89d21fc4a5acbb7c83816d023b5`로 `build/web-review/verification/run-IfrNpT`에서 통과했다. 이 표현의 사람 검토 개선 여부는 아직 측정하지 않았다.

호출 인수 관찰은 별도 `call-arguments-slice` 모드로 추가했다. 같은 순수 선행 구간의 저장값을 인수 식까지 연결하고 인수를 왼쪽부터 계산하며, 마지막 인수 이후에만 준비 완료를 기록한다. callee 식별자 값 읽기의 순수 정상 완료는 가정이고 실제 호출·반환·인수 간 참조 동일성은 미확인이다. 기존 Actual 원본 기록 117개를 재사용해 준비된 인수 객체 37개·조기 반환 50개·TypeError 30개를 대조했다. 새 원본 실행 117회로 중복 집계하지 않는다. 초기화 전 callee 읽기·호출 불가능한 값·후속 인수 오류도 경계 검사에 포함했다. 핵심 검사 240개·전체 검증 34개 단계가 엔진 `faa3d01b577c961803e7596e24c5512a3f6e767e718d6dd2a7b4ae4c950fe339`로 `build/web-review/verification/run-w4IWoM`에서 통과했다. 실제 이벤트·상태·서버 실행이나 전체 행동 완료로 간주하지 않는다.

표준 원시 문자열 `toLowerCase`를 추가하고 `trim`과 이어진 계산을 실행 순서의 한 문장으로 표시한다. 원본 Excalidraw 색상 입력의 첫 const를 98개 입력에서 전후 196회 실행해 IR과 대조했으며, 64개 결과가 추가 공백 제거로 달라졌다. null·undefined의 TypeError 4회는 이 실행 수에 포함하고 미지원 값 6회·표준 메서드 변경 반례 2회는 따로 센다. 원본과 IR은 같은 Node의 표준 문자열 구현을 사용하므로 유니코드 구현 자체의 독립 검증이나 다른 브라우저의 검증은 아니다. 엔진 해시에 Node·V8·Unicode·ICU·플랫폼·아키텍처를 포함했다. 핵심 검사 246개·전체 검증 35개 단계가 엔진 `8fe23528e1ca66596c76548980e5c23aefb741960a7d884be70c2084f9286a42`로 `build/web-review/verification/run-CKtlEH`에서 통과했다. 정규식·색상 해석 함수·상태·화면·저장은 이 새 계산 구간의 범위 밖이며 전체 행동 0/12·사람 참가자 0명을 유지한다.

원본 파일에서 후보를 찾는 `discover` 진입점을 추가했다. const 문장·명시된 JSX 속성·함수 블록 마지막 직접 호출을 기존 추출기로 검사하며, IR 추출·거부·미검사를 구분한다. 제한된 개수와 작업량 안에서 검사하고 페이지를 이어 갈 수 있다. 고정된 실제 파일 3개에서 후보 264개·소스 범위 256곳을 10페이지로 조사했으며 IR 추출 170개·거부 94개, CLI 재검사 12회가 확인됐다. 정적 JSX와 선행 계산 없는 호출 진입 5개를 포함한 구문 통계이며 원본 실행은 0회다. 소스 선택 결과를 기존 추출 명령으로 다시 읽어 동일한 분석인지 확인했고, 거부 오류의 가상 파일 위치를 원본 위치로 연결했다. 핵심 검사 252개·전체 검증 36개 단계가 엔진 `ef5edb4e2209904054bddbfa6ec0d32653e2af93b8a098a42a16c9f8208326d3`로 `build/web-review/verification/run-OjzBnI`에서 통과했다. 실제 변경 줄과의 연관이나 전체 행동 검증으로 해석하지 않는다.

변경 후보 탐색 `discover-change`은 두 원본과 단일 파일 Git 패치를 대조해 변경 후 전체 파일을 복원하고, 후보 위치·선택 구문·해석한 계산 구간에 변경 행을 연결한다. 거부·미검사 후보는 계산 구간이 미확인임을 `null`로 남기며 전후 후보를 같은 행동으로 자동 대응하지 않는다. 원본 6개·전후 후보 510개를 실제 변경 3개의 고정 Git blob과 대조하고 CLI 재검사 6회를 수행했다. 원본 프로그램 실행은 0회다. 들여쓰기·주석 때문에 호출 행이 선행 계산 구간에 잘못 들어가는 문제를 실패하는 검사로 재현해 고쳤고, Actual 호출 진입은 65~68행, 인수 포함은 65~69행으로 구분했다. 핵심 검사 260개·전체 검증 37개 단계가 엔진 `1663d1f65818d96901f5897cae5ff48a4e9c86835cdd8c9beec404b0ea49ed60`로 `build/web-review/verification/run-06a0Uf`에서 통과했다. 소스 교차는 행동 변화나 동등성의 증거가 아니며 전체 행동 0/12·사람 참가자 0명은 유지한다.

`discover-change --focus changed-lines`는 변경 행과 선택 구문이 교차하는 후보에 검사 한도를 사용한다. 전체 목록의 후보 번호를 유지하며 범위 밖 후보는 미검사로 남긴다. 고정 사례의 전후 후보 510개 중 92개를 대상으로 검사했고, 그 결과가 전체 검사에서 얻은 같은 92개 후보 결과와 정확히 일치했다. 나머지 418개와 간접 의존성의 영향은 미확인이다. 전체·집중 선택을 포함한 CLI 재검사는 12회이며 이 수치로 속도나 사람 검토 성과의 개선을 주장하지 않는다. 핵심 검사 263개·전체 검증 37개 단계가 엔진 `d0fb0e879c14f90d7dd2d8280bca53efdb1b78f225c9c3f978ed449861d0ccea`로 `build/web-review/verification/run-s5b7p9`에서 통과했다.

후보 목록에서 읽기까지 이어지는 `lift-candidate`를 추가했다. 저장한 페이지의 엔진·선택 조건·후보 결과를 현재 원본으로 다시 검사하며, 변경 페이지는 전후 원본과 패치도 복원·대조하고 before·after를 명시해야 한다. 미지원·미검사 후보를 추출 성공으로 바꾸지 않는다. 실제 파일 탐색의 세 후보에서는 기존 명시적 추출 CLI와 같은 결과를 확인했고, 변경 집중 탐색의 세 후보도 재추출해 한국어로 읽었다. 해당 두 검사 도구의 CLI 재검사는 각각 15회·18회이며 원본 실행은 0회다. `anchor-page.json`·`anchor.json`·`anchor-reading.md`로 같은 경로를 재현할 수 있다.

한국어 Markdown 읽기는 연속된 저장과 다음 계산을 같은 깊이로 표시하고, 조건의 각 갈래 안에 해당하는 후속 계산을 묶는다. 초기화 식 안의 분기·미사용 초기화·예외 순서는 그대로 남기며 조기 반환 갈래에 인수 계산 안내가 붙던 혼동을 수정했다. 관련 실패를 먼저 재현한 뒤 전체 읽기 트리와 원본 연결이 유지되는지 검사했다. 핵심 검사 271개·원본 두 앱 실행을 포함한 전체 검증 37개 단계가 엔진 `67f5c1236450a3532af186965d75ce4e0c4422d410e65a9e156bfe9d597ff751`로 `build/web-review/verification/run-pO8zCU`에서 통과했다. 검토 작업대의 JSON 트리 표시와 사람 평가 조건은 이 Markdown 배치로 교체하지 않았다. 전체 행동 0/12·사람 참가자 0명 상태를 유지한다.

## 선행 연구와 비교할 주장

검증할 가설은 ‘실제 프론트엔드의 분산된 동작을 의미 보존 근거와 함께 재구성하면 기존 검토 조건보다 영향과 예외를 쉽게 이해할 수 있다’다. 새로운 패러다임을 이미 만들었다고 주장하지 않는다.

[VLP](https://arxiv.org/html/2607.02333v1)는 사람이 읽는 중간 표현과 검토·수정·검증을 이미 결합한다. [SemanticDiff](https://semanticdiff.com/docs/what-is-semanticdiff/)는 언어를 인식하는 변경 보기를 제공한다. [Meticulous](https://app.meticulous.ai/docs/onboarding-guide)는 사용자 세션을 PR 검토에 연결한다. 이들과의 차이는 대상 언어 이름만으로 성립하지 않으며, 원본에서 얻는 표현의 충실도·처리 범위·검토 성과로 평가한다.

이 문서가 새 입력 대상과 우선순위의 기준이다. 기존 네이티브 `.gl` 호환 계약과 C G0의 구현 범위는 각각 유지한다.
