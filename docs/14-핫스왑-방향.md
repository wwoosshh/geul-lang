# 핫 코드 스왑 방향 — 실행 중 본문 교체

2026-09-20. 장인의 틀로 시작하는 방향이다. 시장 승부가 아니라, 글이 자기 백엔드를 쥐고 있어야만 지을 수 있는 능력을 짓는다. review-language 를 접으며 남긴 방법([[../연구-중단-기록-2026-09-09.md]])을 이 방향에도 그대로 적용한다.

## "왜 언어인가"는 이 방향의 질문이 아니다

그 질문은 새 문제에 새 언어를 만들지 고를 때(review-language 상황)의 시장 질문이었다. 여기서는 다르다. **글은 이미 짓고 있는 언어이고, 핫스왑은 그 언어에 더하는 기능이다.** "언어냐 라이브러리냐"를 고르는 자리가 아니다. 그러므로 정당화는 묻지 않는다.

허탈 기록([[../연구-중단-기록-2026-09-09.md]])에서 이 방향으로 넘어오는 규율은 하나뿐이다: **범위·데모·안 하는 것을 정직하게 못박는다.** 아래 "v0 범위"와 "안 하는 것"이 그 자리다. 시작 조건은 "왜 언어인가"의 답이 아니라, v0 데모가 무엇이면 성공인가를 정하는 것이다.

(참고: 글의 타입 시스템은 계산된 주소의 호출을 막는다 — 아래 확인 사실 2. 그래서 이 기능은 어차피 userland 라이브러리로는 못 만들고 컴파일러·런타임에 들어간다. 이건 정당화가 아니라 구현 위치의 사실이다.)

## 목표를 정확히

HTML 개발 서버의 마법은 "빌드가 없다"가 아니다(Vite 도 뒤에서 변환한다). **실행 중인 프로그램의 상태를 죽이지 않고 코드를 갈아 끼우는 것**이다. 런타임이 모듈 그래프와 상태를 소유해서 가능하다.

그러므로 목표는 "빌드 없이"가 아니라 **네이티브 대상의, 프로세스 내부, 협조적, 상태 보존 핫 코드 스왑**이다. "빌드 없이"라고 말하지 않는다.

## 글이 이미 가진 것 (왜 글에 다룰 만한가)

- **IAT 는 이미 우회 테이블이다.** 외부 함수 호출은 `call [rip+disp]`(`call_iat`) — OS 로더가 채우는 함수 포인터 테이블을 거친다. 핫스왑이 필요로 하는 우회 구조를 글은 외부 함수에 대해 이미 쓴다. (`ref/geul/codegen.py` `gen_call`)
- **레지스터 간접 호출도 이미 낸다.** 함수 포인터 값 호출은 `call_reg`. 내부 함수만 `call rel32`(`call_label`) 직접 호출이다.
- **백엔드를 전부 쥐고 있다.** 렉서→x64 코드생성→PE 작성까지 자기 것이라, 내부 호출을 테이블로 돌리는 변경이 가능하다. LLVM 위였다면 못 한다.
- **런타임이 kernel32 만 쓴다.** VirtualAlloc·VirtualProtect 를 더해도 이 불변식이 유지된다.
- **함수 포인터를 구조체 필드로 이미 쓴다.** 백업 GUI 의 `[공허 참조, 정수, 정수, 정수 -> 정수] 창처리`(Win32 콜백). 우회의 원시 재료가 있다.

## 확인한 사실 (2026-09-20, 이 PC)

1. **글은 이 PC 에서 컴파일·실행된다** — Python 참조 구현(`ref/geulc.py`), C 컴파일러 불필요. 글이 PE 를 직접 낸다.
2. **글은 임의 주소를 함수로 부르는 것을 거부한다.** `[-> 정수] f = p.`(p 는 VirtualAlloc 결과) → `오류: '공허 참조' 타입을 '[ -> 정수]'에 넣을 수 없습니다 — 호환되지 않는 타입`. 문법 명세도 함수 타입으로의 변환을 금한다(03 명세). ⇒ **핫스왑은 첫 이정표부터 컴파일러 작업이다.** userland 라이브러리로 우회 불가. (탐침: `research/hotswap/탐침-대입.gl`)
3. **협조적 핫스왑이 이 머신의 보안 SW 아래에서 물리적으로 된다.** VirtualAlloc RW → 본문 기록 → RX 로 좁힘(W^X) → 포인터 호출 → RW 로 되돌려 본문 교체 → RX → 재호출. `v1=111, v2=222` 로 교체가 반영됐다. 세션을 죽이던 보안 SW 가 이 협조적 방식(주입 없음, 프롤로그 덮어쓰기 없음)은 막지 않았다. (탐침: `research/hotswap/viability.c`)

## 난이도 사다리 (글 매핑)

| 단계 | 글에서 | v0 |
|---|---|---|
| (a) 함수 **본문** 교체(시그니처 동일) | 내부 호출을 글 함수 테이블로 우회 + 런타임 교체 | **여기** |
| (b) 함수 추가·제거 | 테이블 항목 추가 | 이후 |
| (c) 함수 **시그니처** 변경 | 호출부도 갱신 | 이후 |
| (d) **레코드/묶음 레이아웃 변경(살아있는 값이 있는데)** | 힙의 옛 값은 옛 레이아웃 → 상태 마이그레이션 | **벽** |
| (e) 전역 초기화·살아있는 값의 타입 변경 | — | 최난 |

어려움은 문법이 아니라 실행·메모리 모델과 "상태를 누가 소유하는가"에 있다. C/Java 가 "언어 자체로" 못 한 것도 ABI 가 주소·레이아웃을 못박기 때문이지 문법 때문이 아니다.

## v0 범위 — 하는 것과 안 하는 것

**하는 것:** 시그니처가 같은 함수 하나의 본문을, 실행 중인 글 프로그램이 재시작 없이 새 본문으로 바꿔 부른다. 전역·힙 상태는 그대로 살아 있다. 바이너리·행동 증거로 확인한다.

**안 하는 것(이름 붙여 못박는다):**
- 레코드/묶음 레이아웃 변경 → v0 은 **재시작(외부 상태 보존)**으로 처리한다. 살아있는 값의 마이그레이션은 안 한다.
- 함수 시그니처 변경, 함수 추가·제거.
- 다중 스레드 안전 지점(v0 은 단일 스레드, 명시적 교체 지점).
- 남의 프로세스 주입, 함수 프롤로그 후킹 — 설계상 영구히 안 한다.
- "빌드가 사라진다"는 주장. v0 은 바뀐 함수를 다시 컴파일한다. 사라지는 건 **재시작과 상태 손실**이다.

## 협조적 설계 (주입 아님)

호출이 **글 함수 테이블**(글판 IAT)을 거친다. 런타임이 안전 지점에서 항목을 갈아 끼운다. VirtualProtect 로 W^X 를 지킨다(쓸 때 RW, 실행 때 RX, 동시 부여 없음). 남의 프로세스에 쓰지 않고, 프롤로그를 덮지 않는다. 이 선택은 (1) 더 깨끗한 설계이고 (2) Erlang·HMR 이 실제로 사는 곳이며 (3) 보안 스캐너 문제를 피한다 — 세 이유가 같은 방향이다.

## 검증

- **자체호스팅 고정점을 깨지 않는다.** 내부 호출을 테이블로 돌리는 코드생성 변경은 글로 쓴 컴파일러가 여전히 바이트 동일한 결과를 내야 한다. 못 지키면 옵션 뒤에 둔다. (`python build.py selfhost 컴파일러`)
- **바이너리·행동 증거.** 데모 프로그램이 교체 전후로 다른 값을 찍는 것을, 재시작 없이 보인다. 기존 바이트 동일·고정점 규율과 같은 종류의 증거다.
- 임의 표본이 아니라 관찰 가능한 상태 변화로 확인한다.

## 실사용 테스트 — 생명 게임 (2026-09-21)

방향 문서의 "실사용이 먼저" 원칙대로, 진짜 edit→rebuild→reload 루프를 콘솔 생명 게임으로 시험했다(`research/hotswap/생명/`). 핵심: `교체`의 진짜 가치는 "빌드 때 없던 새 코드를 실행 중 적용"이므로, **규칙 함수를 따로 컴파일해 넣어야** 한다.

이를 위해 참조 구현에 **`--조각`**(`--fragment`)을 더했다: 순수 잎 함수(다른 함수 호출·전역·문자열 없음) 하나를 위치 독립 원시 기계코드 `.bin` 으로 낸다. 외부 참조가 남으면 거부한다(위치 독립 보장). 생명 게임 규칙 `[정수 살아있나를 정수 이웃수를 규칙]는 -> 정수` 는 순수 잎이라 이에 딱 맞는다.

호스트(`생명.gl`, `--핫스왑`)는 격자·세대를 쥐고, 규칙을 함수 테이블로 부르며, `규칙.bin` 의 수정 시각을 폴링해 바뀌면 VirtualAlloc RX 에 적재하고 `교체(규칙, 새주소)` 한다 — 새 컴파일러 없이 기존 kernel32 extern·표준 파일 함수로.

**결과(성공):** 실행 중 `규칙.bin` 을 Conway → "이웃 하나라도 있으면 산다"로 재빌드하자, 호스트가 감지해 교체했다. **격자 패턴은 그대로 이어지고 규칙만 바뀌었다** — 살아있는 칸이 교체 순간부터 10→44→92→149 로 번졌다(같은 두 무리가 그 자리에서 성장). 재시작·상태손실 없음. HTML 개발 서버의 그 감각이 네이티브 글에서 성립.

**실사용이 드러낸 것(다음 개선점):**
- **`--조각` self 미러.** 가치가 확인됐으니 글로 쓴 컴파일러에도 넣어 릴리스 `geulc` 로도 되게 한다.
- **잎 함수 제약.** 규칙이 헬퍼를 부르거나 전역·문자열을 쓰면 `--조각` 이 거부한다. 그런 리로드 단위는 DLL(+base 재배치) 이 필요 — 벽(d) 이후의 별도 방향.
- **트리거 지연.** mtime 폴링은 Windows 의 last-write-time 지연 탓에 재빌드 후 감지까지 수초가 걸렸다(핫스왑 자체는 즉시). 더 나은 트리거(내용 해시·명시 신호·디렉터리 변경 알림)가 개발 경험 개선점.

## 방법 (허탈 기록의 세 교훈)

- **언어여야 하는 이유를 처음에 묻지 않는다(이 방향에선).** → 위 "왜 언어인가는 이 방향의 질문이 아니다". 글을 짓는 중이므로 정당화가 아니라 범위·데모를 못박는다.
- **자산에서 출발하지 않는다.** → 살아남는 건 "글이라는 한국어 언어에 핫리로드가 붙는다"가 아니다. SOV·조사는 핫스왑에 무관하다. 쓸모 있는 자산은 **백엔드 소유**이고, 그건 *만드는* 것을 가능하게 하는 조건이지 시장 차별점이 아니다.
- **구현보다 사례와 사람이 먼저다.** → 장인의 틀에서 사용자는 당신 자신이다. 그래도 데모 목표(무엇이 실행 중 바뀌면 성공인가)를 짓기 전에 정한다.
