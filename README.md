# 글 (geul) — 한국어 문법으로 쓰는 자체호스팅 시스템 언어

**글은 한국어 어순(SOV)과 조사(을/를/에/에서/로)를 문법으로 삼는 시스템 프로그래밍 언어다.** 글로 쓴 컴파일러가 자기 자신을 컴파일해 참조 구현과 **바이트가 같은** Windows x64 실행 파일을 만든다. C 컴파일러·링커·런타임 없이 기계어와 PE 실행 파일을 직접 낸다. 만들어진 실행 파일은 Windows에 늘 있는 `kernel32.dll`과 `shell32.dll`(명령줄 인자 분리 하나)만 임포트한다.

한 사람이 AI 코딩 에이전트와 함께 설계·구현·검증했다(2026-09) — 무엇을 어떻게 나눴는지는 [만든 방법](#만든-방법)에 있다. 2세대 1.2에서 **완성**이며(1.2.1은 명세·테스트를 맞춘 고침), 스스로 "연구·예술 프로젝트"로 분류한다 — 이유는 아래 [상태](#상태와-분류)에 있다.

```
[시작하기]는 -> 정수 {
    "안녕, 글!\n"을 쓰다.
    반환 0.
}
```

## 글의 본질 — 조사가 인자의 역할을 정한다

한국어는 어순이 아니라 조사로 역할을 표시한다. "원본**을** 대상**에** 복사하다"에서 무엇이 원본이고 무엇이 대상인지는 자리가 아니라 `을`과 `에`가 정한다. 글은 이것을 그대로 함수 호출 규칙으로 삼는다.

```
[문자열 원본을 문자열 대상에 복사]는 -> 정수 { ... }

원본을 대상에 복사하다.          (* 한국어 문장처럼 — 동사형 호출 *)
복사(원본 을, 대상 에).           (* 괄호 호출도 조사를 쓴다 *)
```

매개변수 선언 `[문자열 원본을 문자열 대상에 복사]`가 각 자리의 조사를 정하고, 호출부의 인자는 **위치가 아니라 조사로** 매개변수에 대응된다. 함수 이름은 명사형(`복사`), 부를 때는 동사형(`복사하다`)이다.

이 설계의 대가는 **안전성**이다. 영어 어순 언어에서 `copy(dst, src)`는 자리를 바꿔 써도 조용히 컴파일되고 데이터가 날아간다. 글에서는 같은 타입의 인자가 역할이 다른데 조사를 안 붙이면 컴파일러가 거부한다(설계 결정 D-30):

```
오류: '복사' 호출에서 두 인자를 바꿔 써도 컴파일됩니다: '원본'(을/를), '대상'(에)
      — 둘 중 하나에 역할 조사를 붙여 구별하세요
```

문법에 격이 있어서만 가능한 검사이고, 글로 쓴 첫 실제 도구(백업 프로그램)에서 원본↔대상 실수를 컴파일 시점에 막는 것으로 증명했다. 이것이 "한국어로**도** 된다"가 아니라 "한국어**라서** 되는 것"이다.

## 왜 기술적으로 의미 있는가

- **자체호스팅 고정점.** 글로 쓴 컴파일러(9,353줄)가 자기 자신을 컴파일한다. 참조 구현(파이썬)이 만든 컴파일러 → 그것이 만든 컴파일러 → 그것이 만든 컴파일러, 세 세대의 바이트가 같다. 두 독립 구현이 202개 테스트 프로그램 전부에서 같은 토큰·구문 트리·IR·기계어(부정 테스트는 같은 오류 줄)를 낸다.
- **바닥부터 직접.** 어휘 분석부터 x86-64 인코딩·레지스터 할당·PE32+ 기록까지 외부 도구가 없다. C 런타임도 없다 — 힙·문자열·서식 출력·종료·명령줄·예외 처리를 kernel32 위에 글로 썼다(명령줄을 인자로 쪼개는 `CommandLineToArgvW` 하나만 shell32).
- **재현 가능한 빌드.** 타임스탬프 0, 고정 이미지 베이스, 결정적 문자열 풀. 같은 소스는 언제나 같은 바이트다. 저장소를 다른 경로로 옮겨도 컴파일러 exe가 바이트 동일하다.
- **실행 중 함수 교체.** `--핫스왑`이면 내부 호출이 함수 테이블을 거치고 `교체(함수, 새주소)`가 슬롯을 바꾼다 — 실행 중인 프로그램의 상태를 살린 채 코드만 갈린다. 생명 게임의 살아있는 패턴이 규칙만 바뀐 채 이어지는 것을 확인했다.
- **Windows 상호운용.** 임의 DLL의 함수를 한국어 이름으로 선언해 부르고, Windows가 글 함수를 되부른다(창 프로그램의 콜백). 백업 도구는 CLI와 Win32 GUI 둘 다 글로 썼다.

## 어떻게 작동하는가

```
소스(.gl)
  → 어휘 분석    한글 단어 끝에서 조사를 떼고, 붙여 쓴 '('는 호출로 읽는다
  → 구문 분석    SOV 절 → 조사 붙은 인자 목록, 동사형 호출, 범위 반복, 식 보간
  → 의미 분석    이름·타입·제네릭(단형화)·암시/명시 변환·D-30 방향 안전성 검사
  → 타입 IR      비SSA, 타입 부착. 경계 검사·결과 전파가 여기서 명시적 명령이 된다
  → 인라인       작은 함수(12명령 이하)를 한 겹 편다
  → 코드 생성    핍홀 분석, 선형 스캔 레지스터 할당(정수 7개·XMM 10개), Win64 호출 규약
  → x86-64      REX/ModRM/SIB를 직접 인코딩, RIP 상대 고정
  → PE32+       .text / .rdata(문자열·임포트 테이블) / .data, 시작 코드도 IR로 생성
```

참조 구현(`ref/`, 파이썬 6,858줄)이 명세를 그대로 구현한 영구 부트스트랩이고, 자체 컴파일러(`self/`)가 단계마다 같은 구조로 이를 따른다. 언어를 키울 때는 두 구현을 함께 고치고, 토큰·구문·IR 덤프와 실행 파일 바이트를 교차 비교해 갈라짐을 잡는다. 자세한 원리는 [작동 원리](docs/16-작동-원리.md).

## 언어 기능

묶음(구조체)·합침·나열, 참조와 색인 역참조(`p[0]`), 함수 포인터와 묶음 안의 함수 필드, 제네릭(단형화), 조각 `T[]`(경계 검사), 결과 타입 `T 결과`(오류 전파 `시도`/`혹은`), 사전·목록·동적배열·정렬·문자열·파일·디렉터리·시간 표준 라이브러리(kernel32 위에 글로), 범위 반복 `(정수 i는 0부터 n 전까지)`, 식 보간 `"{a + b}"`, 외부 DLL 선언, 창 프로그램(`--창`), 실행 중 함수 교체(`--핫스왑`, `교체`).

원칙은 [헌장](docs/00-헌장.md)에 있다: 오류만 있고 경고는 없다, 조용한 실패가 없다, 문서에만 있는 문법이 없다, 고정 풀은 검사한다.

## 만든 방법

이 저장소의 커밋은 거의 전부 AI 코딩 에이전트(Claude)와 함께 썼다. 각 커밋 끝의 `Co-Authored-By` 줄이 그 기록이다 — 1세대 113개 전부, 2세대는 1.2.0까지 88개 중 86개. 2세대가 첫 설계 문서(2026-09-03 08:24)에서 자체호스팅 고정점(같은 날 11:13)까지 세 시간이 안 걸린 것도 그래서다. 그러니 이 저장소가 보여 주는 것은 "컴파일러를 손으로 짰다"가 아니다.

사람이 정하고 책임진 것은 둘이다.

- **무엇을 만들고 언제 멈출지.** 1세대를 감사 결과에 따라 버리고 다시 지은 것, 헌장과 설계 결정 D-01~D-47의 채택, 세 번의 방향 중단과 완성 선언.
- **생성된 코드가 조용히 틀릴 수 없는 구조.** 명세를 먼저 쓰고, 독립된 두 구현(파이썬 참조 구현과 글로 쓴 컴파일러)이 토큰·구문·IR·기계어 바이트까지 서로를 대조하고, 부정 테스트가 오류의 줄·열·문구를 고정하고, 문서 예제가 빌드에서 실행된다. 코드는 누가 썼든 이 그물을 통과해야 들어온다.

그물에 구멍이 있으면 그 자리에서 결함이 산다. 1.2.0의 핫스왑 기능은 테스트 러너가 컴파일러 옵션을 넘기지 못해 긍정 테스트 없이 들어갔고, 1.2.1에서 그 테스트를 채우자 잠복 결함 넷이 나왔다([D-46](docs/02-설계결정-기록.md)). 위의 검증 결과는 누가 썼는지와 무관하게 `python build.py` 로 다시 돌려 확인할 수 있다.

## 상태와 분류

**1.2에서 완성이다.** 문법과 표준 라이브러리는 [호환 약속](docs/11-호환-약속.md)으로 얼려 있고, 더 만들지 않는다. 1.2.1(2026-10-08)은 언어를 바꾸지 않는 고침이다 — 1.2.0의 기능(`교체`, `--핫스왑`)이 헌장이 정한 완료 조건(명세·긍정/부정 테스트)에 못 미쳤던 것을 채웠고, 그 과정에서 드러난 잠복 결함 넷을 고쳤다([D-46](docs/02-설계결정-기록.md)).

이 프로젝트는 스스로를 **연구·예술 프로젝트**로 분류한다. 세 번 "무엇에 쓸 것인가"를 물었고(검토 언어, 핫리로드, 게임 엔진 언어), 셋 다 "더 단순한 기존 수단으로 왜 안 되는가"라는 시험에 떨어졌다. 원래 사명("뿌리부터 한글인 별개의 컴퓨팅 나무")은 하드웨어 바닥에서 불가능했고, 고쳐 세운 사명("두 언어, 하나의 컴퓨팅")은 일관하지만 그 대중성 상한을 일본어 なでしこ의 20년이 이미 보여준다. 그래서 쓸모를 근거 없이 전제하고 더 만드는 대신, 완성으로 매듭지었다. 그 과정과 근거가 이 저장소의 일부다:

- [완성 기록 (2026-09-21)](완성-기록-2026-09-21.md) — 왜 여기가 끝인지, 무엇이 남는지
- [연구 중단 기록 (2026-09-09)](연구-중단-기록-2026-09-09.md) — 검토 언어 방향의 탈락과 방법의 교훈
- [대중성 조사](docs/15-대중성-조사.md) — 세 나라 50년의 선행 사례와 한국 개발자 담론
- [시장조사](docs/12-시장조사.md) · [핫스왑 방향](docs/14-핫스왑-방향.md) · [읽기 쉬움 점검](docs/10-읽기-쉬움-점검.md)

## 시작하기

쓰기만 할 때는 `geulc.exe` 하나면 된다. 배포물 `geul-<버전>-windows-x64.zip`을 풀면 `geulc.exe`와 `표준/`이 나란히 있다. 둘이 나란히 있으면 소스는 어느 폴더에 있어도 되고, 그 폴더를 PATH에 넣으면 어디서나 `geulc`로 부를 수 있다.

파이썬이 있으면 PyPI로 설치할 수도 있다. `geulc` 명령이 PATH에 잡히고, 안에 든 컴파일러는 같은 판의 GitHub 릴리스와 바이트가 같다([D-47](docs/02-설계결정-기록.md)).

```bash
pip install geul             # 또는 pipx install geul / uv tool install geul
```

```bash
geulc 안녕.gl        # 안녕.exe 생성. -o <출력.exe>, --check, --창, --핫스왑, --dump-ir, --version, --help (명세 6절)
```

개발에는 Python 3.12가 필요하다.

```bash
python build.py test            # 수용 테스트 전체 (--self: 글로 쓴 컴파일러로)
python build.py test --핫스왑   # 핫스왑 투명성: 긍정 테스트 전부를 --핫스왑 빌드로
python build.py selfhost        # 자체호스팅 단계별 교차 검증 + 고정점 + 명령줄 대조
python build.py docs            # 문서 예제를 컴파일·실행해 결과와 맞춤
python build.py tools           # 프로그램/ 의 도구들을 만들어 본다
python build.py release         # 배포물 — 자기 컴파일 바이트가 같을 때만 묶는다
python build.py wheel           # PyPI 휠 — release 다음 묶고 임시 가상환경에 설치해 본다
python ref/geulc.py 파일.gl     # 참조 구현으로 컴파일
```

처음이면 [입문서](docs/09-입문.md)부터 — 열네 장, 각 장에 돌아가는 프로그램이 하나씩, 앞선 지식 불필요. 편집기 색은 [`editors/vscode`](editors/vscode/README.md)(조사에 따로 색이 붙는다).

## 내력

1세대(2026-04~09, [`main` 브랜치](https://github.com/wwoosshh/geul-lang/tree/main), v0.8.0)는 감사에서 결함이 네 가지 설계 결정(상태 의존 토큰화, 타입 없는 IR, 조용한 실패, 너무 이른 자체호스팅)에서 나온다는 것이 확인되어 종료했다. 2세대(2026-09-03~21, 이 브랜치 `v2`)는 그 넷을 설계 단계에서 뒤집어 다시 지었다 — [1세대 교훈](docs/01-1세대-교훈.md).
