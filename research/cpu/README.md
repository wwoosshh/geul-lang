# 글(geul) 컴파일러의 x86-64 대 C — 같은 알고리즘, 같은 입력 (2026-10-12)

바깥 평가: "생성 x64 의 성능은 아직 수치가 없다(fib(40) 하나뿐). 호스트는 GPU 에 묶여 있어 파이썬과 같은 속도였다는 것이 아무것도
말해 주지 않는다. 레지스터 7개 선형 스캔과 12명령 인라인이면 C 최적화 컴파일러와는 차이가 있을 것이다." 그 차이를 잰다.

## 무엇을 재나

| 이름 | 무엇 | 글 | C |
|---|---|---|---|
| fib | 재귀 호출 fib(40) | [fib.gl](fib.gl) | [fib.c](fib.c) |
| sieve | 에라토스테네스의 체, 5천만까지 — 바이트 배열과 이중 반복 | [sieve.gl](sieve.gl) | [sieve.c](sieve.c) |
| bubble | 거품 정렬 3만 개(1세대 기준선의 크기) — 배열 읽기 · 쓰기와 비교 | [bubble.gl](bubble.gl) | [bubble.c](bubble.c) |
| matmul | 배정밀도 행렬곱 500 × 500 (i-k-j) | [matmul.gl](matmul.gl) | [matmul.c](matmul.c) |

- C 는 글 소스를 줄마다 옮겼다 — 같은 타입(64비트 정수), 같은 함수 나눔, 같은 표준 라이브러리 꼴(정수목록의 범위 검사, 수학 함수의
  비트 조작). 다르게 쓰면 더 빠른 C(예: SHA-256 의 32비트 부호없는 정수)는 재지 않았다 — 언어가 아니라 컴파일러를 견주려고.
- 글: 이 저장소의 자체 컴파일러(`build/self_컴파일러.exe` — 배포되는 `geulc.exe` 와 같은 바이트를 낸다).
- C: zig cc(clang) — `-O0`, `-O2`, `-O2` 에서 벡터화를 끈 것. 모두 `-ffp-contract=off`(글은 소스가 `곱해더하기` 를 적을 때만 곱과
  합을 합친다 — 그래서 실수 결과가 비트까지 같다).
- 출력(한 줄)이 모든 빌드에서 같아야 잰다. sha256 은 파이썬 hashlib 과도, rope 는 표 전체의 비트를 접은 수로 견준다.
- 재기: 빌드마다 한 번 데운 뒤 차례를 돌려 가며 7 번 — 프로세스 전체의 벽시계 시간(시작 포함)의 중앙값. GPU 재기와 함께 돌리지 않는다.
- 다시 재기: `python -I -X utf8 research/cpu/재기.py` → [결과.json](결과.json).

## 결과 (2026-10-12 — 글 1.3.0 자체 컴파일러, zig 0.16.0, Intel 13세대(Raptor Lake) · Windows 11)

여섯 짝 모두 출력이 모든 빌드에서 같았다 — SHA-256 은 파이썬 hashlib 과도, RoPE 는 표 2 × 2,097,152 칸의 비트를 접은 수로(실수 결과가
비트까지 같다). 값은 [결과.json](결과.json). 시간은 7 번의 가운데 값(프로세스 시작 포함 — 빈 프로그램이 글 6.0 · C 5.6 ms).

| | 글 | C -O0 | C -O2 | C -O2 벡터화 끔 | 글 / C -O0 | 글 / C -O2 | 글 / C -O2 벡터화 끔 |
|---|---|---|---|---|---|---|---|
| fib(40) — 재귀 호출 | 0.450 s | 0.518 | 0.215 | 0.215 | 0.87 | **2.09** | 2.09 |
| sieve — 바이트 배열, 이중 반복 | 0.380 | 0.563 | 0.252 | 0.264 | 0.67 | **1.51** | 1.44 |
| bubble — 배열 읽기 · 쓰기, 비교 | 1.088 | 3.514 | 0.533 | 0.532 | 0.31 | **2.04** | 2.05 |
| rope — GeulPU 의 RoPE 표(실수 · 큰 정수) | 0.126 | 0.201 | 0.050 | 0.050 | 0.63 | **2.50** | 2.52 |
| sha256 — GeulPU 의 해시(64 MB) | 1.422 | 2.686 | 0.369 | 0.241 | 0.53 | **3.85** | 5.91 |
| matmul — 배정밀도 500³ | 0.179 | 0.755 | 0.017 | 0.035 | 0.24 | **10.5** | 5.18 |

읽는 법:
- **글은 최적화하지 않은 C(-O0)보다 모두 빠르다**(0.24 ~ 0.87 배 시간) — 핍홀(D-12) · 레지스터 할당(D-20) · 작은 함수 인라인(D-31)의 몫이다.
- **최적화한 C(-O2)와는 정수 · 분기가 많은 코드에서 1.5 ~ 2.5 배**(fib · 체 · 거품 정렬 · RoPE 표), 비트 조작이 몰린 SHA-256 에서 3.9 배
  (clang 은 벡터화를 끄면 오히려 빨라져 5.9 배), 배정밀도 행렬곱에서 5.2 배(벡터화 끔)다. 행렬곱의 10.5 배는 clang 의 AVX2 벡터화까지 든
  값이다 — C 쪽 시간이 17 ms 라 시작 시간(약 6 ms)이 섞여 있고, 빼면 6.0 · 15.7 배다.
- 같은 알고리즘이라 차이는 코드 생성에서 온다: 레지스터 일곱 개의 선형 스캔과 12 명령까지의 한 겹 인라인(정수목록_값의 범위 검사 같은
  부름이 남는다), 회전 · 바이트 모으기 같은 명령 고르기와 반복의 변형이 없다, 벡터화가 없다. 글의 SHA-256 은 32비트 부호없는 정수 대신
  64비트 정수에 가리개를 쓰는 꼴이라 C 도 그대로 옮겼다 — 언어의 꼴을 바꾼 C 는 재지 않았다.
- 그래서 "시스템 언어"의 근거로 말할 수 있는 것: C 런타임 없이 C -O0 보다 빠르고, LLVM 이 최적화한 C 의 2 ~ 6 배(스칼라) 시간이다.
  더 줄이려면 인라인의 문턱 · 레지스터 할당(XMM 포함)과 명령 고르기가 첫 손잡이다 — 두 구현이 같은 바이트를 내야 하는 규칙(D-12) 안에서.

## PTX 뒷단의 시간 — 미리 적은 기준 (2026-10-12)

PTX 뒷단(`research/gpu/자체PTX/PTX.gl`)은 글로 쓰고 글 컴파일러로 빌드한 CPU 프로그램이다. GeulPU 의 모듈을 고칠 때마다 · CI 가 돌
때마다 이 시간을 낸다. 위 비교의 결론("C 를 따라잡는 일반 최적화보다, 실제로 걸리는 곳을 재고 줄인다")의 첫 적용이다.

**진단 — 바꾸기 전**([표본재기.py](표본재기.py): 1 ms 마다 주 스레드를 멈춰 RIP 와 RBP 사슬을 읽는 표본 프로파일러, 함수 표는
참조 구현이 같은 바이트의 실행 파일을 만들며 낸다). 0.5B 모듈(소스 6.8 MB)에서:
- 시간의 **71 %** 가 `글자수`(문자열 길이) — `실행한도찾기` 가 커널마다 소스 전체를 훑으며 `(* 실행한도 … *)` 표시를 만날 때마다
  `문자열_자르기` 를 부르고, 그 함수가 원본 전체(6.8 MB)의 길이를 처음부터 센다. 커널 수 × 표시 수 × 6.8 MB 의 일이다.
- 다음은 표준 정수목록의 원소 읽기 · 쓰기(`정수목록_범위검사` 5.6 % · `_값` 3.1 % · `_설정` 1.9 %) — 원소 하나에 부름 둘.

**기준선** ([PTX시간.py](PTX시간.py) → [PTX시간_전.json](PTX시간_전.json)): 모듈 여섯 합 156.5 초 — 0.5B 24.9 · 7B Q8_0 15.5 ·
7B Q4_0 15.2 · 14B Q4_0 15.2 · 7B k-양자화 42.9 · 14B k-양자화 42.9 초. 출력 PTX 는 모두 기록과 같다.

**바꿀 것** (출력은 바이트까지 그대로):
1. PTX 뒷단의 `실행한도찾기` — 낱말을 잘라 새 문자열로 만들지 않고 소스 안에서 제자리로 견준다.
2. 표준 `문자열_자르기` — 원본 전체의 길이를 세지 않고, 필요한 데(시작 + 추출길이)까지만 끝을 찾는다. 결과는 같다.
3. 표준 그릇의 원소 읽기 · 쓰기(정수목록 · 문자열목록 · 동적배열 · 안정배열의 `_값` · `_설정`) — 범위 검사를 그 함수 안에서 하고,
   벗어날 때만 오류 함수를 부른다(지금은 원소마다 검사 함수를 부른다). 오류 메시지 · 종료 코드는 같다.
