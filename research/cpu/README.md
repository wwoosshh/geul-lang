# 글(geul)이 만든 x86-64 대 C — 같은 알고리즘, 같은 입력

생성 코드의 속도와 컴파일러 자신의 속도를 재는 곳이다. 코드 생성이나 컴파일러를 바꿀 때 전후를 여기서 잰다. 여섯 짝과 `재기.py` · `표본재기.py` 는
`research/gpu` 가지(2026-10-12, GeulPU 연구 중)에서 만든 것을 그대로 옮겼다 — 그 가지의 같은 폴더에는 PTX 뒷단의 시간 기록이 더 있다.
컴파일러 자신의 속도는 아래 [컴파일러 자신의 속도](#컴파일러-자신의-속도).

## 무엇을 재나

| 이름 | 무엇 | 글 | C |
|---|---|---|---|
| fib | 재귀 호출 fib(40) | [fib.gl](fib.gl) | [fib.c](fib.c) |
| sieve | 에라토스테네스의 체, 5천만까지 — 바이트 배열과 이중 반복 | [sieve.gl](sieve.gl) | [sieve.c](sieve.c) |
| bubble | 거품 정렬 3만 개(1세대 기준선의 크기) — 배열 읽기 · 쓰기와 비교 | [bubble.gl](bubble.gl) | [bubble.c](bubble.c) |
| matmul | 배정밀도 행렬곱 500 × 500 (i-k-j) | [matmul.gl](matmul.gl) | [matmul.c](matmul.c) |
| sha256 | SHA-256, 64 MB — GeulPU 의 `호스트/해시.gl` 그대로(64비트 정수 + 32비트 가리개, 상수는 정수목록) | [sha256.gl](sha256.gl) | [sha256.c](sha256.c) |
| rope | GeulPU 의 RoPE 표(`호스트/로프.gl` 그대로) — 7B 의 표 32768 × 64: 두 배 정밀도 실수, 원주율의 큰 정수, fp64 다항식과 바른 반올림 | [rope.gl](rope.gl) | [rope.c](rope.c) |

- C 는 글 소스를 줄마다 옮겼다 — 같은 타입(64비트 정수), 같은 함수 나눔, 같은 표준 라이브러리 꼴(정수목록의 범위 검사, 수학 함수의
  비트 조작). 언어의 꼴을 바꾼 더 빠른 C(예: SHA-256 의 32비트 부호없는 정수)는 재지 않는다 — 언어가 아니라 컴파일러를 견주려고.
- C: zig cc(clang) — `-O0`, `-O2`, `-O2` 에서 벡터화를 끈 것. 모두 `-ffp-contract=off`(글은 소스가 `곱해더하기` 를 적을 때만 곱과
  합을 합친다 — 그래서 실수 결과가 비트까지 같다).
- 출력(한 줄)이 모든 빌드에서 같아야 잰다. sha256 은 파이썬 hashlib 과도, rope 는 표 전체의 비트를 접은 수로 견준다.
- 다른 언어(2026-11-26): [다른언어/](다른언어/) 에 C 를 다시 줄마다 옮긴 Rust · Go · Java 판이 있다 — 같은 타입(64비트 정수), 같은 함수
  나눔, 같은 정수목록(용량 8 에서 두 배, 범위 검사 함수), 안전한 색인(경계 검사), 곱과 합을 합치지 않음. 언어가 C 를 그대로 따를 수
  없는 곳(Java 의 지역 배열은 `new`, Rust 의 바꿔 쓰는 전역은 `OnceLock` · 구조체 인자, Go · Rust 는 지역 배열을 0 으로 채움)은
  언어마다의 README 에 적었다. [다른언어/빈/](다른언어/빈/) 은 프로세스를 띄우는 값만 재는 빈 프로그램이다.

```bash
python -I -X utf8 research/cpu/언어견주기.py --횟수 11 --코어 P --gcc <gcc.exe> --tcc <tcc.exe> --go <go.exe>   # PATH 에 없는 도구만 준다
python -I -X utf8 research/cpu/언어컴파일견주기.py --횟수 7 --코어 P --gcc <gcc.exe> --tcc <tcc.exe> --go <go.exe>

```

재는 법에서 밝혀 둘 것:

- 노트북에서는 회차 사이에 같은 실행 파일이 10 ~ 15 % 흔들린다(부스트 · 열). 전후 비교는 `판견주기.py` 로 같은 회차 안에서 번갈아 잰다.
  데스크톱(i7-14700K, P코어에 묶어)에서는 한 시간 떨어진 두 회차가 2 % 안이었다([아래](#결과--데스크톱-i7-14700k-여러-언어-2026-11-26-글-141)).
- P코어 · E코어가 섞인 CPU 는 잴 프로세스를 P코어에 묶으면 흔들림이 준다 — 윈도에서 자식 프로세스는 부모의 친화성을 물려받으므로 재는
  파이썬을 묶으면 된다(예: `psutil.Process().cpu_affinity([0, 1, 2, 3])` 뒤 스크립트를 부른다).
- GPU 재기나 다른 무거운 일과 함께 돌리지 않는다.

|---|---|---|---|

| 거품 정렬 안쪽(교환 없을 때) | 21 · 스택 읽기 1 · 뛰는 분기 3 | 14 · 0 · 2 | 7 · 0 · 2 |
| 체 안쪽 | 13 · 뛰는 분기 2 | 5 · 1 | 4 (둘씩 펼쳐 8) |

- 행렬곱: 반복 불변인 `n` · 세 배열 · `i` 가 스필되어 원소마다 스택에서 아홉 번 읽고, `i * n` · `k * n` 을 원소마다 곱하고 `i * n + j` 를
  두 번 셈한다. D-56 은 복사(`mov`)와 실수 결과의 RAX 경유만 걷었다 — 남은 것은 [다음 손잡이](#다음-손잡이-기계어를-보고-잰-것만)의 1 · 7.
- sha256: 한 줄 함수 `오른돌림` 이 부름으로 남아 실행 시간의 52 % 였다(표본재기). rope: 실수 연산의 결과마다 `movq rax, xmm0` ·
  `movq xmmN, rax` 로 RAX 를 돌아 의존 사슬이 길었다. fib: gcc 16 은 재귀 하나를 반복으로 바꾸고 여러 겹 펼친다(글의 4 배 — clang 은 2 배).

**하나씩 켠 시제품** — 참조 구현 사본에 환경 변수로 켜는 고침을 넣어 같은 회차에서 번갈아 9 번(빨라진 배수). 분기 꼴은 첫 판(바로 다음

## 외부(운영체제) 시간 — 무엇인가

2026-11-25, 글 1.4.1. [표본재기.py](표본재기.py) 가 운영체제 안의 시간도 가른다 — 그 주소가 든 DLL 의 .pdata · 내보내기 표로 함수
이름을 붙이고, DLL 의 풀기 정보(UNWIND_INFO — 윈도가 예외 처리에 쓰는 것)로 운영체제 프레임을 풀어 부른 글 함수까지 잇는다. 부른
쪽을 찾지 못한 표본은 GeulPU 뒷단 0.05 %, 자체 컴파일러 3.4 %(대부분 프로세스를 띄우는 동안 — 글 코드가 아직 돌지 않는다).

| | 자체 컴파일러 (자기 자신, 20 번) | GeulPU PTX 뒷단 (qwen2Q8, 2 번) |
|---|---|---|
| 외부 전체 | 26.4 % | 21.0 % |
| 메모리 — `재할당` · `할당` · `초기할당` · `해제` | **19.1 %** (7.6 · 5.4 · 4.7 · 1.5) | **19.1 %** (8.8 · 8.2 · 2.0 · 0.2) |
| 파일 — 열기 · 읽기 · 쓰기 · 닫기 | 3.6 % (열기 2.6 — 그중 포함 찾기의 `파일있는가` 1.8) | 1.8 % (쓰기 1.5 — PTX 87 MB) |
| 프로세스 시작 · 끝 | 3.7 % | 0.1 % |

메모리의 몫은 대부분 목록이 자랄 때다 — 두 배로 키우며 옛 자료를 새 자리로 복사하고(`RtlCopyMemory`), 새로 받은 페이지를 처음
만질 때마다 운영체제가 0 으로 채운다(그 시간도 복사하는 명령에 잡힌다). 부른 글 함수의 사슬(전체 대비):

- 자체 컴파일러: `재할당 < 동적배열_새원소 < 새명령`(IR 명령 배열) 4.0 %, `초기할당 < 안정배열_새원소 < 새노드`(구문 노드 블록 —
  1024 칸을 0 으로) 3.5 %, `파일_열기 < 파일있는가 < 포함찾기` 1.8 %, `재할당 < 동적배열_새원소 < 토큰추가` 1.4 %.
- GeulPU PTX 뒷단: `재할당 < 정수목록_추가 < 상태옮기기 < 범위증명` 3.9 %, `할당 < 문자열_복제 < 문자열목록_추가 < 커널옮기기`(출력
  줄을 복제해 모은다) 2.8 %, `재할당 < 정수목록_추가 < 채운목록 < …`(네 곳) 2.0 %, `할당 < 서식글 < 커널옮기기` 0.9 %. 최대 작업
  집합이 2.7 GB 쯤이다 — `채운목록` 은 빈 목록에 n 번 더해 만들고(용량 8 에서 두 배씩), 커널마다 만든 목록을 해제하지 않는다
  (`PTX.gl` 에 `정수목록_해제` 가 없다).

GeulPU 쪽 고침(GeulPUv2 의 `perf/backend-lists` — 이 저장소 밖): `채운목록` 이 메모리를 한 번에 잡고, 커널마다 새로 만들던
전역 표(PTX 45 개 · SPIR-V 74 개)가 옛 메모리를 다시 쓰고, PTX 의 본문 · 머리 줄을 다시 쓰는 버퍼에 바로 넣어 끝에 한 번 쓰고,
SPIR-V 의 낱말을 자리를 한 번 잡아 바로 쓴다. 같은 커널 소스 다섯 모듈을 1.4.1 의 뒷단과 번갈아 세 번 — PTX 뒷단 42.2 → 34.0 s
(**1.24 배**), SPIR-V 뒷단 23.5 → 20.5 s(**1.15 배**), 가장 큰 모듈(qwen35K)의 최대 작업 집합 3.7 → 1.6 GB(PTX) · 2.8 → 1.6 GB
(SPIR-V). 모듈 76 개의 PTX · SPIR-V 59 개는 바이트까지 같다. 고친 뒤 PTX 뒷단의 외부 시간은 21.0 → 13.6 % 이고, 남은 것은 대부분
글 쪽이다 — 앞단의 구문 노드 블록 · 토큰 · IR 배열이 자랄 때, 파일 쓰기(표준의 `파일_쓰기` 가 4 KB 버퍼에 한 바이트씩 옮긴다).

프로세스 시작: kernel32 만 가져오는 최소 실행 파일은 5.1 ms, shell32 도 가져오면(`CommandLineToArgvW`) 8.9 ms 다(P코어, 번갈아
200 번의 가운데). 글의 실행 파일은 명령줄을 나누려고 모두 shell32 를 가져오므로 프로세스마다 약 3.8 ms 를 더 쓴다 — 오래 도는
프로그램에는 작고, hello 같은 작은 프로그램 · 시험 · 컴파일러를 부를 때마다는 크다.

## 다음 손잡이 (기계어를 보고 잰 것만)

1. **스필 선택과 레지스터 수** — 빈 레지스터가 없으면 끝이 가장 먼 구간을 내보내는 선형 스캔(D-20)이 반복의 깊이 · 쓰임 수를 보지
   않는다. 거품 정렬의 `n` 은 D-56 의 복사 전파로 레지스터에 들었지만, 행렬곱처럼 반복 내내 쓰는 지역이 일곱보다 많으면 반복 불변인
   것(`n` · 세 배열 · `i`)이 여전히 스필되어 안쪽 반복에서 스택을 아홉 번 읽는다. 값에 쓰는 레지스터가 피호출자 보존 일곱뿐이다
   (RAX · RCX · RDX · R8 ~ R11 은 스크래치) — 부름을 건너지 않는 구간에 호출자 보존 레지스터를 쓰면 SHA-256 의 상태 여덟(A ~ H)도 든다
   (D-56 뒤에도 `해시블록` 안에 스택 접근 75 곳).
2. **상수 나눗셈** — `x % 100000` 이 `cqo; idiv` 다. 2 의 거듭제곱이면 시프트 · 가리개(부호 맞춤 포함), 그 밖은 곱셈 역원으로. 표준
   `안정배열_원소` 의 `/ 1024` · `% 1024` 는 D-55 에서 소스를 `>> 10` · `& 1023` 으로 바꿨다(검사를 지난 위치는 0 이상) — 컴파일러가
   스스로 바꾸는 일은 남았다.

   끝에서 위로 뛴다 — 반복을 돌려 아래에서
   보면 반복마다 뛰는 분기가 하나 준다. `ret` 뒤의 닿지 않는 마무리(`mov eax, 0` 과 에필로그)는 남았다.

   (`안정배열_원소` 52 · `정수목록_추가` 58)은 여전히 부름이다. 곧은 함수의 한도는 D-56 에서 12 → 24.
5. **인라인 뒤의 상수 접기** — D-56 으로 `오른돌림(A, 2)` 가 펴지지만 회전량이 매개변수 지역에 남아 `sar r, cl` 과 `32 - n` 을 실행 중에

   접기 · 죽은 코드 제거는 값이 없다"는 판단은 컴파일러 자신의 IR(7만 명령에 접을 상수 4 개)로 잰 것이라 인라인한 수치 코드에는 맞지 않는다.
6. **코드 배치** — 함수 시작이 아무 바이트에나 온다. 기계어가 바이트까지 같은 fib 의 `피보` 가 주소만 달라 0.366 ~ 0.464 초였고,
   함수 시작을 64 B 에 맞추면 0.343 ~ 0.347 초였다(시제품, 같은 회차에서 15 번 번갈아). 반복 위주 코드는 함수만 맞추면 반복 머리가
   옮겨 가 ±10 % 오르내린다(거품 정렬 0.789 ↔ 0.870 초) — 반복 머리도 맞춰야 한다. 재기의 흔들림도 이것으로 준다.
7. **큰 것** — 재귀를 반복으로(gcc 16 은 fib 의 두 부름 중 하나를 반복으로 바꾸고 여러 겹 펼쳐 글의 4 배 빠르다 — clang 은 2 배),
   공통 부분식 · 반복 불변식(행렬곱의 안쪽 반복이 `i * n` · `k * n` 을 원소마다 곱하고 `i * n + j` 를 두 번 셈한다 — 소스에서 손으로
   끌어내면 1.33 배, D-56 과 함께 1.78 배), 벡터화(행렬곱에 남은 gcc 와의 3.4 배 가운데 2 배쯤).

모두 두 구현이 같은 바이트를 내야 하는 규칙(D-12) 안에서 두 구현에 같이 넣는다.
