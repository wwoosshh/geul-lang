# 글(geul)이 만든 x86-64 대 C — 같은 알고리즘, 같은 입력

생성 코드의 속도와 컴파일러 자신의 속도를 재는 곳이다. 코드 생성이나 컴파일러를 바꿀 때 전후를 여기서 잰다. 여섯 짝과 `재기.py` · `표본재기.py` 는
`research/gpu` 가지(2026-10-12, GeulPU 연구 중)에서 만든 것을 그대로 옮겼다 — 그 가지의 같은 폴더에는 PTX 뒷단의 시간 기록이 더 있다.
컴파일러 자신의 속도는 아래 [컴파일러 자신의 속도](#컴파일러-자신의-속도).

## 무엇을 재나

| 이름 | 무엇 | 글 | C |
|---|---|---|---|
| fib | 재귀 호출 fib(40) | [fib.gl](fib.gl) | [fib.c](fib.c) |
| sieve | 에라토스테네스의 체, 5천만까지 — 바이트 배열과 이중 반복 | [sieve.gl](sieve.gl) | [sieve.c](sieve.c) |
| bubble | 거품 정렬 3만 개(1세대 기준선의 크기) — 배열 읽기 · 쓰기와 비교 | [bubble.gl](bubble.gl) | [bubble.c](bubble.c) |
| matmul | 배정밀도 행렬곱 500 × 500 (i-k-j) | [matmul.gl](matmul.gl) | [matmul.c](matmul.c) |
| sha256 | SHA-256, 64 MB — GeulPU 의 `호스트/해시.gl` 그대로(64비트 정수 + 32비트 가리개, 상수는 정수목록) | [sha256.gl](sha256.gl) | [sha256.c](sha256.c) |
| rope | GeulPU 의 RoPE 표(`호스트/로프.gl` 그대로) — 7B 의 표 32768 × 64: 두 배 정밀도 실수, 원주율의 큰 정수, fp64 다항식과 바른 반올림 | [rope.gl](rope.gl) | [rope.c](rope.c) |

- C 는 글 소스를 줄마다 옮겼다 — 같은 타입(64비트 정수), 같은 함수 나눔, 같은 표준 라이브러리 꼴(정수목록의 범위 검사, 수학 함수의
  비트 조작). 언어의 꼴을 바꾼 더 빠른 C(예: SHA-256 의 32비트 부호없는 정수)는 재지 않는다 — 언어가 아니라 컴파일러를 견주려고.
- C: zig cc(clang) — `-O0`, `-O2`, `-O2` 에서 벡터화를 끈 것. 모두 `-ffp-contract=off`(글은 소스가 `곱해더하기` 를 적을 때만 곱과
  합을 합친다 — 그래서 실수 결과가 비트까지 같다).
- 출력(한 줄)이 모든 빌드에서 같아야 잰다. sha256 은 파이썬 hashlib 과도, rope 는 표 전체의 비트를 접은 수로 견준다.

| [판견주기.py](판견주기.py) | 두 컴파일러(판)로 같은 여섯 소스를 만들어 번갈아 돈다 — 코드 생성을 바꾼 전후 비교. 고치기 전의 `build/self_컴파일러.exe` 와 `표준/` 을 다른 폴더로 떠 두고 그 폴더를 준다 |
| [표본재기.py](표본재기.py) | 글 프로그램의 표본 프로파일러 — 1 ms 마다 주 스레드의 RIP · RBP 사슬을 읽어 함수별 자기 · 포함 시간. 함수 표는 참조 구현이 같은 바이트의 실행 파일을 만들며 낸다. 컴파일러 자신도 잰다(아래) |
| [컴파일견주기.py](컴파일견주기.py) | 두 컴파일러로 같은 입력(기본: 자체 컴파일러 자신 · 백업창)을 번갈아 컴파일해 컴파일 시간을 견준다 |
| [출력견주기.py](출력견주기.py) | 두 컴파일러가 모든 입력(spec-tests · 표준 · self · 프로그램 · research) × 모든 출력 모드(실행 파일, 리눅스 ELF, 핫스왑, 덤프 셋, 검사)에서 종료 코드 · 표준출력 · 표준오류 · 출력 파일까지 같은지 — 컴파일러의 안쪽만 바꾼 고침의 검증 |

```bash
python -I -X utf8 research/cpu/재기.py                       # zig 가 PATH 에 없으면 --zig <zig.exe>
python -I -X utf8 research/cpu/판견주기.py <옛 루트>           # 새 루트의 기본값은 이 저장소
python -I -X utf8 research/cpu/표본재기.py <소스.gl> -- <프로그램 인자...>
python -I -X utf8 research/cpu/컴파일견주기.py <옛 컴파일러 exe>
python -I -X utf8 research/cpu/출력견주기.py <옛 컴파일러 exe>
python -I -X utf8 research/cpu/표본재기.py self/컴파일러.gl -- self/컴파일러.gl -o build/표본.exe   # 컴파일러 자신 (저장소 꼭대기에서)
```

재는 법에서 밝혀 둘 것:

- 노트북에서는 회차 사이에 같은 실행 파일이 10 ~ 15 % 흔들린다(부스트 · 열). 전후 비교는 `판견주기.py` 로 같은 회차 안에서 번갈아 잰다.
- P코어 · E코어가 섞인 CPU 는 잴 프로세스를 P코어에 묶으면 흔들림이 준다 — 윈도에서 자식 프로세스는 부모의 친화성을 물려받으므로 재는
  파이썬을 묶으면 된다(예: `psutil.Process().cpu_affinity([0, 1, 2, 3])` 뒤 스크립트를 부른다).
- GPU 재기나 다른 무거운 일과 함께 돌리지 않는다.

**다음 손잡이** (GeulPU 뒷단, D-55 뒤의 프로파일 — 자기 시간):

1. **외부 21 %** — 운영체제 안의 시간이다. 할당(HeapAlloc · HeapFree) · 87 MB 의 PTX 쓰기 · 시작과 끝 중 무엇인지 먼저 갈라야 한다
   (표본재기는 운영체제 함수의 이름을 모른다).
2. **문자열 · 서식 18 %** — 위 표의 여섯 함수. 모두 한 바이트씩 도는 반복이라 가드 꼴이 아니다. 같은 문자열의 길이를 거듭 재는
   곳을 줄이거나 반복의 기계어를 고치는 쪽이다.
3. **`정수목록_추가` 4 %** — 58 명령이라 펴지지 않는다. 늘리는 길(`재할당`)을 따로 함수로 빼면 용량이 모자랄 때만 부르는 가드 꼴이
   된다(재 보지 않았다). `안정배열_원소`(52 명령)도 같은 생각을 해 볼 만하다.
4. **GeulPU 자신** — `범위증명`(포함 28 %) · `상태옮기기`(포함 14 %)의 알고리즘은 GeulPU 쪽의 일이다.

## 다음 손잡이 (기계어를 보고 잰 것만)

1. **스필 선택** — 빈 레지스터가 없으면 끝이 가장 먼 구간을 내보내는 선형 스캔(D-20)이 반복의 깊이 · 쓰임 수를 보지 않는다(거품 정렬의 `n`).
2. **상수 나눗셈** — `x % 100000` 이 `cqo; idiv` 다. 2 의 거듭제곱이면 시프트 · 가리개(부호 맞춤 포함), 그 밖은 곱셈 역원으로. 표준
   `안정배열_원소` 의 `/ 1024` · `% 1024` 는 D-55 에서 소스를 `>> 10` · `& 1023` 으로 바꿨다(검사를 지난 위치는 0 이상) — 컴파일러가
   스스로 바꾸는 일은 남았다.
3. **분기 꼴** — 반복 · 조건이 모두 `jl 몸; jmp 끝` 이다(조건을 뒤집어 `jge 끝` 하나로). `ret` 뒤에 닿지 않는 마무리가 붙는다.
4. ~~분기 하나가 든 작은 함수의 인라인~~ — D-55(가드 꼴)에서 했다. 반복이 든 것(`문자열_비교` · `글자수`)과 32 명령을 넘는 것
   (`안정배열_원소` 52 · `정수목록_추가` 58)은 여전히 부름이다.
5. **큰 것** — 재귀를 반복으로(clang 은 fib 의 두 부름 중 하나를 반복으로 바꿔 부름을 절반으로 줄인다), 공통 부분식 · 반복 불변식
   (`a[j]` 두 번 읽기, `n - 1`), 벡터화(행렬곱의 7.7 배 중 절반 남짓).

모두 두 구현이 같은 바이트를 내야 하는 규칙(D-12) 안에서 두 구현에 같이 넣는다.
