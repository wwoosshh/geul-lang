# 0단계 — 실제 버그에서 무엇이 손실됐나 (docs/17 §7)

종이 시험(0′)은 설계자가 실수를 골랐다. 이 단계는 **공개된 실제 버그**를 정해 둔 규칙으로 모아 무엇이 손실됐는지
분류하고, 글의 문법이 그것을 막는지 잰다. docs/17 의 판정: 목록의 **절반 이상**을 글의 컴파일 오류 또는 "적을 자리
없음"으로 표현할 수 있으면 계속, 아니면 방향을 고친다.

아래 "방법"은 버그를 모으기 전에 적고 커밋했다(2026-10-08). 결과는 그 뒤에 붙인다.

## 방법

### 출처와 질의

마감: 2026-10-01 전에 머지되었거나 닫힌 것. 질의는 `gh search` 로 돌리고, 출처마다 순서대로 내려가며 **포함 조건을
만족하는 처음 10개**를 넣는다(사후 분석은 전부). 건너뛴 후보도 이유와 함께 적는다.

| 출처 | 질의 | 순서 |
|---|---|---|
| Anthropic [사후 분석](https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues) (2025-09) | 글에 적힌 문제 전부 | 글의 순서 |
| PyTorch (`pytorch/pytorch`) | 닫힌 이슈, 라벨 `module: correctness (silent)` | 생성일 내림차순 |
| vLLM (`vllm-project/vllm`) | 머지된 PR, 제목에 다음 낱말 중 하나: incorrect · wrong · accuracy · NaN · garbage · gibberish · precision · correctness · overflow (질의 아홉의 합집합) | 생성일 내림차순 |
| llama.cpp (`ggml-org/llama.cpp`) | vLLM 과 같은 낱말, 머지된 PR | 생성일 내림차순 |

### 포함 조건 (모두 만족)

1. **결과가 틀렸다** — 틀린 값, NaN·Inf, 엉뚱한 출력(쓰레기·반복·다른 언어), 정확도 하락, 또는 계산 중의 잘못된 메모리
   접근. 검사 코드가 낸 예외만 있는 것, 멈춤, 메모리 부족, 성능, 빌드·설치, 문서, API·UI 는 뺀다.
2. **원인이 연산에 있다** — 커널, 연산 구현, 모델의 수식 코드(층·어텐션·샘플링 수식), 양자화·역양자화, 가중치의 배치·형식,
   수치 설정(타입·정밀도 플래그), 컴파일러·코드 생성. 토크나이저, 채팅 틀, 요청 배정·스케줄링 논리, 입출력은 뺀다.
3. **고쳤거나 원인이 밝혀졌다** — 머지된 수정, 또는 원인을 밝힌 이슈(수정 커밋·PR 이 이어진 것). "계획 없음"으로 닫힌 것은 뺀다.

### 모으기와 분류를 나눈다

- **모으기** — 후보를 순서대로 읽고(PR·이슈 본문, 필요하면 diff) 증상·원인·수정을 사실대로 적는다. 모으는 쪽은 글의
  문법이나 이 연구의 가설을 보지 않는다.
- **분류** — 다 모은 뒤 한 번, 아래 기준으로 한다. 애매하면 막지 못한 쪽(통과)으로 센다.

### 분류 기준

**무엇이 손실됐나** — docs/17 §5 의 갈래에 컴파일러 내부를 따로 둔다. 주 갈래 하나, 필요하면 부 갈래 하나.

| 갈래 | 묻는 것 | 예 |
|---|---|---|
| 자리 | 값이 어디에 있고 어디로 가는가 | 축의 이름·순서·배치, 인덱스·보폭·오프셋, 크기의 대응, 경계, 주소 공간 |
| 정체 | 무슨 값인가 | 정밀도·타입, 저장 형식(양자화·영점·묶음), 척도, 종류 |
| 흐름 | 누가 읽고 누가 쓰는가 | 역할(출처·목적지·누적), 겹침, 순서·동기화, 상태의 재사용 |
| 의도 | 무엇을 계산하려는가 | 공식, 경계의 방향, 알고리즘 |
| 컴파일러 내부 | 컴파일러가 의미를 바꿨는가 | 오컴파일, 최적화 재량(합침·순서 바꿈), 근사 |

**글이 막는가** — 근거는 종이 시험의 [가상 문법 v0](../종이시험/README.md) 규칙 1~11 과 docs/17 에 적힌 계획(2단계 의미
층, PTX 계약)뿐이다. 판정하면서 새 규칙을 지어내 막는 것은 세지 않는다.

| 판정 | 뜻 | 판정 비율에 |
|---|---|---|
| 거부 | v0 규칙이나 2단계 의미 층이 그 실수를 컴파일 오류로 만든다 — 규칙 번호를 적는다 | 센다 |
| 자리 없음 | 그 실수를 적을 코드가 v0 표기에 없다 — 인덱스 계산·보폭·크기 인자·묶음 순서 등 | 센다 |
| 계약 | 컴파일러 내부 갈래에서, PTX 계약·비트 대조 같은 단계별 검사가 드러낸다 (주장 A) | 따로 적고, 세지 않는다 |
| 조건부 | 지금 문서에 없는 규칙이 있어야 막는다 | 따로 적고, 세지 않는다 |
| 통과 | 막지 못한다 | — |

**증상** — 다른 연구의 AI 버그(무한 반복, 다른 언어 출력, 논점 상실, 출력 실패)와 잇기 위해 함께 적는다: 조용한 수치
오차·정확도 하락 / NaN·Inf / 엉뚱한 출력(쓰레기·반복·다른 언어) / 출력 실패(잘못된 메모리 접근 등).

**판정** — (거부 + 자리 없음) ÷ 포함된 버그 전체 ≥ 1/2 이면 계속, 아니면 방향을 고친다.

### 미리 적는 한계

- 분류는 한 쪽(이 연구의 AI 에이전트)이 한다. 행마다 링크와 근거를 두어 누구든 다시 볼 수 있게 한다.
- 글의 문법은 아직 가상이다. "막는다"는 종이 위의 판정이다.
- 제목 낱말로 고른 PR 은 제목에 증상을 적은 버그 쪽으로 기운다. 라벨로 고른 PyTorch 가 그것을 조금 덜어 준다.

## 결과 (2026-10-08) — 기준 미달

규칙대로 **방향을 고친다.** 행마다의 표(증상·원인·갈래·판정과 근거, 제외한 후보와 이유)는 [결과.md](결과.md) 에 있다 —

### 분류하며 정한 해석

1. **v0 로 그 연산을 적을 수 있어야** 거부·자리 없음을 준다. 적을 수 없는 연산 — 빈 칸이 있는 뷰, 간접 인덱싱(gather·scatter),
   가변 길이·페이지 KV, 순환, argmax, 분산 통신, 자동 미분 — 은 조건부(표기를 더하면 막힐 꼴) 또는 통과다.
2. 한 PR 이 여러 원인을 고쳤으면 가장 약한 판정을 준다.
3. 같은 원인의 두 이슈(PyTorch #198866·#198333)는 방법대로 둘 다 넣었다. 하나로 세도 결론은 같다(민감도).
4. **처음 판정을 넷 고쳤다.** PyTorch #198652, vLLM #51915, llama.cpp #28956·#26223 을 처음에는 거부로 보았다가, 1번 해석과
   범위 문제(#2717·#24909)의 일관성에 따라 조건부로 고쳤다. 넷 다 비율을 낮추는 쪽이다(37% → 28%).

### 민감도

| 셈법 | 비율 |
|---|---|
| 방법대로 | 12/43 = 28% |
| 같은 원인 둘을 하나로 | 12/42 = 29% |
| 컴파일러 안의 손실을 분모에서 뺌 | 12/33 = 36% |
| 조건부까지 셈 (표기를 더한다면) | 24/43 = 56% |
| 계약까지 셈 (주장 A 의 검사를 센다면) | 22/43 = 51% |

방법대로의 문법 판정은 어떻게 세도 50% 에 못 미친다. 50% 를 넘는 것은 표기를 더하거나(조건부) 컴파일러의 검사(계약)를 셀 때뿐이다.

### 의미 손실의 분류 — 실제 버그에서 나온 세부 갈래

컴파일러 안의 손실 10개도 무엇을 잃었는지로 다시 나누면 다음과 같다.

| 갈래 | 수 | 세부 |
|---|---|---|
| 자리 | **25** (컴파일러 안 6 포함) | **정수 폭 넘침 9** (인덱스·오프셋·크기의 곱이 32비트를 넘음), 배치 가정 8 (보폭·저장 순서·저장 배치·저장 형식·축·브로드캐스트 판단), 인덱스 계산 2, 공유 메모리 배치 2, 난수와 원소의 대응 2, 경계·조각 크기 2 |
| 정체 | 10 (컴파일러 안 1) | 값이 형식의 범위를 넘음 3, 정밀도 2, 원소 폭 1, 형식의 정의 1, 척도 1, NaN 의 의미 1, 원인 비공개 1 |
| 흐름 | 4 (컴파일러 안 2) | 겹침 2, 순서·동기화 1, 상태의 전달 1 |
| 의도 | 3 | 공식 2, 커널의 전제 1 |
| 불명 | 1 | 컴파일러 오컴파일 (세부 비공개) |

- **자리가 가장 크다(58%).** 가장 흔한 한 가지 꼴은 **정수 폭 넘침**(전체의 21%)이다 — 긴 문맥·큰 배치에서 인덱스와 오프셋을
  32비트로 계산했다. 그다음이 배치 가정(보폭·저장 순서)이다.
- **컴파일러 안의 손실이 23%** 이고, 잃는 것은 사용자 코드와 같은 갈래(자리·흐름·정체)다.
- **증상은 대부분 조용하다** — 조용한 수치 오차 24(56%), 엉뚱한 출력 9, NaN·Inf 5, 출력 실패 5.
- **끝없는 반복 셋은 모두 자리의 손실이다** — 분산 조각 크기(vLLM #57779), 뷰의 보폭(llama.cpp #28956), 마스크 오프셋의 정수 넘침
  (llama.cpp #23610). 영어 답에 다른 언어 글자가 섞인 사례(사후 분석)는 원인이 공개되지 않았다.

### 무엇을 고칠까 — 후보 (정하는 것은 사용자)

- **(가) 주장 A 를 앞에 세운다.** 문법이 사용자의 실수를 직접 거부한 것은 3개뿐이다. 계약 10 과 자리 없음 9 — 합쳐 19개(44%) —
  는 글에서는 **컴파일러가 맡게 되는 일**이다: 인덱스의 정수 폭을 맞게 고르고, 배치를 타입대로 계산하고, 안에서 의미를 잃지 않고,
  단계마다 대조한다. 글의 가치는 "실수를 거부하는 문법"보다 "의미를 들고 내려가는 컴파일러"에 있고, 문법은 그 검사에 쓸 사실을
  빠뜨림 없이 공급하는 쪽이다.
- **(나) 표기를 넓히되 새 표본으로 다시 잰다.** 조건부 12 의 표기는 2단계 문법의 후보다. 다만 이 43개를 보고 고른 것이라, 넣은 뒤에는
  **새 표본**(같은 질의의 다음 10개씩, 또는 2026-10-01 뒤의 버그)으로 같은 기준을 다시 재야 한다 — 이 표본에 맞춘 규칙이 되지 않게.
- **(다) 주장 B 를 좁혀 적는다.** 종이 시험의 21/28(75%)은 설계자 편향이었다(그 문서가 미리 적은 대로). 실제 버그에서 문법이 직접
  하는 일은 배치 가정의 거부와 인덱스 계산의 제거다.

### 한계

- 분류는 한 쪽(이 연구의 AI 에이전트)이 했고, 넷을 고쳐 다시 보았다(위 4번). 행마다 링크와 근거가 있다.
- 출처마다 최신 10개라 그 시기(대부분 2026년)의 작업 — 긴 문맥, FP8·FP4, torch.compile — 쪽으로 기운다.
- PyTorch 라벨 표본은 torch.compile 의 버그가 많다(10 중 7).
- 글의 문법은 아직 가상이다. "막는다"는 종이 위의 판정이다.
