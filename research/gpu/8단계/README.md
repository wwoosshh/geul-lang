# 8단계 — 자리 둘 계약: 밝힌 정밀도로 프롬프트를 더 빠르게 (docs/17 §7 "8단계")

사용자 결정(2026-10-09): 슬로건은 "적힌 대로만 잃고, 느려지지 않는다" — 의미를 지키되 속도를 버리지 않는다. 그리고 속도에 천장을 두지
않는다: 비교 대상을 이겼다고 멈추지 않고, 안정성을 포기하지 않는 빠른 길이 있으면 반드시 해 본다. 판정은 실험보다 먼저 적었다(1a09a32).

7단계에서 큰 모델(GPT-2 XL)의 프롬프트가 llama.cpp 의 1.65배 느린 까닭은 6단계의 정수 블록 계약이 활성값을 **자리 넷**(30 비트)으로 두어
텐서 일이 llama.cpp(한 자리, 8 비트)의 네 배이기 때문이었다. 이 단계는 같은 계약에서 자리 수만 둘인 판을 더한다.

## 계약 — 자리 둘

6단계의 정수 블록 계약에서 자리 수만 둘이다(둘 다 밝힌 정밀도, 둘 다 남는다 — 호스트가 `자리수=2` 로 고른다).
1. E = ⌊log₂ max_k |x_k|⌋, [−98, 100] 으로(자리 넷과 같다).
2. n_k = 가까운정수(x_k · 2^(13 − E)), |n| ≤ 2¹⁴. 균형 256진 두 자리 D₀ ∈ [−128, 127], D₁ ∈ [−64, 64].
3. S_j = Σ_k D_j,k · q_k,n — 정수로 정확(정수 텐서 코어든 dp4a 든 같다).
4. v_j = S_j · 2^(8j + E − 13) (정확), u = v₁ + v₀, y ← 곱해더하기(u, d_b,n, y), 출력 = y + 치우침 → 끝손질.

활성값의 눈금은 블록 최댓값의 2⁻¹⁴ — llama.cpp 의 8 비트(2⁻⁷)보다 128배 촘촘하다. 일반으로 자리수 m 의 고정소수점 비트는 P = 8m − 3
([정수계약.py](../6단계/정수계약.py) 의 `자리수` 매개변수 — 넷 29, 둘 13).

**왜 둘인가 — 하드웨어 산수.** 정수 텐서 코어는 f16 텐서 코어(fp32 누적)의 두 배 속도다(이 GPU 에서 int8 320 TOPS). 자리 둘이면 텐서
일이 llama.cpp 의 두 배 — f16 텐서 코어 엔진과 같은 시간이 산수로 성립한다.

**판정 전에 잰 것.** 흉내(numpy, Q4_0 의 실제 층, fp64 대비 행 노름 상대차 중앙값): small c_fc — 가닥 약속 2.4 × 10⁻⁷, 자리 둘
6.4 × 10⁻⁵(이상치 1% × 30 이면 1.3 × 10⁻⁴), 자리 셋 2.7 × 10⁻⁷, 자리 넷 9.8 × 10⁻⁸; XL c_fc · mlp c_proj 도 자리 둘 6.4~6.6 × 10⁻⁵ / 1.3~1.4 × 10⁻⁴.
llama.cpp 가 활성값을 8 비트로 다시 양자화하며 행렬곱 하나에서 잃는 것(5.4 × 10⁻³)의 1/40~1/80, 밝힌 반실수 KV 의 손실(3 × 10⁻⁵)과 같은
자릿수. 물리적 바닥(프롬프트 1024 의 선형 층 정수 연산 / int8 최고치): XL 자리 둘 18.9 ms(자리 넷 37.8), small 1.1 ms.

## 어떻게

- **타일 판의 u.** 자리 둘에서는 T = 256·S₁ + S₀ 가 정수로 정확(|T| < 2²⁸)하고, v₁ + v₀ = T · 2^(E−13) 의 RN 은 RN(T) · 2^(E−13)
  (2 의 거듭제곱 곱은 정확) — u = (T 으로 짧은실수) × 2^(E−13), 그 비트는 M₀ − 2²² − 23·2²³. 블록마다 정수 → 실수 변환 하나와 곱 하나.
- **dp4a 줄 판 · 메가커널**은 자리 수만큼 S_j 를 모아 같은 식으로 — 타일 판과 비트까지 같다(같은 계약).
- **바꾸기**(정수로 · 층정규화정수 · 흐름어텐션정수 · _겔루정수)는 자리 둘만 쓴다 — 자릿값 칸이 반, 판의 자리 영역이 반.
- **판 표.** 자리 둘은 레지스터가 줄어 판 넷을 더 둔다(긴4 · 긴2 · 깊은 · 깊은넓은 — 호스트가 모양마다 재서 고른다). 자리 넷의 판 여섯은
  그대로.
- 값이 같음은 세 겹으로 봤다: CPU 참조(자리수=2)와 판 열 가지 × 두 형식 × small · XL 의 실제 층, small · XL 의 모든 길 · 메가커널, 4c.

## 경과 (판정 기준은 그대로 — 해 본 것과 안 된 것)

자리 넷 → 둘로 바꾼 직후(개발용 재기): XL Q4 프롬프트 92.0 → 60.0 ms(128 / 512 / 1024: 14.3 / 46.2 / 92.0 → 10.6 / 28.7 / 60.0; llama.cpp
10.8 / 28.1 / 55.4), small 6.2 → 4.6 ms(960). 타일 하나(XL c_fc, 행 1024)는 자리 넷 494 µs(53%) → 자리 둘 275~282 µs(**47~48%**).
그다음은 타일 효율을 올리려는 시도였고 — **모두 효과가 없었다**. 번갈아 재는 틀(같은 프로세스에서 변형들을 돌아가며 7번)로 잰 값:

| 시도 (값은 모두 같다) | 결과 (XL c_fc 긴타일) | 가설 |
|---|---|---|
| 끝 계산: 정수 → 실수 변환(cvt) | 282 µs, 47% | 기준 |
| 끝 계산: 마법수 덧셈 둘(변환 없음) | 315 µs, 42% | 변환 파이프가 병목 ✗ |
| 끝 계산: 마법수를 mma 누적 입력으로(명령 둘 줄임) | 337 µs, 39%, 넘침 48 B | 명령 발행이 병목 ✗ |
| 척도를 열마다 한 번 f32 로 넓혀 판에 | 같음 | 반실수 → 짧은실수 변환이 병목 ✗ |
| 워프를 더 띄우는 타일(256 스레드, 행 조각 하나) | 24~39% | 점유가 병목 ✗ |
| 행 조각 넷(깊은타일 64 × 128) · 판 넷(긴4) · 실행한도 2(긴2) | 44~46% | B 조각 준비의 나눠 쓰기 ✗ |

시간 나누기(변형 커널 — 전부 295 / 복사 없음 243 / 동기화 없음 285 / 곱만 220 / 끝만 255 / 읽기만 163 µs): 전역 → 판 복사는 18%, 동기화는
3% 이고, **복사와 동기화를 다 빼도 계산 핵심(판 읽기 + mma + 끝 계산)이 54%** 에서 멈춘다. mma 만은 60% (이론 131 µs 대 220). 출력 칸마다
블록마다 드는 끝 계산은 계약이 정한 몫(블록 32 칸마다 곱해더하기 하나)이라 자리 수와 상관없이 같고, 자리 둘에서는 그것이 mma 와 같은
무게가 된다. 더 가는 길은 끝 계산을 다른 워프에 맡기는 것(워프 분업)이나 블록 두 개를 한 바퀴에 — 다음 후보.

어텐션도 쪼갰다(XL 1024, 층당): 전부 240 µs, 점수 FMA 84, 가중합 FMA 64, **나머지 94 µs(39%)** — FMA 두 단계는 최고치의 57% 이고, 나머지는
셔플 → 지수 → 저장 → 동기화로 이어지는 직렬 사슬의 지연이다(판 48 KB 라 SM 에 블록 둘뿐 — 겹칠 워프가 없다). K · V 의 전역 읽기는 6 µs(small)
밖에 안 된다. 프롬프트 1024 에서 어텐션은 XL 20%, small 30% — 타일보다 큰 다음 지렛대이고, V 를 반실수로 판에 두고 K 를 한 조각 앞서
올리는 식의 구조 변경이라 따로 판정을 적고 한다.

## 판정 뒤의 판단

자리 둘은 **small 에서는 슬로건을 완성한다** — 프롬프트 · 생성 · 의미 · 정확도 모두 llama.cpp 를 이긴다. **XL 에서는 아직 4~22% 모자란다.**
타일 하나의 효율이 47% 에서 움직이지 않았고(위 "경과"), 어텐션의 직렬 사슬이 20% 를 먹는다. 둘 다 구조를 바꾸는 일이라 다음 단계로
넘긴다 — 판정부터 적는다.
