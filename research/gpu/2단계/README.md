## 2a 주소 공간 — 통과

규칙: **커널의 참조 매개변수는 전역 메모리를 가리키고, 거기서 나온 주소(색인·필드·복사)도 전역이다.** 타입처럼 전해질 뿐
추측하지 않는다 — 한 변수에 서로 다른 공간이 섞이면 그 커널은 예전처럼 범용 주소로 돌아간다. 그리고 주소가 load/store 의
자리로만 쓰이는 지역 변수는 레지스터에 둔다.

| 커널 | 전 (레지스터 / 스택) | 뒤 | 결과 |
|---|---|---|---|
| 벡터덧셈 | 16 / **40 B** | 14 / **0** | 1,048,576개 중 틀린 값 0 (손 PTX 12 / 0) |
| 벡터덧셈_보폭 | — / 스택 있음 | 16 / 0 | 틀린 값 0 |
| 곱더하기 | 16 / 48 B | 16 / 0 | CPU 의 글과 비트가 다른 값 0 |
| 제곱차 | — | 14 / 0 | x·x − x·x 가 0 이 아닌 칸 0 |
| 행렬곱 (감사 A1) | 30 / 88 B | 40 / 0 | B 14가지 불변, CPU 와 비트 같음. **19.8 ms → 3.7 ms** (B = 4096) |

## 2b 타일 — 통과

`타일행렬곱.gl` 은 32 × 32 블록이 입력·가중치의 조각을 공유 메모리에 올리고(동기화) 각 스레드가 자기 칸에 k 를 차례로 더한다.
연구용 내장 일곱(블록안가로·블록안세로·블록가로·블록세로·공유메모리0·1·동기화)을 쓴다 — 언어가 아니라, 타일을 손으로 써 보기 위한
것이다. 나중에는 배분어(`씩`·`마다`)에서 컴파일러가 이 꼴을 만들어야 한다(주장 C2).

| 잰 것 | 결과 |
|---|---|
| 타일 판의 출력 전체가 기준 판과 다른 B (14가지 중) | **없음** — 비트까지 같다 |
| 0번 행이 B = 1 과 다른 B | 없음 (행 불변) |
| 0번 행과 CPU 기준(같은 순서, 연산마다 반올림)이 다른 칸 | 0 |
| 시간 (B = 4096, 10회 중앙값) | 기준 판 3.67 ms → **타일 판 2.38 ms**, PyTorch `F.linear` 0.25 ms |

처음(19.8 ms)보다 8.3배 빨라졌고 PyTorch 와의 차이는 94배에서 약 9.6배로 줄었다. 남은 차이의 일부는 의미의 값이다 — PyTorch(cuBLAS)는
곱과 덧셈을 FMA 하나로 하고(반올림 한 번) 더하는 순서도 B 에 따라 바꾸지만, 글은 소스대로 연산마다 반올림하므로 같은 일에 명령이
둘 든다. 같은 의미로 견주면(주장 C 의 원칙) 차이는 더 작다 — 그 비교는 레지스터 타일까지 들어온 뒤에 다시 잰다.

## 2c 범위 검사 — 통과

실수 → 정수(·중간정수) 변환은 값이 대상의 범위 [lo, hi) 밖이거나 NaN 이면, 실수 → 짧은실수 변환은 유한한 값이 무한이 되면, 커널이
모듈의 오류 칸 `__geul_err` 에 비트를 켠다(1 정수, 2 짧은실수). 호스트가 실행 뒤에 읽는다.

| 입력 | 오류 칸 | 검사가 없을 때 GPU 가 조용히 낸 값 (정수 / 중간정수 / 짧은실수) |
|---|---|---|
| 범위 안 100만 개 (\|x\| < 2e9) | 0 — 결과가 정답과, 검사 없는 판과 비트까지 같음 | — |
| 3e9 | 1 | 3000000000 / **2147483647** / 3e9 |
| 2^31 | 1 | 2147483648 / **2147483647** / 2147483648 |
| 2^31 − 1 · −0.5 | 0 · 0 | (범위 안) |
| 1e19 | 1 | **9223372036854775807** / 2147483647 / 1e19 |
| NaN | 1 | **−9223372036854775808** / −2147483648 / NaN |
| 1e39 | 3 | 9223372036854775807 / 2147483647 / **inf** |
| inf | 1 | (정수 변환이 범위 밖, 짧은실수는 이미 무한이라 오류가 아님) |

비용: 1,600만 개에서 검사 판 1.009 ms, 검사 없는 판 1.034 ms — 잴 수 있는 차이가 없다(메모리가 병목인 커널).
같은 변환을 x86 CPU 는 범위 밖에서 정수의 최솟값을 내고 GPU 는 끝값으로 포화한다 — 이 규칙이면 둘 다 "오류"가 되어 CPU 와 GPU 의
의미가 갈리지 않는다. CPU 백엔드에 같은 규칙을 넣는 것과 글로 쓴 호스트(`쿠다.gl`)가 오류 칸을 읽게 하는 것은 다음 일이다.
f16·bf16 같은 낮은 정밀도 타입은 아직 언어에 없어서, 감사에서 본 "중간값이 f16 범위를 넘는" 꼴은 그 타입이 들어올 때 이 검사를
산술로 넓혀야 한다.

## 2e·2f·2g — 성능 (2026-10-08)

사용자 판단: 처음보다 빨라졌지만 다른 컴파일러보다 아직 많이 느려 쓸 수 없는 수준이다. 그래서 "쓸 만한 수준"의 첫 기준을
**같은 의미에서 PyTorch 의 2배 안**으로 먼저 적고(커밋 e22b424) 했다. 문제는 그대로 B = 4096, K = 1024, N = 512 (fp32).

| 판 | 시간 (ms) | PyTorch 대비 | 결과 |
|---|---|---|---|
| 기준 판 (행렬곱.gl, 출력 칸마다 스레드 하나) | 3.65 | 약 16배 (처음은 19.8 ms, 94배 — 2a 전) | 기준 |
| 2b 타일 (32 × 32, 공유 메모리) | 2.34 | 약 10배 | 기준 판과 비트까지 같음 |
| 2f 레지스터 타일 4 × 4 (2e 전 → 뒤) | 1.76 → 0.69 | 약 3배 | 비트까지 같음 |
| 2f 레지스터 타일 8 × 8 + 겹쳐 읽기 | **0.55** | **2.5배** | 비트까지 같음 — 연산마다 반올림 |
| 2g 합침(곱해더하기) 8 × 8 + 겹쳐 읽기 | **0.48** | **2.2배** (7번 재기의 중앙값, 범위 2.2~2.3) | 정확한 FMA 참값과 비트까지 같음 |
| PyTorch `F.linear` (cuBLAS) | 0.21 ~ 0.25 | 1 | 곱과 덧셈을 FMA 로, 더하는 순서는 B 에 따라 바뀜 |

모든 글 판은 B 14가지에서 0번 행의 비트가 바뀌지 않는다(행 불변). PyTorch 는 바뀐다(감사 A1).

**2e 정수 폭의 증명 — 통과.** 흐름을 따르는 구간 해석으로 정수 임시값의 범위를 구한다 — 근거는 상수, 스레드·블록 번호의
범위, 반복 조건으로 좁힌 변수뿐이고, 실행할 때 받는 크기에서 나온 값은 좁히지 않는다. 음이 아니고 32비트 범위임이 증명된
나눗셈·나머지를 32비트 명령으로 낸다(GPU 의 64비트 나눗셈은 소프트웨어로 돌아서 비싸다) — 레지스터 타일 판이 1.73 → 0.61 ms.
곱셈·주소 계산도 좁혀 봤지만 드라이버 컴파일러가 반복 변수의 곱을 덧셈으로 바꾸는 최적화와 겹쳐 이득이 없거나 오히려 느려졌다
(32 × 32 타일 2.29 → 2.98 ms) — 그래서 좁히지 않는다. 큰 입력 시험: 입력 원소 2,181,038,080개(최대 색인 > 2^31)에서 레지스터 타일
판이 기준 판과 출력 전체가 비트까지 같고 마지막 행이 CPU 기준과 같다([큰색인재기.py](큰색인재기.py)).

**2f 레지스터 타일 — 통과.** 스레드 하나가 4 × 4 칸(그리고 8 × 8 칸)을 레지스터에 든다. 더하는 순서가 그대로라 기준 판과 출력
전체가 비트까지 같다(B 14가지, CPU 기준). 겹쳐 읽기(지금 조각을 계산하는 동안 다음 조각을 레지스터로 미리 읽음)를 더한 판이 가장
빠르다. 소스는 [타일생성.py](타일생성.py) 가 만든다.

**2g 밝힌 합침 — 기준 미달 (2.2배).** 연구용 내장 `곱해더하기(x, y, z)` 는 `fma.rn` 하나로 내고, 소스가 이 낱말로 밝힐 때만
합친다. 정확한 FMA 참값(분수로 계산하고 한 번만 반올림)과 비트까지 같다. 시간은 PyTorch 의 2.2배 — 처음 잰 2.0배는 PyTorch 쪽 시간이
흔들려 나온 값이었고, 번갈아 일곱 번 잰 중앙값([배수재기.py](배수재기.py))은 2.23배다. 블록 수 때문인지 보려고 직사각 타일
(128 × 64, 64 × 128)도 재 봤지만 2.24~2.44배로 나아지지 않았다.

- **의미의 값은 크지 않다.** 연산마다 반올림하는 판(0.55 ms)은 합침 판(0.48 ms)보다 약 15% 느릴 뿐이다.
- **남은 차이의 후보**: 네 칸씩 한 번에 읽고 쓰는 벡터 메모리 명령(지금 글에는 그 표기가 없다 — `씩` 으로 말할 자리다, 주장 C2),
  공유 메모리를 두 판으로 겹치기, 64비트 주소 계산의 비용. 그리고 AI 연산에서 정말 쓸 만해지려면 f16·bf16 과 텐서 코어가 필요하다 —
  그때는 누적의 의미(순서·반올림)를 소스가 밝히는 규칙이 먼저 있어야 한다.
