# 12단계 — 겹치기 · 어텐션 · 지속 사용 (docs/17 §7 "12단계")

사용자 결정(2026-10-10): 겹치기 구조 변경을 진행하고 어텐션도 개선한다 — "특히 실사용에서는 지속적인 사용이 필수적인데 아무리 처음이
빠르더라도 사용할때 성능이 줄거나 더 느려지면 속도쪽에서 내세울 입지가 없어". 판정은 11단계의 기준 그대로에 실사용 둘(12f 자라는 대화,
12g 오래 돌리기)을 더해 실험보다 먼저 적었다(117e985). 값은 한 비트도 바꾸지 않는다 — 12a 가 확인한다.

## 해 본 것 중 안 된 것 (모두 비트 대조를 거쳤다 — 값은 같고 시간만)

| 시도 | 결과 |
|---|---|
| **타일의 비동기 장벽 판 `장벽판`** — 판마다 찼다(스레드마다 복사도착 + 장벽도착, 2T) · 다 썼다(T) mbarrier, 블록 kb 를 계산한 뒤 블록 kb + S − 1 을 올린다(블록마다의 기다림 · 동기화 없이) | c_fc 248 → 261 µs, c_proj 74 → 80 µs — 느림. 앞서 올리는 거리가 블록 둘에서 하나로 줄고 스레드마다 장벽 연산 셋 |
| 타일의 B 미리 읽기 `B미리` — 열 조각 n + 1 의 B 를 n 의 mma 앞에 | ±1% (같음) |
| 타일의 누적 마법수(`둘자리길 = "누적"`) — 변환 없이 mma 의 누적 입력으로 | 282~482 µs — 레지스터 넘침(8~96 B) |
| 갈래 판 바퀴를 다시 짜기(앞 바퀴 접기를 키 읽기 지연 동안) | 레지스터 255 · 넘침 48 B, 느리거나 같음 |
| 갈래 판에 다음 조각 L2 미리 · 워프 11 개 | 레지스터 255 · 넘침 32 B (느림) / 레지스터 168 · 넘침 208 B (느림) |
| 생성 메가커널: 머리 이어 달리기 · 접기 미리 읽기 · 조각의 값 L2 미리 · 도착 알리기 늦추기 | 730 → 1088 µs · 같음 · 700 → 704.5 · 700 → 703.5 |
| 생성 메가커널에서 조각마다의 64 비트 나눗셈 부름을 없앰 | 727 → 727 µs — 대역폭에 묶인 단계라 시간이 그대로(프롬프트 쪽에서는 크게 줄었다) |

**프로파일러가 보여 준 타일의 천장(XL c_fc, ncu).** 정체 표본: 텐서 파이프 대기(math) 28% · 발행 19% · 선택 안 됨 12% · 고정 지연
10% · 장벽 8% · 전역 대기 8%. mma 명령의 정체 78% 가 텐서 파이프가 바빠서다. SMSP 마다 바퀴의 텐서 일(워프 셋 × mma 32 × 16 사이클 =
1536 사이클)과 발행(워프 셋 × 445 명령 ≈ 1335)이 거의 같아, 워프 셋으로는 둘이 겹치지 않는다 — 장벽을 없애도(장벽판) 이 천장은 그대로다.
11단계의 결론("mbarrier 로 블록마다의 장벽을 없애고 올리는 워프와 곱하는 워프를 나누기")은 재 보니 맞지 않았다: 장벽은 8% 이고, 올리는
워프를 따로 두면 레지스터(159 × 160 스레드 × 3 블록 > 64K)가 SM 의 블록을 셋에서 둘로 줄인다.

**판정 뒤의 판단.** 사용자가 걱정한 "쓰는 동안 느려지는 것" 셋을 찾아 고쳤다 — 짧은 덩이(차례 판의 블록이 머리 수뿐 → 갈래 판), 나눗셈
하위 함수 부름(KV 끝손질), 파이썬 쓰레기 수거(계획이 쌓일수록 길어짐 → 얼림). 그 결과 자라는 대화(문맥 10만까지)와 오래 돌리기(2 분) 모두
llama.cpp 를 모든 구간 · 창에서 앞서고, 문맥 10만의 생성도 처음으로 앞선다. 겹치기 구조 변경(mbarrier)은 비트가 같지만 느렸고, 프로파일러는
타일의 천장이 장벽이 아니라 텐서 파이프와 발행이 같은 양이라는 데 있음을 보였다. 남은 것은 계약의 산술(자리 둘 · 블록마다의 끝 계산 · 적힌
지수)이 정하는 명령 수 — 바꾸려면 계약 쪽을 미리 적고 정확도를 다시 재야 한다. 긴 문맥의 짧은 덩이(16 · 128 · 256)는 아직 llama.cpp 보다
느린 곳이 있다(덩이 ≤ 16 은 머리 수만큼의 SM 만 쓴다 — 조각을 블록들에 나누면 차례 접기의 몫을 전역에 써야 한다).

## 바로잡은 기록 · 밝혀 둘 것

- **예비 실행.** 공식 실행 앞에 `a긴` 인자의 처리 잘못(고른 부분이 비면 모두 — 고침)으로 모든 부분이 한 번 돌았다
  ([결과/12단계_예비.json](결과/12단계_예비.json)). 그 결과를 보고 고친 것이 셋이다(값과는 모두 상관없다): (가) 마법수 읽기를 갈래 판에만,
  (나) 12g 의 창마다 같은 차례열 — 예비 실행은 창마다 씨앗 (13, i) 이라 창끼리 일감이 달랐다(글의 마지막 창 / 첫 창 0.835, llama.cpp 도
  0.87 — 일감의 차이가 섞였다), (다) 쓰레기 수거 얼리기 — 예비 실행 12f 의 구간 25600~38400 이 넣기 중앙값으로 졌다(34.2 대 32.9 ms); 그
  구간에 51.6 ms 인 차례(덩이 286)가 있었고 다시 재면 19.8 ms 였다 — 세대 2 수거.
- **12a 의 대조 스크립트 잘못(공식 실행 앞에 고침).** 프롬프트 어텐션의 출력 자리는 [자리 2][행수][너비] 라 자리 1 의 자리가 그 실행의 행수를
  따른다. 긴 문맥 대조와 갈래시험.py 가 가장 큰 행수로 읽어 덩이가 그보다 작으면 자리 1 이 엉뚱한 곳이었다(CPU 참조와 다른 칸이 났고,
  갈래 판 대 차례 판은 둘 다 같은 엉뚱한 곳이라 같았다). 고쳐서 다시 재니 모두 다른 칸 0. 그 사이에도 끝에서 끝 대조(비트시험 · 대화 길)는
  자리 1 을 c_proj 에 그대로 쓰는 길이라 통과하고 있었다.
- **미리 적은 할 일 중 하지 않은 것.** 비동기 복사의 주소를 32 비트로 — 하지 않았다. 프로파일러에서 복사와 주소는 표본의 몇 %
  (LDGSTS 2.4%, UIADD3 4.9%)였고, 천장은 위의 텐서 파이프 대기였다.
