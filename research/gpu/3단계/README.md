# 3단계 — GPT-2 small 을 글 커널로 (docs/17 §7 "3단계 시작")

실제 AI 모델 하나를 글로 쓴 GPU 커널로 돌려, 이전(PyTorch)과 무엇이 다르고 얼마나 좋은지 본다. 대상은 GPT-2 small
(openai-community/gpt2, 124M, fp32). 판정은 실험보다 먼저 적었다(커밋 06bb9e7). 이 PC: RTX 4070 Ti, PyTorch 2.14.1+cu130
(`build/감사venv`, TF32 꺼짐 — 기본값).

| 파일 | 무엇 |
|---|---|
| [gpt2.gl](gpt2.gl) | 글 커널: 임베딩, 층정규화, KV저장, 어텐션, 가장큰번호(다음 토큰 고르기) |
| [선형생성.py](선형생성.py) → [선형.gl](선형.gl) | 행렬곱 커널 9개(판 셋 × 끝손질 셋: 그대로·잔차 더하기·GELU). 더하는 순서의 약속은 생성기의 설명에 |
| [글gpt2.py](글gpt2.py) | 호스트 — **PyTorch 를 쓰지 않는다**: 가중치 파일 읽기(safetensors), 토크나이저(GPT-2 바이트 BPE), 커널을 부르는 순서, 탐욕 생성 |
| [토치gpt2.py](토치gpt2.py) | 비교 대상: 같은 모델의 PyTorch eager(fp32, 참값용 fp64)와 참고용 CUDA 그래프 판 |
| [재기.py](재기.py) | 3a·3b·3c 를 재서 [결과/3단계.json](결과/3단계.json) 에 적는다 |

```
build/감사venv/Scripts/python -I research/gpu/3단계/재기.py
```

모델 파일(config.json, vocab.json, merges.txt, model.safetensors 548 MB)은 사용자의 허락을 받아 Hugging Face 에서 `build/gpt2/` 로
내려받았다 — 저장소에는 넣지 않는다.

**무엇이 어디서 도는가.** GPU 계산은 모두 글 커널(글ptx.py → PTX → `nvcuda.dll`)이 한다. 토큰 하나에 커널 100개(임베딩 1, 층마다
8 × 12, 마지막 층정규화 1, 로짓 1, 가장큰번호 1). 다음 토큰도 GPU 에서 고르므로 호스트는 생성이 끝날 때까지 기다리지 않는다.
지수는 근사 명령을 쓰는 `근사지수`(소스가 밝힌 근사 — PTX 계약 P2), 제곱근·나눗셈은 정확한 반올림이다.

## 설계의 의미 — 순서는 약속, 블록 모양은 자유

한 토큰의 계산은 함께 계산하는 토큰의 수와 상관없게 했다(`행마다`).

- **선형** — 칸마다 k 를 16 가닥(k ≡ g mod 16)으로 나눠 가닥마다 차례로 곱해더하고(`곱해더하기`, 반올림 한 번씩), 치우침에 가닥
  0..15 를 차례로 더한다. 판 셋(블록 하나가 1행 × 32열, 4행 × 128열, 8행 × 128열)이 모두 이 순서를 지킨다. 그래서 행 수에 따라
  빠른 판을 골라도 칸마다 비트가 같다 — 합성 입력 다섯 모양 × 행 수 셋에서 모든 판이 1x1x32 판과 다른 칸 0.
- **층정규화** — 스레드마다 칸을 차례로 더하고 부분합 256 개를 정해진 나무 모양(반씩 접기)으로 더한다.
- **어텐션** — 질의마다 블록 하나. 더하는 순서는 그 질의의 위치에만 달렸다.

## 3a 정확성 — 기준 미달 (토큰은 셋 다 같음, 마지막 로짓의 오차가 한 프롬프트에서 2배를 넘음)

기준: 탐욕 생성 64토큰이 PyTorch 와 같고, 마지막 로짓(64번째 토큰을 고른 로짓)의 fp64 참값 대비 상대차(‖x − 참값‖₂ / ‖참값‖₂)가
PyTorch 의 2배 안. fp64 참값은 같은 모델을 PyTorch fp64 로 계산했다.

| 프롬프트 | 64토큰 | 마지막 로짓 상대차 글 / PyTorch | 배수 | 판정 |
|---|---|---|---|---|
| "The meaning of life is" (5토큰) | 같음 | 1.55e-7 / 1.04e-7 | 1.49 | 통과 |
| 유니콘 기사 첫 두 문장 (44토큰) | 같음 | 1.15e-5 / 3.23e-6 | **3.56** | 기준 미달 |
| "Alan Turing was a" (4토큰) | 같음 | 1.15e-7 / 6.92e-8 | 1.66 | 통과 |

생성 예: "Alan Turing was a" → " brilliant mathematician, and he was a great friend of mine. He was a great friend…" — 글과 PyTorch 가
64토큰까지 같고, fp64 참값도 같은 토큰을 고른다(세 프롬프트 모두).

**사후 분석 (판정이 아니다 — 기준은 바꾸지 않는다).** 로짓의 상대차는 걸음마다 1e-7 에서 4e-4 까지 출렁인다(두 쪽 모두).

| 프롬프트 | 64걸음 중앙값 글 / PyTorch | 64걸음 최댓값 글 / PyTorch | 글 ≤ PyTorch 인 걸음 | 2배 안인 걸음 | 걸음별 배수의 기하평균 |
|---|---|---|---|---|---|
| 1 | 1.35e-7 / 1.45e-7 | 5.7e-5 / 4.2e-4 | 37 / 64 | 58 / 64 | 0.78 |
| 2 | 1.17e-7 / 1.24e-7 | 1.15e-5 / 5.8e-6 | 31 / 64 | 58 / 64 | 0.93 |
| 3 | 2.10e-7 / 3.86e-7 | 1.1e-5 / 2.0e-5 | 37 / 64 | 58 / 64 | 0.78 |

- 걸음 전체로 보면 글이 평균적으로 PyTorch 보다 조금 정확하다(기하평균 배수 0.78~0.93). 근사 지수를 쓰는데도 그렇다 — 후보는 선형의
  16 가닥 합, 층정규화·어텐션의 나무 모양 합.
- **첫 판은 셋 다 기준 안이었다.** 층정규화·어텐션을 한 스레드가 차례로 더하던 첫 판의 마지막 걸음 배수는 1.86 / 1.20 / 1.54 였다.
  더하는 순서만 나무 모양으로 바꾼 판(긴 프롬프트가 3배 빨라짐)에서 문장 2 의 마지막 걸음이 글의 64걸음 중 가장 나쁜 걸음이 되었다.
- 마지막 한 걸음만 보는 기준은 더하는 순서 같은 작은 변화에도 판정이 뒤집히는 지표였다. 다음 판정은 걸음 전체의 분포(중앙값·기하평균)로
  미리 적는다.

## 3b 의미 (행 불변) — 통과

같은 토큰열(프롬프트 + 생성 64토큰)의 로짓을 여러 길로 계산해, 하나씩(decode 만) 계산한 기준과 비트가 다른 칸을 셌다. 세 문장
한 묶음은 길이가 같아야 해서 가장 짧은 길이(68토큰)로 잘랐다.

| 길 | 글: 다른 칸 | PyTorch: 다른 칸 (전체 칸 중) | PyTorch 최대 절대차 |
|---|---|---|---|
| 문장 1 한 번에 (prefill) | **0** | 3,268,495 (94%) | 0.011 |
| 문장 1 프롬프트는 한 번에, 나머지 하나씩 (생성할 때의 길) | **0** | 2,568,560 (74%) | 0.0027 |
| 문장 1 두 조각 | **0** | 3,269,084 (94%) | 0.0035 |
| 문장 2 한 번에 / 프롬프트+하나씩 / 두 조각 | **0 / 0 / 0** | 94% / 83% / 94% | 0.0007 |
| 문장 3 한 번에 / 프롬프트+하나씩 / 두 조각 | **0 / 0 / 0** | 96% / 83% / 95% | 0.0013 |
| 세 문장 한 묶음, 한 번에 | **0** | 9,706,088 (95%) | 0.0054 |
| 세 문장 한 묶음, 하나씩 | **0** | 8,098,598 (79%) | 0.0022 |

- 글은 같은 문장을 혼자 / 다른 문장과 함께 / 한 번에 / 하나씩 / 나눠서 계산해도 로짓이 비트까지 같다. 선형은 이 길들에서 서로 다른
  판(1행, 4행, 8행 블록)으로 돌았는데도 같다.
- PyTorch 는 같은 계산이 길에 따라 칸의 74~96% 에서 비트가 바뀐다. 서버가 함께 처리하는 요청의 수에 따라 같은 질문의 답이 달라질 수
  있는 까닭(LLM 추론의 비결정성)이 이것이다. 이번 세 프롬프트에서는 그 차이가 탐욕 선택을 바꾸지는 않았다(고른 토큰이 바뀐 행 0).

## 3c 속도 — 통과

배치 1 탐욕 생성. 토큰당 시간 = (64토큰 생성 시간 − 1토큰 생성 시간) / 63. 글·PyTorch 를 번갈아 7번 재서 중앙값.

| 프롬프트 | 글 (ms/토큰) | PyTorch eager | PyTorch CUDA 그래프 (참고) | 글 / eager |
|---|---|---|---|---|
| 1 (5토큰) | **1.47** | 3.29 | 1.54 | 0.45 |
| 2 (44토큰) | **1.48** | 3.19 | 1.53 | 0.46 |
| 3 (4토큰) | **1.47** | 3.18 | 1.54 | 0.46 |

프롬프트 처리 + 첫 토큰 (ms):

| 프롬프트 | 글 | PyTorch eager |
|---|---|---|
| 4~44토큰 (위 셋) | 2.3 / 3.2 / 2.3 | 4.6 / 3.9 / 3.9 |
| 128토큰 | 6.1 | 3.7 |
| 512토큰 | 26.0 | 6.9 |

- **생성은 PyTorch eager 보다 약 2.2배 빠르다.** 파이썬·실행 비용을 없앤 CUDA 그래프 판(판정 밖, 참고)보다도 약 4% 빠르다. 글 판은
  토큰마다 커널 100개를 부르는 데 호스트에서 약 0.5 ms 를 쓰고, GPU 쪽 시간이 그보다 길어 호스트가 기다리지 않는다. 토큰마다 읽는
  가중치가 약 0.5 GB 라 이 GPU(504 GB/s)에서는 1 ms 가 바닥이다 — 지금 1.47 ms.
- **긴 프롬프트 처리는 느리다** — 128토큰 1.6배, 512토큰 3.8배. 남은 몫은 행렬곱(16 가닥 순서를 지키는 타일이라 블록이 맡는 칸이
  작다)과 어텐션(질의마다 키·값을 다시 읽는다)이다. 첫 판(행 하나씩 계산)은 512토큰에 78 ms 였다.

선형 판 고르기 (합성 입력, 커널 하나의 시간 ms — 모든 판이 1x1x32 와 다른 칸 0):

| 모양 (행 × 깊이 × 열) | 1x1x32 | 4x4x32 | 8x4x32 |
|---|---|---|---|
| 1 × 768 × 3072 | 0.012 | — | 0.024 |
| 64 × 768 × 3072 | 0.257 | 0.081 | 0.077 |
| 512 × 768 × 3072 | 2.000 | 0.552 | 0.467 |
| 512 × 3072 × 768 | 1.943 | 0.532 | 0.482 |

그래서 행 하나는 1x1x32, 16행까지 4x4x32, 그 위는 8x4x32 를 쓴다.

## 적어 둘 것 (한계)

- 비교 대상은 이 연구가 쓴 PyTorch 판이다 — HF transformers 의 GPT-2 와 같은 연산(Conv1D = `addmm`, `layer_norm`,
  `scaled_dot_product_attention`, `gelu(tanh)`)을 부른다. transformers 는 이 PC 에 없어서 쓰지 않았다. transformers 의 `generate` 는
  이보다 파이썬 일이 많아 더 느리다 — 이 판이 더 빡빡한 비교다.
- fp32 만. f16·bf16·텐서 코어는 아직 없다 — 실제 서비스는 그쪽을 쓴다.
- 모델 하나(GPT-2 small), GPU 하나, 프롬프트 셋.
- 커널은 연구용 내장(블록 번호, 공유 메모리, 동기화, `곱해더하기`, `근사지수`, `제곱근`, `큰쪽`)으로 썼다 — 언어의 문법이 아니다.
  배분어(`마다`·`씩`)에서 컴파일러가 이 꼴을 만드는 것은 주장 C2 의 일이다.
- 오류 칸(2c 범위 검사)은 모든 실행 뒤 0 이었다.
- 3d(알려진 실수를 넣으면 컴파일이 거부)는 의미 층(축 표기)이 들어온 뒤에 한다.
