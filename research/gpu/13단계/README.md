# 13단계 — 두 층 접기: 긴 문맥의 짧은 덩이까지 (docs/17 §7 "13단계")

사용자 결정(2026-10-10): "어텐션을 고쳐봐" — 12단계 뒤의 추천(어텐션의 접는 순서를 두 층으로 바꾸는 계약 변경). 판정은 실험보다 먼저
적었다(422b705). 9단계의 접기는 키 조각(위치 64)을 처음부터 끝까지 한 줄로 접어, 한 (행, 머리)의 일을 블록들에 나눌 수 없었다 — 덩이가
짧으면 블록이 머리 수뿐이라 긴 문맥의 짧은 덩이가 llama.cpp 보다 느렸다(문맥 98K 덩이 16: 14.30 대 10.23 ms).

## 새 계약 — 위치 1024 이하는 비트 그대로

조각을 묶음(조각 16 개 = 위치 1024; 묶음 g 는 위치 [1024g, 1024g + 1024))으로 나눠 (1) 묶음 안에서 조각을 지금과 같은 식 · 같은 차례로
접어 묶음 상태 (M_g, L_g, O_g) 를 만들고(묶음의 첫 조각이 처음 값), (2) 묶음들을 g = 0, 1, … 차례로 같은 식으로 접는다(첫 묶음이 처음 값):
M′ = max(M, M_g), 가 = 적힌지수(M − M′), 나 = 적힌지수(M_g − M′), L ← 곱해더하기(L_g, 나, L·가), O ← 곱해더하기(O_g, 나, O·가). 묶음의
경계는 위치만으로 정해지므로 어느 길(프롬프트 · 나눈 덩이 · 대화 · 하나씩 · 메가커널)로 계산해도 같은 비트다. 위치 1024 까지는 묶음이
하나라 9~12단계와 비트까지 같다 — GPT-2 small · XL 의 모든 결과는 그대로(13a 가 12단계 나무와 견줘 확인한다). CPU 참조:
[정수계약.어텐션](../6단계/정수계약.py)(`묶음=16`; `묶음=None` 이면 옛 한 층 — 견주기용, `첫행` — 뒤의 행만).

## 바꾼 것 (값은 새 계약 그대로 — CPU 참조와 비트까지; 정수 KV 모듈만, 8단계까지의 모듈 소스 · PTX 그대로)

| 바꾼 것 | 무엇 | 결과 |
|---|---|---|
| 생성의 접기 `정수접기` (정수조각접기 · 생성 메가커널의 접는 블록) | 블록이 조각 256 개(묶음 16 개)씩: 묶음 안의 누적 최댓값(레인 16 개가 묶음 하나인 셔플), 묶음마다 L · O 사슬(O 는 스레드 256 이 (d, 묶음 넷)씩 — 조각 16 개를 먼저 띄운다) → 묶음 상태, 그다음 묶음 사이를 같은 식으로 | [접기시험.py](접기시험.py): numpy 의 두 층 접기와 모든 위치에서 다른 칸 0. 문맥 10만에서 따로 재면 24.5 → 27.7 µs 지만 메가커널의 걸음은 같다(8815 µs 안팎 — [메가단계](../12단계/메가단계.py)로 12단계 나무와 번갈아) |
| 묶음 판 `정수어텐션묶음` (질의 64) | 차례 판과 같은 몸으로 블록 하나가 (머리, 질의 64, 묶음 g) 의 조각 ≤ 16 개를 접어 행마다의 묶음 상태를 묶음칸 [행][머리][묶음][68] 에. 격자는 (질의 조각 + 질조각수 · (머리 + 머리수 · 묶음), 문장) — 같은 (머리, 묶음)의 질의 조각들이 이웃(L2 에서 키 · 값을 나눈다). 유효한 행이 없는 워프(짧은 덩이)는 계산을 건너뛴다 | 문맥 98K: 덩이 64 801 µs (12단계 갈래 판 1094), 128 1281 (2186), 256 2508 (차례 3598), 1024 9996 (차례 10407) — 층 하나 |
| 묶음 판 `정수어텐션갈래묶음` (질의 16) | 12단계 갈래 판의 몸(워프 여덟이 조각 여덟을 함께)으로 블록 하나가 (머리, 질의 16, 묶음 g) — 바퀴 둘이 묶음 하나 | 짧은 덩이가 메모리에 묶인다: 문맥 98K 덩이 16 691 µs(KV 306 MB 를 443 GB/s — torch 의 합으로 잰 이 GPU 의 실제 읽기 대역 460~467 GB/s 의 96%), 2048 덩이 16 17 µs (질의 64 판 43) |
| 묶음 접기 `정수묶음접기` | 블록(64 스레드)이 (머리, 행) — 묶음 상태를 차례로 접어 출력 자리 · 정보로(정수어텐션과 같은 바꾸기). 누적 최댓값은 셔플 훑기, 가 · 나는 묶음마다 함께, 사슬만 차례로 | 문맥 98K 덩이 16 9 µs, 64 17 µs, 192 111 µs, 1024 717 µs(묶음 상태 321 MB 읽기) |
| 두 층 차례 판 `정수어텐션두층` | 차례 판과 같은 격자로 조각을 차례로 돌되 묶음의 첫 조각에서 처음 값, 묶음 끝마다 행의 누적 상태(두층칸 — 블록 · 스레드마다 낱말 40, [블록][넷 10][스레드][4] 라 ld · st .v4)와 접는다. 누적 상태를 레지스터에 두면 232 + 36 > 255 | 합성 16384 프롬프트의 한 층 11.82 ms (12단계 차례 판 11.68 의 1.012배) |
| 호스트 (글gpt2.py) | 최대길이 > 1024 인 엔진만 새 판: 행 ≤ 묶음판행(1024)이면 묶음 판 + 묶음 접기 — 위치마다 질의 16 / 64 판과 격자(묶음 수)를 고른다(`_묶음판고르기` — 그래프의 위치 마디를 고칠 때 함수 · 격자 · 블록도 함께), 넘으면 두 층 판. 위치 1024 이하의 엔진(GPT-2 small · XL)은 12단계의 판 그대로 | 아래 13c |
| 조각칸을 행 넷 이상으로 | 행 넷까지의 프롬프트는 생성 판(정수조각어텐션)이 조각칸에 행마다 쓰는데 칸은 최대문장 행이었다 — 최대문장 1 인 엔진(긴 문맥 · 12f · 12g 의 엔진)에서 덩이 2 ~ 4 가 칸 끝을 넘어 썼다 | 고침. 9~12단계의 잰 실행에는 덩이 2 ~ 4 가 없었다(12a 의 대화는 1 과 5 이상, 12f 16 이상, 12g 16 이상) — 13a 에 덩이 2 · 3 · 4 를 섞은 대화를 더했다 |

## 해 본 것 중 안 된 것 (모두 비트 대조를 거쳤다 — 값은 같고 시간만)

| 시도 | 결과 |
|---|---|
| 묶음 판(질의 64)에서 유효한 행이 없는 워프의 계산만 건너뛰기 — 짧은 덩이를 메모리에 묶으려고 | 문맥 98K 덩이 16 720 → 697 µs (3%) — 블록마다 계산하는 워프가 하나라 그 워프의 지연이 천장. 질의 16 판을 따로 만들었다 |
| 묶음 접기를 판에 먼저 올리는 꼴(256 스레드, 판 36 KB) | SM 에 블록 둘 — 짧은 문맥에서 느림(2048 · 16: 4.8 → 7.3 µs, 98K · 64: 16.7 → 30.2) |
| 묶음 접기의 전역 읽기를 처음에 모두(묶음마다 레지스터 하나 — 255) | 98K · 16 9.1 → 8.5 µs 지만 98K · 64 16.7 → 26.5, 192 111 → 149 — 뺐다 |
| 두 층 판에도 워프 건너뛰기 | 16384 프롬프트 1.019 → 1.027배 — 긴 덩이에만 쓰는 판이라 뺐다 |
| 두층칸 읽기를 다음 조각의 지수풀기 앞으로 당기기(지연 겹치기) | 1.019 → 1.039배 — 레지스터 배치가 바뀌었다(접기를 아예 빼도 1.028배) |
| (참고) 개별 띄움마다 이벤트로 잰 커널 시간 | 작은 커널은 띄움 지연이 섞여 크게 나온다(묶음 접기 27 µs 로 보였으나 잇달아 띄워 재면 9 µs) — 나누기.py 는 잇달아 스무 번 |

**판정 뒤의 판단.** 목표(긴 문맥의 짧은 덩이)는 이뤘다 — 12단계 끝에서 llama.cpp 보다 느리던 열한 칸이 모두 앞서고, 자라는 대화(12f)의
넣기도 여덟 구간 모두 0.70~0.81배(12단계 0.76~0.94). 13d 의 세 칸은 13단계가 값 · 커널을 바꾸지 않은 길에서 12단계에도 1% 안팎이던
차이가 이번 실행에서 넘어간 것이다 — 판정 뒤에 12단계 나무와 번갈아 재니 small 1024 프롬프트는 두 나무가 같고(Q8_0 3.79~3.84 대
3.83~3.85, Q4_0 3.98~4.00 대 3.98~4.00 ms — 둘 다 12단계 공식 값보다 느린 날), 생성 메가커널의 걸음도 같았다(문맥 10만 8807~8820 대

단계 사이를 줄여야 한다.
