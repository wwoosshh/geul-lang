## 1단계 탐침 (2026-10-08) — 통과

이 PC: RTX 4070 Ti (sm_89), CUDA 드라이버 13.4. **CUDA 툴킷·nvcc 는 없다** — 그래픽 드라이버의
`nvcuda.dll` 만 쓴다.

```
python ref/geulc.py research/gpu/탐침/실행기.gl -o build/실행기.exe
build/실행기.exe research/gpu/탐침/손벡터덧셈.ptx vadd                 (* 1a: 손으로 쓴 PTX *)
python research/gpu/글ptx.py research/gpu/탐침/벡터덧셈.gl -o build/벡터덧셈.ptx
build/실행기.exe build/벡터덧셈.ptx 벡터덧셈                            (* 1b: 글 소스에서 만든 PTX *)
python research/gpu/글ptx.py research/gpu/탐침/벡터덧셈_보폭.gl -o build/보폭.ptx
build/실행기.exe build/보폭.ptx 벡터덧셈_보폭 16                       (* 1b: 반복문·실행개수 — 블록 16개로 100만 원소 *)
```

셋 다 `1048576개 중 틀린 값 0개, 합[12345] = 37035`. 격자 보폭 판은 스레드 4,096개가 원소를 256개씩 맡는다 —
반복문(점프·분기)과 GPU 내장 `실행개수`, 복합 대입까지 PTX 로 옮겨졌다. 소스에서 GPU 실행까지 C 가 한 줄도 없다:
커널은 글로 쓰고 참조 구현의 앞단이 타입 IR 로 내리고, 호스트도 글로 써서 드라이버를 외부 선언으로 부른다.

### 관찰 — 의미가 어디서 끊기는가

1. **PTX 는 ASCII 만 받는다.** 주석에 한글이 한 글자만 있어도 드라이버가 `cuModuleLoadData` 를
   "invalid argument" 로 거부한다(파이썬으로 같은 파일의 한글을 빼면 통과 — 원인 확정). 그래서 한글 이름은 기계와의
   경계에서 `_G` + UTF-8 16진수로 바뀐다(`벡터덧셈` → `_Gebb2a1ed84b0eb8da7ec8588`). 이름이라는 의미는 경계를 넘을 때
   대응표로만 이어진다 — 변환기와 호스트(`쿠다.gl` 의 `PTX이름`)가 같은 규칙을 따로 구현해 맞췄다.
2. **자리(주소 공간)의 의미가 IR 에 없다.** 글의 타입은 `짧은실수 참조` 까지만 말하고, 그 참조가 전역·공유·지역
   메모리 중 어디를 가리키는지는 말하지 않는다. 그래서 변환기는 모든 읽기·쓰기를 범용 주소(`ld.f32`)로 낸다 —
   `ld.global.f32` 를 낼 근거가 없다. 의미 층이 채울 첫 빈칸.
3. **조사의 역할이 IR 에서 사라진다.** 커널 머리의 `첫째에서`·`둘째와`·`합에` 는 앞단까지 살아 있다가 IR 의
   매개변수 `p0..p3` 에서 지워진다. 남아 있었다면 읽기만 하는 자리(`에서`)에 쓰는 코드를 거부할 수 있고(정확성),
   읽기 전용 캐시(`ld.global.nc`)를 쓸 수 있다(성능) — 같은 의미가 두 쪽에 다 쓰인다.
4. 지역 변수가 메모리 자리(`.local`)를 거친다. IR 이 비SSA 메모리 슬롯 형태라서다. PTX JIT 가 레지스터로 올리므로
   탐침에는 문제가 없지만, 성능 단계에서 다시 본다.
5. 실행기를 쓰며 글의 키워드와 부딪힌 이름: `결과`(D-18 키워드), `묶음`(선언 키워드). 외부 선언에서 같은 타입인데
   역할이 다른 자리(장치 주소와 크기, 핸들과 핸들)는 호출부에 조사를 요구받았다(D-30) — `cuMemcpyHtoD` 의
   대상·원본·크기를 바꿔 넘기는 실수가 문법으로 막힌다.

### 기계어까지 — 드라이버의 정답지와 cubin 직접 실행 (탐침 S0, 2026-10-08)

PTX 의 마지막 단계(PTX → SASS 기계어)는 NVIDIA 드라이버 안의 비공개 컴파일러가 한다. 그 결과를 꺼내 보면:

```
python research/gpu/탐침/드라이버기계어.py build/벡터덧셈.ptx build/벡터덧셈.cubin
build/실행기.exe build/벡터덧셈.cubin 벡터덧셈            (* PTX 없이 기계어 파일을 바로 *)
```

| | 레지스터 | 스택 | cubin |
|---|---|---|---|
| 손 PTX (`vadd`) | 12 | 0 | 3,496 B |
| 글이 만든 PTX (`벡터덧셈`) | 16 | **40** | 4,136 B |

- **기계어까지 내려갔다.** 드라이버가 이 GPU(sm_89)용 cubin(ELF, PTX 글자 없음)을 만들었고, 글로 쓴 호스트가 그 cubin 을
  PTX 없이 `cuModuleLoadData` 로 올려 실행했다 — 틀린 값 0. 이때 드라이버는 로더 역할만 한다. CPU 쪽에서 Windows 가 글의
  PE 를 올리는 것과 같은 자리다. 남은 것은 이 파일을 글이 직접 만드는 일(SASS 인코딩 + cubin 포장).
- **자리의 의미 손실이 기계어에서 값을 치른다.** 같은 일을 하는 두 커널에서 글 쪽만 스택 40바이트를 쓴다. IR 이 주소
  공간을 몰라 지역 변수를 범용 주소로 다뤘고, 드라이버 컴파일러가 그 값들을 레지스터로 올릴 수 없었다.
- **정답지가 공짜다.** 어떤 PTX 를 줘도 드라이버가 이 GPU 의 정답 기계어를 돌려준다. 글이 SASS 를 직접 낼 때 같은 커널의
  드라이버 cubin 과 바이트 대조하면 된다 — 참조 구현과 자체 컴파일러를 대조해 온 방식 그대로이고, CUDA 툴킷의 역어셈블러도
  필요 없다.

### S1 — 기계어 파일(cubin)의 포장을 글이 직접 쓴다 (2026-10-08) — 통과

```
python research/gpu/탐침/드라이버기계어.py research/gpu/탐침/손벡터덧셈.ptx build/손.cubin    (* 정답지 *)
python ref/geulc.py research/gpu/탐침/큐빈.gl -o build/큐빈.exe
build/큐빈.exe build/손.cubin build/글판.cubin                    (* SASS 만 가져와 글이 처음부터 다시 포장 *)
python research/gpu/탐침/큐빈쓰기.py build/손.cubin build/파이썬판.cubin
build/실행기.exe build/글판.cubin vadd
```

글로 쓴 작성기(`큐빈.gl`)와 파이썬 참조판(`큐빈쓰기.py`)의 출력이 **바이트까지 같고**(2,240 B), 드라이버가 그것을 받아
GPU 가 실행한다 — 손 PTX 커널도, 글 커널(2,752 B)도 1,048,576개 중 틀린 값 0. SASS 명령 바이트와 코드의 사실(레지스터 수,
매개변수 크기, 종료 위치)은 아직 드라이버 cubin 에서 가져온다(S2 에서 글이 낸다). 형식은 `큐빈해부.py` 로 풀었다.

**드라이버가 요구하는 최소 구성** (실험으로 찾음 — 섹션을 하나씩 빼며 받아들이는지 봤다)

| 섹션 | 필요 | 비고 |
|---|---|---|
| `.shstrtab` `.strtab` `.symtab` | 필요 | 기호: 빈 기호, `.text`·`.nv.constant0` 섹션 기호, 커널(전역 함수, other 0x10) |
| `.note.nv.tkinfo`, `.note.nv.cuinfo` | **필요** | 빼면 "device kernel image is invalid". 형식만 무효로 바꿔 두면 받는다 — 이름으로 찾는 듯. 내용(도구 문자열)은 검사하지 않는다: 우리 문자열로 바꿔도 받는다. cuinfo 는 tkinfo 를 가리킨다 |
| `.nv.info.<커널>` | 필요 | 매개변수 정보가 여기 있다 (아래) |
| `.nv.constant0.<커널>` | 필요 | 0x160 + 매개변수 바이트, 0 으로 채움 |
| `.text.<커널>` | 필요 | `sh_info` 윗바이트 = 레지스터 수, 아래 = 커널 기호 번호 |
| 전역 `.nv.info`, 프로그램 헤더, `.debug_frame`, `.nv.callgraph`, `.nv.rel.action` | 없어도 됨 | 글 커널의 스택 40 B 도 전역 정보(스택 크기) 없이 돌았다 — 드라이버의 기본 스택 안이라 그런 듯(미확인; 큰 스택은 필요할 수 있다) |

배치 규칙은 NVIDIA 와 같다: 드라이버 cubin 의 섹션 14개를 우리 규칙(머리 | 섹션 자료 | 섹션 머리표 | 프로그램 헤더)으로
다시 쓰면 3,496 B 전부가 같다.

**메타데이터를 하나씩 뺐을 때** — 가장 바닥에서는 검사가 거의 없다

| 뺀 것 | 결과 |
|---|---|
| 0x5F·0x66(이름 모름), `CUDA_API_VERSION`, `MAXREG_COUNT`, `EXIT_INSTR_OFFSETS`, `CBANK_PARAM_SIZE` | 그래도 돈다 |
| `PARAM_CBANK` (매개변수가 놓일 상수 영역) | 실행 중 "illegal memory access" |
| `KPARAM_INFO` (매개변수가 무엇인가) | **오류 없이 1,048,576개 중 1,048,575개가 틀린다** |
| 레지스터 수를 적게 적음 (12 → 4) | 이번엔 맞았다 — 운인지 드라이버가 다시 세는지 모른다(위험) |

매개변수의 의미를 적은 메타데이터가 빠지자 오류 코드 하나 없이 결과가 조용히 틀렸다. 의미 손실이 오류 없는 오답이 되는
모습이 기계 메타데이터 수준에서 그대로 나온다 — 아래로 갈수록 의미를 지킬 책임이 컴파일러로 넘어온다(주장 A).

덤: 작성기를 쓰다가 글의 D-30 이 `바이트열_고치기64(출력, 40, 길이)` — 자리와 값이 둘 다 정수 — 를 바꿔 쓰기 위험으로 거부했다.
ELF 머리의 섹션 머리표 위치를 고치는 자리였다. 조사를 붙여 `(출력 에, 40 에, 길이 을)` 로 밝혔다.

**이 갈래는 S1 에서 멈춘다** (2026-10-08). S2·S3 는 중단했고 이유는 [docs/17 §7](../../docs/17-연구-의미를-지키는-GPU-컴파일러.md)에
있다. 위에 적은 "S2 에서 글이 낸다", "드라이버 cubin 과 바이트 대조" 계획은 하지 않는다. 대신 PTX 를 계약 경계로 삼는다(아래).

## PTX 계약 P1 — 곱과 덧셈의 합침 (2026-10-08) — 통과

PTX 의 `mul.f32`·`add.f32` 는 반올림을 적지 않으면 드라이버가 FMA 하나로 합쳐도 되는 명령이다. 합치면 반올림이 한 번
빠져, 곱하고 반올림한 뒤 더하고 반올림하는 글의 CPU 백엔드(`mulss`·`addss`)와 값이 달라진다. 처음 판의 `글ptx.py` 가
이 꼴을 냈고 드라이버가 실제로 합쳤다 — 벡터 덧셈에는 곱이 없어 1단계에서는 드러나지 않았다.

```
python ref/geulc.py research/gpu/탐침/곱더하기실행기.gl -o build/곱더하기실행기.exe
python research/gpu/글ptx.py research/gpu/탐침/곱더하기.gl -o build/곱더하기.ptx
build/곱더하기실행기.exe build/곱더하기.ptx 곱더하기
python research/gpu/탐침/반올림빼기.py build/곱더하기.ptx build/곱더하기_반올림없음.ptx     (* 고치기 전 꼴 *)
build/곱더하기실행기.exe build/곱더하기_반올림없음.ptx 곱더하기
```
