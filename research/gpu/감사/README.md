# 감사 — 기존 스택의 밑바닥에 남은 조용한 손실을 찾는다 (docs/17 §7 방향 수정)

0단계는 실제 버그를 분류했다. 이 갈래는 그 분류를 **지도**로 삼아, 아직 아무도 고치지 않은 조용한 손실이 기존 AI 연산
스택에 남아 있는지 이 PC 에서 직접 찾는다. 대상은 PyTorch(CUDA 판)다 — vLLM 은 Windows 에서 돌지 않고, llama.cpp 의
CUDA 판은 툴킷이 있어야 빌드된다.

아래 "방법"은 검사를 돌리기 전에 적고 커밋했다(2026-10-08). 결과는 그 뒤에 붙인다.

## 방법

### 환경
RTX 4070 Ti (sm_89), 드라이버 CUDA 13.4, Windows 11, Python 3.12.10, PyTorch 2.14.1+cu130 (download.pytorch.org 의 공식 판,
`build/감사venv` 에 따로 설치). 기본 설정은 건드리지 않는다 — 사용자가 처음 받았을 때의 동작을 잰다.

### 성질 — "의미"를 검사할 수 있는 꼴로

| 성질 | 뜻 | 0단계 갈래 |
|---|---|---|
| 행 불변 | 한 행(토큰·시퀀스)의 결과는 함께 계산한 다른 행의 수와 상관없다 (글: `행마다`) | 흐름 |
| 배치 무관 | 같은 값이면 메모리 배치(전치·건너뛴 자르기·보폭 0·어긋난 시작)가 달라도 결과가 같다 | 자리 |
| 정수 폭 | 원소 수·바이트가 2^31 을 넘어도 먼 자리의 값이 맞다 | 자리 |
| 범위 | 참값이 그 타입으로 표현되면 NaN·Inf 가 나오지 않는다 | 정체 |
| 정밀도 | 타입(fp32·fp16)을 밝힌 연산은 그 타입의 정밀도로 계산된다 | 정체 / 컴파일러 재량 |

### A1 — 알려진 손실을 재현한다 (방법이 통하는지 본다)

**행 불변.** 연산마다 0번 행의 결과를 행 1개로 계산한 것과, 행 B 개 중 하나로 계산한 것을 **비트로** 견준다.
B ∈ {1, 2, 3, 4, 8, 16, 32, 64, 128, 256, 512, 1024, 2048, 4096}, 타입 fp32·bf16·fp16.

- PyTorch: `F.linear`(K = N = 4096, 그리고 K = 1024·N = 512), `sum(dim=-1)`, `softmax`, `rms_norm`, `layer_norm`(행 길이 4096),
  `scaled_dot_product_attention`(시퀀스 B 개, 길이 512, 머리 8, 머리 차원 64 — 0번 시퀀스를 견준다).
- 글: 같은 행렬곱(K = 1024, N = 512, fp32)을 글로 쓴 커널(출력 칸마다 k 를 차례로 더함, `.rn`)로 돌린다. 기준은 같은 순서로
  fp32 를 연산마다 반올림한 CPU 값이다.

**판정**: PyTorch 에서 B 에 따라 0번 행의 비트가 달라지는 연산이 하나 이상 있고, 글 커널은 모든 B 에서 같고 CPU 기준과 비트가
같으면 A1 통과.

### A2 — 지도로 찾는다

검사 목록 (이것만 돌린다 — 결과를 본 뒤 늘리면 그 사실을 적는다).

**H1 정수 폭** — N1 = 2^31 + 2^20 원소. 값은 맞는지 정확히 알 수 있게 만든다(0·1, 위치의 나머지, 작은 정수).
1. `torch.ones(N1, int8).sum()` = N1
2. 끝 원소 읽기: `x[-1]`, `index_select`, `take` — 끝에 써 둔 값 그대로
3. `argmax` (fp16, 끝 자리 하나만 1) = N1 − 1
4. 브로드캐스트 덧셈 `zeros(N1) + ones(1)` (int8) — 합 = N1, 끝 = 1
5. 전치 복사 `[32768, 65568]` (int8, 값 = 위치 % 127) — 먼 자리 표본이 맞는가
6. `torch.where` (int8, N1) — 먼 자리 표본
7. 행 softmax `[2^21 + 1, 1024]` (fp16) — 마지막 행이 그 행만 계산한 것과 같고 합이 1 근처
8. `F.embedding` (가중치 `[2^21 + 1, 1024]` fp16) — 마지막 행을 그대로 꺼내는가
9. 출력이 2^31 원소를 넘는 행렬곱 `[65536, 16] @ [16, 32784]` (fp16, 값 0·1·2 — 모든 부분합이 정확) — 마지막 행이 정확한가
10. `layer_norm` `[2^21 + 1, 1024]` (fp16) — 마지막 행이 그 행만 계산한 것과 1e-2 안

H1 의 손실은 **크게 틀린 값**(상대 1e-2 넘게, 또는 NaN)으로 센다. 마지막 자리의 작은 차이는 행 불변의 문제라 A1 쪽이다.

**H2 배치 무관** — `[1024, 1024]` 무작위 값에서 뷰 넷(전치, `[:, ::2]`, 보폭 0 으로 펼침, `[1:, 3:]`), 타입 fp32·fp16·bf16.
- 정확해야 하는 연산(원소별·변환): add, mul, div, exp, log, sin, tanh, sigmoid, gelu, silu, sqrt, rsqrt, pow(·, 3), abs, 타입 변환 —
  `op(뷰)` 와 `op(뷰.contiguous())` 가 **비트까지** 같아야 한다. 다르면 손실.
- 줄이기 연산(sum, softmax, layer_norm, 행렬곱)은 비트 차이를 참고로만 적는다 — PyTorch 가 약속하지 않는 성질이다.

**H3 범위** (fp16, 그리고 bf16) — 참값을 fp64 로 계산해 그 타입으로 표현되는데 NaN·Inf 가 나오거나 상대 1e-2 를 넘게 틀리면 손실.
1. softmax (로짓 6e4 근처) 2. logsumexp (6e4 근처) 3. layer_norm (3e4 ± 1) 4. rms_norm (3e4 근처) 5. `linalg.vector_norm` ([3e4] × 4 = 6e4)
6. var·std (3e4 ± 1) 7. scaled_dot_product_attention (점수 1e5 근처) 8. cross_entropy (로짓 6e4 근처) 9. cosine_similarity (3e4 근처, 길이 1024)
10. mean ([6e4] × 1024)

**H4 정밀도** — 기본 설정 그대로, fp64 참값과의 상대 오차가 그 타입의 정밀도(fp32 는 1e-5, fp16 은 1e-2)를 넘으면 손실.
1. conv2d fp32 2. 행렬곱 fp32 3. 행렬곱 fp16 — 참값 0 이고 부분합이 fp16 최댓값을 넘는 입력(±300 번갈아, 길이 1024 × 64)
4. 행렬곱 bf16 (긴 K) 5. scaled_dot_product_attention fp32

### 찾은 것의 갈래
손실마다 PyTorch 저장소의 이슈와 문서를 찾아 셋 중 하나로 적는다: **알려짐**(이슈가 있음), **문서화된 기본값**(문서에 적힌
설정의 결과), **새로 찾음**(찾아도 없음 — 찾은 질의를 적는다). 업스트림에 이슈를 올리는 것은 사용자가 정한다.

### A2 판정
**새로 찾음**이 1개 이상이면 이 갈래가 값을 낸다. 0개면 "이 목록에서는 못 찾음"으로 적고, 목록을 넓힐지는 그때 정한다.

### 미리 적는 한계
- 한 PC, 한 GPU 세대(Ada), 한 판(2.14.1). 다른 GPU·판에서는 다를 수 있다.
- PyTorch 는 성숙한 스택이라 새 손실이 나오지 않을 수 있다 — 그것도 결과다.
- `torch.compile` 은 Windows 에서 Triton 이 없어 이 목록에 넣지 않았다(0단계 컴파일러 버그의 대부분이 그쪽이었다).

### A1 행 불변 — 통과

| 연산 | 0번 행의 비트가 B 에 따라 바뀌는가 |
|---|---|
| **글 행렬곱** (fp32, K = 1024, N = 512, [행렬곱.gl](행렬곱.gl)) | **바뀌지 않는다** — B 14가지 모두 같고, CPU 기준(같은 순서, 연산마다 반올림)과 512칸 모두 비트가 같다 |
| PyTorch `linear` | 바뀐다 — fp32·fp16 은 B ≥ 2 전부, bf16 은 4096×4096 에서 B ≥ 2 전부·1024×512 에서 B ≥ 1024. 최대 절대차 fp32 7.6e-6, fp16 2.0e-3, bf16 1.6e-2 |
| PyTorch `sum(dim=-1)` | fp32 만 바뀐다(B 14가지 중 11). bf16·fp16 은 같다 |
| `softmax`·`rms_norm`·`layer_norm`·`scaled_dot_product_attention` | 이 모양에서는 바뀌지 않는다 (SDPA 는 메모리 때문에 B ≤ 512 로 줄였다) |

- 알려진 성질이다. PyTorch 의 수치 정확도 노트가 "`(A@B)[0]` 은 `A[0]@B[0]` 와 비트가 같다고 보장되지 않는다"고 적고,
  Thinking Machines(2025-09)가 LLM 추론에서 온도 0 에서도 답이 바뀌는 주원인으로 짚었다.
- 값: B = 4096 에서 글 커널 19.8 ms, PyTorch `F.linear` 0.21 ms — 약 94배 느리다(2단계 2a 뒤에는 3.7 ms — `결과/행불변.json` 은 2a 뒤에 다시 만든 것이다). 타일·공유 메모리가 없는, 의미를 지키는 기준
  커널이라서다. 의미를 지키면서 빠르게 하는 것은 구조 가설(2단계 뒤)의 몫이다.

### A2 지도 검사 — 새로 찾은 손실 0 → "이 목록에서는 못 찾음"

| 묶음 | 검사 | 손실 |
|---|---|---|
| H1 정수 폭 | 12 (argmax 의 자리 셋 포함) | 0 — 원소가 2^31 을 넘는 텐서에서 열 가지 연산이 모두 맞았다 |
| H2 배치 무관 | 원소별·변환 180 조합 (fp32·fp16·bf16) | 0 — 모두 비트까지 같다. 줄이기(참고)는 fp32 `sum`·행렬곱과 fp16 `sum` 이 뷰에 따라 비트가 다르다 |
| H3 범위 | 22 (fp16·bf16) | 1 — fp16 `cosine_similarity` |
| H4 정밀도 | 8 (3b 덧붙임 포함) | 2 (같은 원인) — fp16 행렬곱 |

**찾은 손실 둘**

1. **fp16 `cosine_similarity`** — 한 벡터의 노름이 fp16 최댓값(65504)을 넘으면, 거의 같은 두 벡터의 유사도가 1 이 아니라
   **정확히 0** 이다(길이 1024 에서 값 2047 까지는 1, 2048 부터 0). GPU·CPU 가 같고 경고가 없다. 참값(≤ 1)은 fp16 으로 표현된다 —
   중간값(노름)만 넘친다. → **알려짐**: [pytorch/pytorch#69512](https://github.com/pytorch/pytorch/issues/69512) — 2021-12 에 열려
   아직 열려 있다. 그때의 재현(작은 무작위 값)은 이제 맞지만 노름이 범위를 넘는 경우는 그대로다. 그 이슈에서 메인테이너들은
   "silent correctness 가 아니라 전형적인 저정밀 문제"라는 의견과 "이런 복합 연산의 정밀도를 무엇으로 보장할지 정해야 한다"는
   의견으로 갈렸다.
2. **fp16 행렬곱** — 모든 값이 fp16 으로 정확하고 참값이 0 인데, K = 8192·65536 에서 inf·NaN 이 나온다(K = 1024 는 0).
   기본값인 줄인 정밀도 줄이기(`allow_fp16_reduced_precision_reduction = True`)를 끄면 정확히 0 이다. → **문서화된 기본값**:
   PyTorch 의 CUDA 노트가 이 설정을 "수치 정밀도와 넘침 가능성을 대가로" 성능을 얻는 것이라고 적는다.

덧붙임을 밝힌다: 방법에 적은 3a(±300 번갈아)는 어느 연속 구간에서도 부분합이 300 을 넘지 않아 이 넘침을 일으킬 수 없다. 그래서
방법을 커밋한 뒤, 돌리기 전에 3b(앞 절반 +300, 뒤 절반 −300)를 더했다. 3a 는 통과했다.

### 무엇을 뜻하나

- **가설 "밑바닥에 조용한 손실이 잠재한다"** — 이 PC 의 PyTorch 에서는 **있지만 알려져 있다.** 5년 가까이 열린 이슈, 문서에 적힌
  기본값, 문서에 적힌 묶음 대 조각의 차이. 모르는 손실이라기보다 **아무도 보장하지 않는 손실**이다. 업계에 빠진 것은 버그 목록이
  아니라 "이 연산은 무엇을 보장하는가"의 계약이다 — #69512 에서 메인테이너가 말한 그것.
- 찾은 둘은 0단계의 같은 갈래다 — **정체: 값이 형식의 범위를 넘음**(중간값만 넘치고 참값은 표현된다). 0단계에서 "좁히기의 범위 검사"
  규칙이 있어야 막힌다고 적은 조건부 3개와 같은 꼴이다. 그 규칙의 값이 실제 스택에서 다시 확인됐다.
- 성숙한 PyTorch eager 연산은 정수 폭(H1)과 원소별 배치 무관(H2)에서 단단했다. 0단계의 실제 버그는 대부분 빠르게 바뀌는 층 —
  vLLM·llama.cpp·FlashAttention 의 손 커널과 torch.compile — 에서 나왔다. 새 손실을 찾으려면 다음 감사는 그쪽이어야 한다
  (llama.cpp 는 Windows 용 CUDA 판을 내려받아 돌릴 수 있고, vLLM 은 Windows 에서 돌지 않으며, torch.compile 은 Triton 이 필요하다).
- 글이 줄 수 있는 것은 그 계약을 **말로 적고 지키게 하는 것**이다 — `행마다`(행 불변: A1 에서 글 커널은 지켰다), 연산마다 반올림
  (PTX 계약 P1), 좁히기의 범위 검사(위 두 손실의 갈래).

## A3 — llama.cpp 감사 (방법, 2026-10-08 — 돌리기 전에 커밋)

0단계에서 실제 버그가 몰린 곳은 손으로 짠 커널이었다. 그래서 둘째 대상은 llama.cpp 의 CUDA 커널이다.

- **대상**: llama.cpp b11496 (2026-10-08) 의 공식 Windows CUDA 13.4 판 — `llama-b11496-bin-win-cuda-13.4-x64.zip`(153 MB)과
  `cudart-llama-bin-win-cuda-13.4-x64.zip`(423 MB), 릴리스의 SHA-256 과 맞춤. `build/llama-b11496` 에 풀었다.
- **방법**: 릴리스에 시험 도구가 없어서 ggml 의 C API(`ggml-base.dll`·`ggml.dll`, 백엔드는 이름으로 `CUDA0`·`CPU`)를 파이썬
  ctypes 로 부른다. 검사 하나를 프로세스 하나로 돌린다 — ggml 이 단언(abort)으로 멈추면 그것은 "오류로 멈춤"이지 조용한 손실이 아니다.
- **기준**: 정확히 알 수 있는 값(작은 정수, 위치의 나머지)은 그 값과, 그 밖은 fp64 참값과 견준다. 행 불변은 CUDA 안에서 비트로 견준다.

**검사 목록** (이것만 돌린다)

| 성질 | 검사 |
|---|---|
| 행 불변 | `mul_mat` 가중치 f32·f16·q8_0·q4_0 (K = N = 4096), 활성 f32 의 열 수 M ∈ {1,2,3,4,8,16,32,64,128,256,512} — 0번 열의 결과가 M = 1 과 비트로 같은가. `rms_norm`·`soft_max` (행 길이 4096) 도 같은 방법 |
| 정수 폭 | (a) `add` f16, 원소 N1 = 2^31 + 2^20 (0 + 1 로 브로드캐스트) — 먼 자리 표본 (b) 전치 뒤 `cont` f16 `[65568, 32768]`, 값 = 위치 % 127 — 먼 자리 표본 (c) `soft_max` f32 `[1024, 2^19 + 1]` (바이트 오프셋이 2^31 을 넘음) — 마지막 행이 그 행만 계산한 것과 같은가 (d) `rms_norm` 같은 모양 (e) `get_rows` f16 표 `[1024, 2^21 + 1]` 에서 마지막 행 (f) 출력 원소가 N1 인 `mul_mat` (값이 정확한 입력) (g) `flash_attn_ext` — 가리개 원소가 2^31 을 넘는 크기(KV 262144 × 질의 8192), 질의 행마다 다른 가리개 — 마지막 질의 행을 fp64 로 계산한 값과 견줌 |
| 배치 무관 | 원소별 연산(`add`·`mul`·`sqr`·`sqrt`·`gelu`·`silu`·`exp`·`scale`) f32 에서 뷰 셋(전치, 행 간격이 넓은 `view_2d`, 어긋난 시작) — `op(뷰)` 와 `op(cont(뷰))` 가 CUDA 안에서 비트까지 같은가 |
| 범위 | (a) `mul_mat` f16 가중치에서 참값 0 이고 부분합이 65504 를 넘는 입력(앞 절반 +300, 뒤 절반 −300, K = 8192) (b) `mul_mat` f16 가중치에 f16 범위를 넘는 활성(1e5)을 곱함 — 참값은 f32 로 표현된다 (c) `flash_attn_ext` f16 에서 q·k 가 65504 를 넘는 점수 — 참값은 유한하다. M ∈ {1, 64} 처럼 커널 경로가 갈릴 만한 크기를 함께 본다 |

찾은 것의 갈래와 판정은 A2 와 같다 — llama.cpp 저장소의 이슈·문서를 찾아 알려짐·문서화된 기본값·새로 찾음으로 나누고,
**새로 찾음 1개 이상**이면 이 대상에서 감사가 값을 낸다.

**새로 찾음 — CUDA `scale` 이 행 간격이 넓은 뷰를 연속이라고 보고 읽는다.** `ggml_scale` 은 행 간격이 있는 입력을 받아들이고
(`ggml_is_padded_1d`), CUDA 와 CPU 백엔드 모두 `supports_op` 에 "지원한다"고 답한다. 그런데 CUDA 커널(`ggml-cuda/scale.cu`)은
원소 수만 받아 평평하게 돌아서, 뷰의 시작부터 연속된 원소를 읽는다 — 결과가 "연속이라고 본 앞부분 × 1.7" 과 비트까지 같고,
524,288칸 중 523,776칸이 틀린다(어긋난 시작은 1,000,000칸 중 999,000). 오류도 경고도 없다. 같은 그래프를 CPU 백엔드는 단언으로
멈춘다 — **같은 연산이 한 백엔드에서는 멈추고 다른 백엔드에서는 조용히 틀린다.** llama.cpp·ggml 저장소에서 `scale non-contiguous`,
`ggml_scale contiguous`, `scale noncont`, `ggml_scale`, `scale padded`, `cuda scale stride`, `GGML_OP_SCALE non-contiguous`(ggml 저장소 포함)로
찾았으나 보고가 없었다. llama.cpp 의 모델 그래프가 실제로 이 꼴을 쓰는지는 확인하지 않았다 — 같은 ggml 을 쓰는 다른 프로그램도 닿는다.
갈래는 0단계의 **자리 — 배치 가정**(보폭을 무시함)이다.

**알려짐 — f16 의 범위.** (a) 는 cuBLAS 경로의 f16 누적이 넘치는 것으로, llama.cpp 가 이미 다룬 갈래다(PR #3816, #19959 "cuBLAS 의
넘침을 피하려 fp32, 계산 타입을 고르는 환경 변수", #20078). (b) 는 f16 가중치와 곱하려고 활성을 f16 으로 바꾸다 넘치는 것으로, 같은
꼴이 Metal(#26223 — 0단계 표본에도 있다)과 Vulkan(#18969 "f16 acc overflow")에서 보고·수정됐다. CUDA 의 같은 사례는 찾지 못했지만
갈래가 알려져 있어 보수적으로 알려짐에 둔다.

**정수 폭 (g) 의 진단 — 자리 손실이 아니라 묶음에 따라 바뀌는 정밀도.** 모든 질의가 같고 가리개가 모두 0 인 한 번의 실행에서, 원소
오프셋이 2^31 을 넘는 행(8192·8255)은 0번 행과 비트까지 같았다 — 먼 자리는 맞게 읽는다. 대신 같은 질의의 정확도가 **함께 계산하는
질의 수에 따라** 크게 바뀐다(이것은 미리 적은 검사가 아니라 진단에서 드러난 것이다).

| 같은 질의를 함께 돌린 질의 수 | 1 | 2 | 8 | 64 | 512 | 2048 | 8256 |
|---|---|---|---|---|---|---|---|
| fp64 참값과의 상대차 | 4.2e-7 | 1.3e-3 | 1.3e-3 | 2.8e-3 | 7.7e-3 | 1.5e-2 | 2.2e-2 ~ 2.6e-2 |

한 번의 실행 안에서도 64개짜리 질의 묶음의 자리에 따라 결과의 비트가 다르다(0~63 과 8192~8255 는 같고, 64~8191 은 다름). 혼자 계산하면
fp32 수준(4e-7)인 같은 행이 큰 묶음 안에서는 약 6만 배 덜 정확하다 — 행 불변과 정밀도 갈래가 겹친 손실이다. ggml 에는 flash attention 의
정밀도를 고르는 설정(`ggml_prec_set_acc`)이 있으므로 갈래는 **문서화된 기본값**에 둔다.

**판정**: 새로 찾음 1 (CUDA `scale`) → 이 대상에서 감사가 **값을 낸다.** 업스트림에 알리는 것은 사용자가 정한다.
