# 11단계 — 프로파일러가 가리킨 곳 (docs/17 §7 "11단계")

사용자 결정(2026-10-10): 10단계의 다음 갈래 중 프로파일러를 먼저. 변형의 시간 나누기로는 타일 뼈대 안의 37% 가 어디로 가는지 보이지 않았다.
판정은 10단계의 기준 그대로 실험보다 먼저 적었다(d411536).

**도구.** Nsight Compute 2026.3.1.2 — 사용자 허락으로 받은 NVIDIA CUDA 재배포 압축(nsight_compute-windows-x86_64-2026.3.1.2-archive.zip,
486,786,020 바이트, redistrib_13.4.2.json 의 SHA-256 과 같음, NVIDIA SLA). 설치 없이 `build/ncu-2026.3.1.2/` 에 둔다(git 밖). ncu 는
한글이 든 경로에서 시작하지 못해(코드 페이지 변환 오류 — 대상과 상관없이) 실행은 ASCII 경로에 푼 사본에서, 대상 스크립트도 ASCII
이름의 얇은 실행기로 띄웠다(저장소 경로는 16진수로 넘김). 성능 계수기는 드라이버 설정이 이미 열려 있었다(RmProfilingAdminOnly = 0).
재는 대상은 실제 XL 1024 프롬프트를 그대로 다시 띄우며 20번째 층의 일곱 실행만 cuProfilerStart/Stop 사이에 둔 것.

## 바로잡은 기록

- 10단계의 **엇갈림** 변형은 값이 틀렸다 — 열 조각 n 의 척도(d₀ · d₁)를 읽은 뒤 n − 1 의 끝 계산을 해서 칸의 75~87.5% 가 틀림. 비트 대조
  없이 시간만 잰 변형이었고 어느 모듈에도 없었다(10a 판정은 그대로). 척도를 조각마다 따로 두어 고쳤고, 겹침 + Pd 접기(역시 틀림)는
  생성기에서 막았다. docs/17 10a 칸 · 10단계 README · 사례 표에 적었다.
- 6단계 행렬곱시험은 처음 여섯 판만 CPU 참조와 대조해 왔다 — 8단계 이후 더한 판(긴4 · 긴2 · 깊은 · 깊은넓은)은 줄 판과의 끝에서 끝 대조로만
  확인돼 왔다. 11a 부터는 모듈의 판 표 전부를 CPU 참조와 대조한다.

**판정 뒤의 판단.** 프로파일러가 가리킨 두 곳(A 조각 옮기기, 척도를 읽자마자 넓히던 워프 둘)을 고치자 타일이 11~16% 빨라졌고, XL 프롬프트가
처음으로 llama.cpp 와 PyTorch f16 을 모든 길이 · 두 형식에서 앞섰다(1024 에서 0.88 · 0.95배 · 0.79 · 0.81배). 값은 한 비트도 바뀌지 않았다.
그래도 타일은 최고치의 절반 남짓이다 — 새 타일은 SMSP 마다 발행 시간과 텐서 시간이 비슷한데 실제 시간은 둘의 합에 가깝다(mma 와 끝 계산이
겹치지 않는다). 다음 지렛대는 구조(비동기 장벽 mbarrier 로 블록마다의 장벽을 없애고 올리는 워프와 곱하는 워프를 나누기)와 어텐션의 적힌
지수(더 싼 적힌 식 — 계약 변경이라 미리 적고 정확도를 다시 잰다)다.
