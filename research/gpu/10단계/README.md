# 10단계 — 바탕부터: XL 프롬프트를 바닥 쪽으로 (docs/17 §7 "10단계")

사용자 결정(2026-10-10): 범위(Llama 계열 · 다른 GPU)를 넓히기 전에 바탕이 되는 길(타일 · 어텐션)을 먼저 바닥 가까이 맞춘다 — 범위를 먼저
넓히면 모든 범위에서 속도를 다시 맞춰야 한다. llama.cpp 는 이 조건의 기준이지 최고 속도가 아니다. 판정은 실험보다 먼저 적었다(ef25845).

**판정 전에 잰 것** 은 docs/17 10단계 절에: XL q8_0 1024 의 커널별 시간(타일 45.9 ms = 84%, 어텐션 6.8, 층정규화 1.8), PyTorch 로 낸 빠른 길의
참고선(f16 cuBLAS + SDPA, CUDA 그래프 — XL 11.4 / 31.5 / 64.7 ms, small 1.31 / 2.85 / 5.56; torch._int_mm 은 더 느림), 바닥(XL 1024 20.9 ms).

읽기: 타일은 뼈대(mma · 조각 읽기 · 고리)만으로 63% 라 끝 계산을 완전히 숨겨도 60% 언저리이고, 끝 계산은 ptxas 가 이미 섞고 있어 더 숨길
자리가 없다. 레지스터(168 — 3 블록)와 점유의 균형이 지금 자리이고, 어텐션은 사슬을 둘로 나눠도 동기화가 그만큼 든다. 프로파일러(Nsight)가
없어 명령 단위의 병목은 못 본다 — 변형의 시간 나누기가 할 수 있는 끝이다.

**판정 뒤의 판단.** 이 단계는 속도를 하나도 바꾸지 못했다 — 모든 시도가 같거나 느렸고 값은 9단계 그대로다. 배운 것은 천장의 모양이다:
타일은 뼈대(mma · 조각 읽기 · 고리)만으로 63% 라 끝 계산을 완전히 숨겨도 60% 언저리이고, 끝 계산은 컴파일러가 이미 섞고 있으며,
레지스터(168 — 블록 셋)와 점유의 균형이 지금 자리다. 어텐션은 사슬을 둘로 나눠도 동기화가 그만큼 든다. 지금 도구(변형의 시간 나누기)로
볼 수 있는 끝에 왔고, 명령 단위의 병목은 프로파일러가 있어야 보인다. 다음 갈래는 넷 — 프로파일러(내려받기 — 사용자 결정), 이름 붙은
장벽으로 올리는 워프와 곱하는 워프를 나누기, 자리 하나 계약(선택지), 범위 넓히기(Llama 계열).
