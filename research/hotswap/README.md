# 핫스왑 탐침·데모

[docs/14-핫스왑-방향.md](../../docs/14-핫스왑-방향.md)를 뒷받침하는 최소 산출물. 방향·이정표 증거이며 제품 코드가 아니다. 재현 산출물은 `build/`(무시됨)에 나온다.

## 확인 사실 (2026-09-20)

### 탐침-대입.gl — 암시 변환은 막혀 있다 (막힌 채로 둔다)

```
python ref/geulc.py research/hotswap/탐침-대입.gl
```

**거부됨:** `오류: '공허 참조' 타입을 '[ -> 정수]'에 넣을 수 없습니다`. 임의 주소가 대입만으로 함수가 되지 않는다. 이정표 1 이후에도 이 암시 경로는 계속 막는다 — 여는 것은 명시 변환 한 곳뿐이다(아래).

### viability.c — 이 머신에서 협조적 핫스왑이 물리적으로 되는가 (C)

글이 아니라 C(`zig cc`). OS·보안 SW 가 협조적 핫스왑을 허용하는지만 본다. kernel32 만 쓴다.

```
zig cc research/hotswap/viability.c -o build/viability.exe && build/viability.exe
```

**통과:** `v1=111 / v2=222`. VirtualAlloc RW → 본문 기록 → RX(W^X) → 포인터 호출 → RW 되돌려 교체 → RX → 재호출. 주입·프롤로그 덮어쓰기 없음. 세션을 죽이던 보안 SW 가 이 협조적 방식은 막지 않았다.

## 이정표 1 (2026-09-20)

### 글-테이블교체.gl — 1a: 우회 + 교체 + 상태 보존 (컴파일러 변경 없음)

```
python ref/geulc.py research/hotswap/글-테이블교체.gl -o build/글-테이블교체.exe && build/글-테이블교체.exe
```

**통과:** `v1=105 / v2=-95 / 누적=2`. 함수 포인터로 부르고 실행 중 `더하기→빼기`로 교체했으며 전역 상태 `누적`이 교체 뒤에도 살아남았다(2). 여기서 교체는 **미리 컴파일된 함수 사이**의 전환이다.

### 글-핫스왑.gl — 1b: 글이 새 기계코드를 부른다 (참조 구현 변경)

```
python ref/geulc.py research/hotswap/글-핫스왑.gl -o build/글-핫스왑.exe && build/글-핫스왑.exe
```

**통과:** `v1=111 / v2=222`. viability.c 가 C 로 보인 것을 글 자신이 한다 — VirtualAlloc 으로 잡은 메모리에 `mov eax,imm; ret` 본문을 써 넣고, 그 주소를 함수로 불러, 본문을 바꿔 재시작 없이 다시 부른다.

**필요했던 언어 변경(통제된 한 곳, ref·self 양쪽):** 공허 참조를 명명 함수 타입으로의 **명시** 변환(`자리 으로 코드조각`). `별칭 코드조각는 [-> 정수].` 로 이름을 준 함수 타입에만 쓴다.
- `ref/geul/sema.py` · `self/의미.gl` — 명시 캐스트 `ok` 에 `공허 참조 → 함수` 한 줄. 암시 변환(`coerce`/`강제변환`)에는 넣지 않았다 — 그래서 위 탐침-대입.gl 은 여전히 거부된다.
- `ref/geul/lower.py` · `self/하강.gl` — 캐스트 하강의 copy 경로에 `ptr → func`(둘 다 64비트 주소).

**검증:** 수용 테스트 193/193(ref·self 양쪽), 자체호스팅 고정점 1·2·3세대 바이트 동일. 정식 spec-test `3.8-변환/06-공허참조를-함수로`(통과)·`07-공허참조-함수-암시거부`(거부)가 경계를 지킨다. 위 글-핫스왑.gl 은 글로 쓴 컴파일러(`build/self_컴파일러.exe`)로 빌드해도 v1=111→v2=222 로 같다.
